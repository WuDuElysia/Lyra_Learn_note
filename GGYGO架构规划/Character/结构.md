## InitState 注册与 PawnData 分发（Gate80 有限验收）

启动配置链由[[System/结构|System]]提供同GI的原生注册前置，Character使用原feature状态机与PawnData分发入口。全局顺序和每个Actor feature的状态唯一归`UGameFrameworkComponentManager`；Extension持有PawnData，CMC接收并校验MovementSet，Hero管理自己的玩家输入装配。配置分发、Host绑定与Health资源订阅各有独立生命周期。

| 入口／调用方 | 输入与实际调用 | 产物及边界 |
| --- | --- | --- |
| 原生 GI → `UGGYGOInitStateRegistrationSubsystem::Initialize` | `UGameInstance::Init` 的 `SubsystemCollection.Initialize(this)` 创建子系统；`InitializeDependency<UGameFrameworkComponentManager>()` 取得同一原 GI 的 Manager，按 Spawned→DataAvailable→DataInitialized→GameplayReady 锚点调用 `RegisterInitState` | 三组相邻正向 true、逆向 false 全通过后才输出 `RegisteredOrder`；已有逆序或无效依赖明确诊断，不重排、不补第二顺序表／Ready／轮询。 |
| Extension → `CheckDefaultInitialization` | PawnData／Controller／其他 feature 的原生通知触发；先 `CheckDefaultInitializationForImplementers`，再 `ContinueInitStateChain` | DataAvailable 要求实际 PawnData；Authority／本地控制端还须 Controller。本地 StateChain 和 feature 注册均不建立全局顺序。 |
| Extension → `CanChangeInitState` | DataAvailable→DataInitialized 查询 `HaveAllFeaturesReachedInitState(Pawn, DataAvailable)` | 所有 feature **已达到或超过** DataAvailable 才分发；各 feature 独立推进，可以处于不同阶段。没有独立的 MovementSet 异步加载等待。 |
| Extension → `HandleChangeInitState` | 进入 DataInitialized 时唯一调用 `ApplyPawnDataToConsumers`，向原 CMC 执行 `SetMovementSet(PawnData->MovementSet)` | CMC 保持配置接收与校验职责；Cue 预热在 setter 之后。Host 绑定、ASC Ready 与 Base／Health typed 订阅各走自己的生命周期，不能作为这次配置分发的串行门禁。 |
| Hero → `CanChangeInitState`／原生输入入口 | Hero 的 DataInitialized 只要求 Extension ≥ DataAvailable；`BeginPlay` 和 `CharacterBase::SetupPlayerInputComponent` 沿既有入口调用 `InitializePlayerInput` | Hero 可以先到 GameplayReady；Setup 可独立建立输入会话。Hero 的 `HandleChangeInitState` 返回后引擎仍提交状态，缺 InputComponent／相机检查提前返回不构成状态守卫。 |

`UGameInstance::ReceiveInit` 先于子系统初始化，不能在该早期事件假定注册已完成；刻意不调用 `Super::Init` 的 Input TestGI 也不具有本前置。每个原 GI 在原生子系统初始化中登记一次；System 新类没有 Manager 缓存、订阅、Tick 或额外资源清理，Actor feature 的注册与注销仍由各组件生命周期负责。

Hero沿原Source创建Session，由CMC创建原Binding，自己持原OwnerSync Observer；真实Started记录或原OwnerSync Ready返回后，查询原Source仍Held才调用`TryAdmitInitialMovementInputRequest`。请求与执行状态归Input／CMC，Hero不补Press或持第二held。原通知／Session／Binding按来源精确清理，接口见[[Movement/结构|Movement]]、[[Input/结构|Input]]。

原Manager的全局顺序必须先于feature推进建立；空顺序表只能判断相同标签，不能把较晚阶段识别为“已达到DataAvailable”。因此System在同GI原生初始化中登记并核对正逆关系；本地StateChain不承担全局顺序。`HasReachedInitState`的同标签相等查询本身不证明顺序有效。

启动配置只分发PawnData与MovementSet，不签ASC Binding或Ready；Health入口仍须明确原Extension／H／认证PublishedContext。实际启动、资源与死亡合同的有限验证分别见[[计划_角色与组件#14.9 Health唯一原资源与Base消费接力|计划记录与验证边界]]。

## Host原生请求接口（已定义，生产迁移中）

`IGGYGOAvatarBindingHostInterface::RequestAvatarBinding`是Character与共同Host的原生协作端口。`AGGYGOCombatantState`编排生产请求，Extension三入口只请求Initialize／Release／Refresh，本组件不持独立ASC缓存或执行ActorInfo写入。Release／Refresh从原H的ASC组件GetOwner捕获Host、从原记录取Context，不按可变ActorInfo Owner猜原端点。已提交Context清理与未提交Init的原Operation分别由ASC认证，见下表和[[AbilitySystem/结构|ASC清理契约]]；Host流程见[[Combatants/结构|Combatants]]。

| 接口／数据 | 输入、作用与输出 |
| --- | --- |
| `IGGYGOAvatarBindingHostInterface::RequestAvatarBinding(Request)` | 同步native纯虚入口。Request携Initialize／Release／Refresh、原weak Host／ASC／Pawn／Extension、原Context及opaque H；Init要求空H，Release／Refresh要求原H及Context。Host编排原资源，不成为ActorInfo执行器。 |
| `FGGYGOAvatarBindingHostResult` / `StepResult` | 默认Rejected／InvalidRequest；`Steps`只记录实际已返回的ASC／本地资源／输入清理历史。保留ASC原`bCommitted`，不增加顶层Ready／Bound／成功提交权威；返回历史不授当前权限。 |
| 原生Busy与接续 | 未完成原生写入中明确Busy、不排队；普通Ready／Released完整原生返回后允许同步接续。旧请求被后继取代即停止，不能借当前H继续清理。 |
| Host H1 → `CheckAvatarBindingCleanupContext(Context,OutReason)` | Release及自身已提交失败收尾核对原已提交来源，支持匹配的Current／Revoked cleanup；不要求工作Ready。关闭原Host／Owner显式选择ClearActorInfo，正常路径PreserveOwner，不由ASC替模式或失败重试。 |
| Host H2 → `TryCleanupFailedAvatarActorInfoInit(OriginalOperation,IsOriginalCallerCurrent)` | Initialize及owner-only Init未commit失败分支只提交该次返回Operation与同步纯原作用域；ASC认证并执行自己的原残留清理。Host记录实际返回步骤，原Init仍失败；cleanup成功仍不提交Binding，不产生Receipt／Notice／Ready。不能把H1的已提交Context资格用于这条未提交清理。 |

跨Host转交由外层先请求旧Host Release并核对实际结果，再请求新Host Initialize；新绑定失败保持未绑定，不自动回滚。ASC唯一签发Binding、执行ActorInfo事务并认证Publish；Host选择和公布Avatar，Extension唯一持本地资源，Health／Hero／CMC各管自身订阅与资源。

## ASC 本地资源四阶段接口（L1）

Host调用本地四阶段，Extension的Getter、注册回放和Ready查询只认真实原H及当前发布资格；Health／Base／Hero消费带身份通知。Installed与Ready分开表达装配和可用性，步骤历史、槽快照或曾发布过的Receipt均不授当前执行权限。

`FGGYGOPawnASCResourceIdentity` 为原 weak ASC、Pawn 和 ASC 签发 Binding；opaque `FGGYGOPawnASCResourceHandle` 只由 Extension 创建，调用方持有原句柄清理。Binding / ActorInfo / 发布凭据唯一归 [[AbilitySystem/结构|ASC]]；Host 负责选择和公布 Avatar，Extension 只管自己本地记录与通知，Health / Hero / CMC 各自管理实际订阅和执行资源。

| 实际接口及输入 | 作用与输出 |
| --- | --- |
| `InstallLocalAbilitySystemResources(ASC, Pawn, CommittedContext)` | 核对当前 ASC Context 和实际 Avatar，仅安装本地记录，返回原资源及本地结果；不开放 Ready，不执行 ActorInfo 写入或分发 PawnData。 |
| `WithdrawLocalAbilitySystemResources(Resource)` | 精确核对当前原记录，先撤当前槽再标记原记录；无广播、Cancel、Cue 或原生 ASC 操作，失效 ASC 也可清自身资源。 |
| `NotifyLocalResourcesReleased(Resource)` | 要求原记录已撤出，先消费一次通知义务再广播带身份通知；旧栈不清后继。EndPlay先关闭新准入；关闭的Released只退休原义务并明确Failed／LifecycleClosed，不广播、不清后继。 |
| `NotifyLocalResourcesReady(Resource, Publication)` | 先验 ASC 的真实 Dispatching，再读取发布证据；匹配原资源及 Context 后才发布 Ready。同 Binding Refresh 只更新曾真实 Ready 的资源，不把未 Ready 安装升级。 |
| `GetCurrentLocalAbilitySystemResource()` | 游戏线程复制当前 opaque 本地槽，包括未 Ready 或 ASC 已失效的记录；仅供发现并捕获原句柄，不保证 Installed／Ready，不授予执行资格。 |
| `IsLocalAbilitySystemResourceInstalled(Resource)` | 只读核对当前原槽、weak 对象、当前 ASC Binding 与实际 Avatar；不要求 Ready，可用于提交后／发布前的装配检查。 |
| `IsLocalAbilitySystemResourceReady(Resource)` | Installed 之外，还须曾真实 Ready 及精确 PublishedContext 的当前发布资格；安装缓存或历史 Receipt 不构成可用资格。 |
| `RegisterLocalAbilitySystemNoticeAndCall(Delegate)` / `UnregisterLocalAbilitySystemNotice(Handle)` | 返回精确委托句柄；立即回放只认当前经认证Ready，清理只移除自身原订阅。Ready／Refreshed携原H与认证PublishedContext；Released携原H、空PublishedContext，只证明本地撤回，不证明ASC Clear提交。 |

结果的 `bLocalChanged` 和资源存在性只描述历史本地动作，不承诺 ASC 全局提交或当前 Ready。外调后重验原对象／资源／发布作用域，失效明确返回，不借后继身份继续。新 API 不授予能力、不取消 GA、不写 CMC，不新增 Binding 号、帧调度器或第二事实来源。

Host安装链：ASC Try真实提交 → Extension Install → Host公布 → ASC Publish → 真实Dispatching桥接Ready；退出链：Withdraw → 原Context Cancel／输入／Cue → ASC Clear → Host退原资源／订阅 → 发布Released。已提交Context清理显式选择Clear模式，未提交Init清理使用该次原Operation；Cue在Clear前使用旧Avatar。普通Ready／Released允许完整原生返回后的合法同步接续，失去原范围的旧栈停止，不清后继。

Getter／注册门禁只认真实Ready；Release不经Getter过滤原资源。Host新装配预检一次捕获原句柄，再检验原身份与Installed；不能用Ready过滤未发布装配，也不能在外调后读取当前槽替换旧授权。原资源退休不建立额外Binding黑名单或替代Ready状态。接口见[[Combatants/结构|宿主边界]]和[[计划_角色与组件#14.7 Avatar 本地资源与发布边界|设计约束]]。

## Base原订阅与typed消费（已编码，未编译）

Base只负责组件接线和自己的原通知token，不与Health争夺实际原资源。cpp内`FHealthAbilitySystemSubscription`仅含原Base／Extension／Health三份弱身份、真实NoticeHandle与退休标记；lambda弱捕该记录，避免委托／资源环。Actor自己的关闭位仅控制订阅准入，不代表ASC／Health Ready。

| 实际入口 | 接线／关键实现与停止点 |
| --- | --- |
| `PostInitializeComponents` → `RegisterHealthAbilitySystemSubscription` | Super后确认原组件实际注册；先将完整原记录装槽，再RegisterLocalAbilitySystemNoticeAndCall。同步回放可以在token返回前退休，AcceptReturnedHandle将晚返回token精确归还原Extension；不读后继订阅。 |
| `ConsumeLocalAbilitySystemNotice` | 入口复制原订阅与整Notice。Ready→Health Initialize，Refreshed→Refresh；Released仅通知原H→Uninitialize，不查Ready／当前H。三个native接口见下一节。 |
| `EndPlay`／`BeginDestroy` → `UnregisterHealthAbilitySystemSubscription` | 先关闭新准入、摘自身原槽并退休，再精确Unregister原token、再Super；Health五token仍由Health自身生命周期清理，不等Released。 |
| 真实后续`BeginPlay` | Super及组件BeginPlay完成后，Actor确实进入新生命周期才重开原订阅；首次已注册不重复。失败明确诊断，无按帧重试或替代资源。 |

普通回放／Ready／Released允许同步完整接续，不加Busy、队列或调度。Health调用后只诊断本次结果，旧消费尾部不回滚或清后继；注册尾部仅退休匹配原订阅。Base自身关闭准入、退原通知token，Health自行归还五token。Base沿死亡事件关闭移动／碰撞并安排下一帧退场，常改的演出由既有蓝图事件消费，不增加第二死亡状态。

## Health原资源与五委托（已编码，未编译）

源码：`Character/Components/GGYGOHealthComponent.h/.cpp`。Health负责唯一死亡阶段、原生属性事件到蓝图的转换及只读值；HealthSet唯一负责数值。Base消费Extension的Ready／Refreshed／Released typed Notice，分别调用Health原资源入口；Base只持通知订阅，不复制Health的H／ASC／Set／Context或Ready。

| 实际接口／调用方 | 输入与作用 | 输出／清理边界 |
| --- | --- | --- |
| 旧BP／Base Ready → `InitializeWithLocalAbilitySystemResource(Extension,H,PublishedContext,OutError)` | 明确原Extension、原H、ASC认证当前发布Context；检查本Pawn／真实Ready／实际HealthSet | 安装唯一原记录和五个真实token，再投影既有DeathState与三次UI初值；bool只说明本次完成历史，不授Ready权限。 |
| Base Refreshed → `RefreshLocalAbilitySystemResource(Extension,H,PublishedContext,OutError)` | 同H、相同原对象与Set；认证新发布Context | 更新同记录Context，不重绑委托、不重播三次初值；每次事件取当前认证Context。 |
| 旧BP／Base Released → `UninitializeFromLocalAbilitySystemResource(H,OutError)` | 仅匹配Health自持原记录的H；不要求Ready | 先退休并摘原槽，再按五token移除原Set委托；旧H不匹配后继时明确拒绝，空槽幂等。 |
| 旧BP → `InitializeWithAbilitySystem(InASC)` / `UninitializeFromAbilitySystem()` | 旧反射签名保持，Init仅捕自身Extension真实H并验证InASC；Uninit捕自身原记录 | 共用上述实际机制，无H／不Ready／ASC不符明确诊断，不构造仅凭ASC的兼容绑定。Base／Hero生产消费者使用typed通知；旧BP调用方同样遵守原H合同，不能以无身份Uninit清后继。 |
| 自身 → `EndPlay` / `OnUnregister` | 先关闭本组件新装配准入，直接捕原记录 | 五token独立归还，不等Extension Released；实际注册／新BeginPlay再重开自身准入。 |

cpp内`FAbilitySystemResource`唯一保存原Health／Pawn／Extension弱身份、H、ASC／HealthSet弱引用、认证PublishedContext、五个token及退休标记。五个lambda仅捕原记录；每次事件入口复制该记录当时的认证Context，而不是永久使用安装Context。处理器、读值、Tag投影、GameplayEvent和自毁GE均消费原记录，不重读当前槽收养后继。

重要实现：`RetireOriginalResource`先标退休、仅摘指针相同的自身槽，复制并清空token后向原Set精确Remove；Set失效只退休原义务，不寻找替代Set。安装与UI／Tag／GE外调后复核原记录、H、Set和Context，失效即停止；同H重建另一记录或同步刷新有效Context时，旧安装失败收尾不清合法后继。同H刷新后的lambda读取新Context，所以无需重新注册事件。

DeathState仍按NotDead→DeathStarted→DeathFinished单调推进；解绑不清死亡Tag，不实现隐式复活。自毁仍走原GE／HealthSet结算，缺必需依赖明确失败；Health不签Binding／Ready，不成为ActorInfo或伤害执行器。常改的GE覆盖、死亡演出与UI表现由现有配置／蓝图事件消费。

StartDeath／FinishDeath依据唯一DeathState单调推进，只在阶段实际改变时广播相应死亡事件；对真实原Ready资源单调投影Dying／Dead。未绑定时仍推进死亡阶段，后续合法装配只补Tag，不重放死亡事件。原H解绑不清持久ASC上的死亡Tag，不隐式复活。Health认证本Pawn、原Extension／H／Context与实际HealthSet；真实OtherAvatar原H、缺H或未Ready均明确拒绝，不能当作正常绑定。动态覆盖及剩余边界见[[计划_角色与组件#14.9 Health唯一原资源与Base消费接力|计划记录]]。

## Pyrios 渲染组件

通用机制已移入 `UGGYGOCharacterRenderComponent`。Hero 构造的 `StylizedRenderComponent` 仍保持旧子类身份，以便现有 Blueprint 迁移。只有显式 `MaterialSlots` 和 `OutlineMaterial` 生效；C++ 不再按 Pyrois 名称或资产路径自动配置。

`RefreshMaterials()` 在组件激活且 BeginPlay 后按槽名安装 MID，并记录原 nullable override。换装先 `ReleaseMaterials()`，换 Mesh/配置后刷新；Tick 检测 Mesh/槽位变化时释放并等待显式刷新。释放仅恢复仍由自身持有的 MID；原 Mesh/槽已变时清除自身遗留覆盖，第三方覆盖保持不动。

`UpdateLighting()` 使用显式灯或独立弱缓存的有效 DirectionalLight，向 MID 写方向、颜色、受限强度及角色级射线遮挡。显式灯关闭不回退其他灯；无有效灯时直接光为零。描边按显式材质和开关创建 Leader Pose 壳。组件不参与 ASC InitState，不写 CMC/ASC。详见 [[渲染实现]]。

Pyrois 骨骼模型的 Body 1、Body 2、Weapon 默认槽位已直接绑定三个 Toon MI；`BP_PC_Pyrios` 没有 Mesh 材质覆盖，因此编辑器打开模型或角色蓝图时就能预览表面材质。`BeginPlay` 再为运行时主光参数创建 MID，并创建描边壳；静态编辑器视口使用 MI 中的基准光强，不生成描边壳。
