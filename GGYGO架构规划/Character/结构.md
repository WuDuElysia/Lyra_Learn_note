## 角色胶囊落脚规则

所有项目角色互相阻挡，但不能踩在其它角色上。`AGGYGOCharacterBase` 构造时通过原生 `SetWalkableSlopeOverride(WalkableSlope_Unwalkable)` 设置共享胶囊；仅 `CanCharacterStepUpOn=No` 不能拒绝从上方落地。玩家、Boss 及共享 Blueprint 继承该配置，碰撞仍为 Pawn；不由具体 GA 过滤 Landed 来伪装规则。

同轴自由下落的零滑动由 [[Movement/结构#角色胶囊滑离|CMC 碰撞入口]] 处理，实际基底与落地仍归 CMC。`GGYGO.Character.Collision.NoCharacterPerch` 覆盖 Hero／Boss 四种上下组合的中心／偏心下落、水平阻挡和环境基底；单机 P3 贴身 AirChain01 已在环境落地并稳定 Walking。联机预测和 Cook 未验证。

## InitState 注册与 PawnData 分发（Gate80 有限验收）

启动配置链由[[System/结构|System]]提供同GI的原生注册前置，Character使用原feature状态机与PawnData分发入口。全局顺序和每个Actor feature的状态唯一归`UGameFrameworkComponentManager`；Extension持有PawnData，CMC接收并校验MovementSet，Hero管理自己的玩家输入装配。配置分发、Host绑定与Health资源订阅各有独立生命周期。

| 入口／调用方 | 输入与实际调用 | 产物及边界 |
| --- | --- | --- |
| 原生 GI → `UGGYGOInitStateRegistrationSubsystem::Initialize` | `UGameInstance::Init` 的 `SubsystemCollection.Initialize(this)` 创建子系统；`InitializeDependency<UGameFrameworkComponentManager>()` 取得同一原 GI 的 Manager，按 Spawned→DataAvailable→DataInitialized→GameplayReady 锚点调用 `RegisterInitState` | 三组相邻正向 true、逆向 false 全通过后才输出 `RegisteredOrder`；已有逆序或无效依赖明确诊断，不重排、不补第二顺序表／Ready／轮询。 |
| Extension → `CheckDefaultInitialization` | PawnData／Controller／其他 feature 的原生通知触发；先 `CheckDefaultInitializationForImplementers`，再 `ContinueInitStateChain` | DataAvailable 要求实际 PawnData；Authority／本地控制端还须 Controller。本地 StateChain 和 feature 注册均不建立全局顺序。 |
| Extension → `CanChangeInitState` | DataAvailable→DataInitialized 查询 `HaveAllFeaturesReachedInitState(Pawn, DataAvailable)` | 所有 feature **已达到或超过** DataAvailable 才分发；各 feature 独立推进，可以处于不同阶段。没有独立的 MovementSet 异步加载等待。 |
| Extension → `HandleChangeInitState` | 进入 DataInitialized 时唯一调用 `ApplyPawnDataToConsumers`，向原 CMC 执行 `SetMovementSet(PawnData->MovementSet)` | CMC 保持配置接收与校验职责；Cue 预热在 setter 之后。Host 绑定、ASC Ready 与 Base／Health typed 订阅各走自己的生命周期，不能作为这次配置分发的串行门禁。 |
| Hero → `CanChangeInitState`／原生输入入口 | Hero 的 DataInitialized 只要求 Extension ≥ DataAvailable；`BeginPlay` 和 `CharacterBase::SetupPlayerInputComponent` 沿既有入口调用 `InitializePlayerInput` | Hero 可以先到 GameplayReady；Setup 可独立建立输入会话。Hero 的 `HandleChangeInitState` 返回后引擎仍提交状态，缺 InputComponent／相机检查提前返回不构成状态守卫。 |

`UGameInstance::ReceiveInit` 先于子系统初始化，不能在该早期事件假定注册已完成；刻意不调用 `Super::Init` 的 Input TestGI 也不具有本前置。每个原 GI 在原生子系统初始化中登记一次；System 新类没有 Manager 缓存、订阅、Tick 或额外资源清理，Actor feature 的注册与注销仍由各组件生命周期负责。

Hero沿原Source创建Session，由CMC创建原Binding，自己持原OwnerSync Observer；真实Started记录或原OwnerSync Ready返回后，查询原Source仍Held才调用`TryAdmitInitialMovementInputRequest`。请求与执行状态归Input／CMC，Hero不补Press或持第二held。原通知／Session／Binding按来源精确清理，接口见[[Movement/结构|Movement]]、[[Input/结构|Input]]。

原Manager的全局顺序必须先于feature推进建立；空顺序表只能判断相同标签，不能把较晚阶段识别为“已达到DataAvailable”。因此System在同GI原生初始化中登记并核对正逆关系；本地StateChain不承担全局顺序。`HasReachedInitState`的同标签相等查询本身不证明顺序有效。

启动配置只分发PawnData与MovementSet，不签ASC Binding或Ready；Health入口仍须明确原Extension／H／认证PublishedContext。实际启动、资源与死亡合同的有限验证分别见[[计划_角色与组件#14.9 Health唯一原资源与Base消费接力|计划记录与验证边界]]。

### 原 PawnData 同步初始化调用

`IsPawnDataInitializationInProgress() const` 是游戏线程上的无参数只读查询，返回原 Extension 的同步初始化调用是否仍在栈上。它核对实际登记、原 Extension／Pawn／World 弱身份及生命周期；没有有效 scope、离开游戏线程、注销、EndPlay 或原身份失效时返回 false。调用方只读这个公开事实，不读取 Extension 私有字段。

| 原入口／接口 | 输入与作用 | 输出／清理责任 |
| --- | --- | --- |
| `CheckDefaultInitialization()` | 原 PawnData／Controller／PlayerState／输入建立／feature 通知进入；栈上 `FPawnDataInitializationScope` 覆盖 `CheckDefaultInitializationForImplementers → ContinueInitStateChain` | 先推进其他 feature 的同步回调也处于本次原 scope；不改变 InitState 顺序或新增调度。 |
| `ApplyPawnDataToConsumers()` | 原 DataInitialized 分发入口建立同类嵌套 scope，再调用原 CMC `SetMovementSet(PawnData->MovementSet)`、发起 Cue 预热 | scope 描述实际同步分发，不等待异步资产、不证明 setter 接受或 Cue 已加载完成。 |
| `FPawnDataInitializationScope`／组件生命周期 | 栈记录保留原弱身份和父 scope；Extension 仅借用当前栈记录指针 | 正常退出仅在当前指针仍等于自己时恢复原父 scope，最外层退出即关闭；`OnUnregister` 清指针，`EndPlay` 先关闭准入并清指针。旧析构不恢复失效父 scope、不覆盖后继；真实后续 BeginPlay 只重开准入，仍须新调用建立 scope。 |
| CMC → `GetLocomotionSteeringSnapshot() const` | 缺 accepted Set 时，先核原 CMC／Character／UpdatedComponent 与 Extension 身份及生命周期、Set 从未提交、累计 native interval 为 0、Extension 未越过 DataInitialized | 原 Actor 构造注册／BeginPlay 完成前允许合法 Initial，覆盖动画早于 Extension 登记的入口；Actor 完成 BeginPlay 后必须查询到上述原同步 scope。无在途却缺 Set、已提交 null／拒绝、已有 native interval 或生命周期关闭均明确 Invalid。 |

Extension／Hero 的 Spawned、DataAvailable、DataInitialized 或 GameplayReady 标签均不证明配置接受；停在早期标签也不能维持长期 Initial。scope 只解释合法同步接线时尚未分发的展示暂态，不发行 ASC Ready 或移动执行资格；accepted MovementSet 的唯一准入仍归 CMC，正常配置与真实源校验沿原链执行。没有新 timer、长期 Ready 状态、第二执行器或按帧静默重试。机制理由及有限验收见[[计划_角色与组件#同步初始化 scope 与冷启动边界|计划记录]]。

## 死亡结束后的 Pawn 处理

`HealthComponent::OnDeathFinished` 保持死亡事实广播；`CharacterBase` 用原生 `SetTimerForNextTick` 在下一帧调用 `K2_HandleDeathFinished()`。[[Teams/结构|Teams]] 的死亡自动替补仍在原广播内同步完成，先于 Pawn 清理。

`K2_HandleDeathFinished()` 由共享角色蓝图实现，返回 true 表示已处理，允许明确保留 Pawn。未覆盖或返回 false 会报出 Pawn 路径，不执行默认销毁。蓝图可选择调用受保护的 `UninitAndDestroy()`：各端释放本 Pawn 仍拥有的 ASC 关联并隐藏，只有服务器解除控制并设置原有 0.1 秒 LifeSpan；不清理已转给后继 Avatar 的资源。

`/Game/BP/Character/BP_Character`、`BP_HeroCharacter`、`BP_BossCharacter` 分别承接原生 Base、Hero、Boss 分支。三份模板的死亡图显式调用清理后返回 true；`BP_Enemy`／旧 `BP_BaseCharacter`、`BP_PC_Pyrios`、`BP_Boss_Test` 分别继承对应模板。后续对象继承模板或覆盖此图，不在 C++ 固定去留。

已编译；死亡处理两项专项和 SquadSwitch 八项通过，其中联机用例使用真实 D3D12、同进程 listen-server／client PIE。专项覆盖广播顺序、显式保留、未配置诊断、客户端权限和 Pyrios 生产蓝图入口。未覆盖独立进程、Cook 和保留后的复活玩法。需求及日志见 [死亡处理结论](F:/ue_project/GGYGO/AAADocs/需求文档/refactor_and_squad_switch.md)。

## 宿主释放端口

`IGGYGOAvatarBindingHostInterface::ReleaseAvatarBinding(ExpectedAvatar)` 是 Character 与共同宿主之间唯一的端口：只在 ExpectedAvatar 仍是宿主当前 Avatar 时释放，已被替换的旧 Pawn 不处理。PawnExtension 在死亡销毁前经它请求释放。取得 ASC 走 `IAbilitySystemInterface`。绑定流程本身见 [[Combatants/结构#绑定与释放顺序|Combatants]]。

## PawnExtension 本地 ASC 订阅

| 接口 | 输入 → 作用 → 输出 |
| --- | --- |
| `HandleAbilitySystemBound(ASC)` | 宿主绑定完成后调用 → 记录当前资源并广播 Ready；已有同一 ASC 不重复广播，已有其它 ASC 时拒绝并诊断（跨宿主须先释放）→ bool。 |
| `HandleAbilitySystemReleased()` | 宿主释放流程中调用 → 先清空当前资源再广播 Released；没有资源时无操作。 |
| `GetCurrentLocalAbilitySystemResource()` / `IsLocalAbilitySystemResourceReady(Handle)` | → 当前资源句柄 / 该句柄是否仍是当前 Ready 资源。换人请求、FX 来源等用它识别"这一次绑定"。 |
| `FGGYGOLocalASCSubscription::Subscribe(Extension, Callback)` / `Unsubscribe()` | 订阅即回放当前 Ready；重复 Ready 不回调；Released 只发给已消费同一资源的订阅；分发前复制订阅表，Ready 分发中资源被替换则停止。`GetReadyASC()` 给出已消费且仍就绪的 ASC。 |
| `HandleControllerChanged()` | Controller 变化 → `RefreshAbilityActorInfo`，再推进 InitState；不经过宿主。 |

Hero、CMC、Health、LocomotionFX 各自持有一个订阅；CharacterBase 不再转发绑定通知。CMC 只在 BeginPlay 订阅。

## 首击渲染资源前置

玩家第一次进游戏时，普攻特效的材质和 Niagara 可能还没准备好。资源由共享 Pawn 蓝图选择，PawnExtension 只持有请求，Hero 在首次按下时读结果。

| 接口 | 输入 → 作用 → 输出 |
| --- | --- |
| `SetAbilityInputResourcePreparation(Preparation)`（BlueprintCallable） | 共享 Pawn 蓝图（`BP_PC_Pyrios`）创建的 Rendering `UGGYGONiagaraMaterialPreparation`，Owner／Outer 必须是本 Extension → 由本组件持有到 EndPlay 再取消；同 Pawn 再附身不重建；已有不同请求时拒绝并取消传入的请求 → true 表示已持有，蓝图随后 Start。失败时蓝图不得 Start。 |
| `AreAbilityInputResourcesReady(InputTag, OutReason) const` | 当前 Action 的输入 Tag → Tag 不在 PawnData `InputTagsRequiringRenderResources` 里，或本 Pawn 的请求已 Ready 时返回 true；否则返回 false 并给出请求状态和原因。不改 ASC 绑定或 InitState，不复制 Ready。 |
| Hero `Input_AbilityActionTriggered` | 首次按下先锁存原 Action 观察，再查上面的结果 → 未 Ready 时打一条 Warning（`RenderResourcesNotReady`）并作废这次请求；同一次按住不补发，Ready 后也不重放旧按下，玩家要重新按。 |

`UGGYGOFXNiagaraComponent` 在安装最终材质之后、原生 `Activate` 之前，为本组件再创建一个材质准备请求并等待完成，取消或退役时撤销请求；`UGGYGOAbilityTask_PlayNiagaraEffect` 只表示已请求激活，不表示画面已出现。验证记录见项目 `AAADocs/需求文档/normal01_first_strike.md`。

## Health 订阅与五委托

HealthComponent 自己订阅 PawnExtension（游戏世界中 OnRegister 与 BeginPlay 各尝试一次）。Ready 时绑定 HealthSet 的 Health／MaxHealth／Poise 变化、OutOfHealth、PoiseBroken 五个委托并保存 token，Released 或资源被替换时只移除自己的 token。OutOfHealth 在服务器上要求 Spec，向 ASC 发 `Event.Death`；HealthComponent 再经自身动态委托把变化交给 UI／蓝图。DeathState 本地唯一，Dying／Dead 单调投影。

## Pyrios 渲染组件

通用机制已移入 `UGGYGOCharacterRenderComponent`。Hero 构造的 `StylizedRenderComponent` 仍保持旧子类身份，以便现有 Blueprint 迁移。只有显式 `MaterialSlots` 和 `OutlineMaterial` 生效；C++ 不再按 Pyrois 名称或资产路径自动配置。

`RefreshMaterials()` 在组件激活且 BeginPlay 后按槽名安装 MID，并记录原 nullable override。换装先 `ReleaseMaterials()`，换 Mesh/配置后刷新；Tick 检测 Mesh/槽位变化时释放并等待显式刷新。释放仅恢复仍由自身持有的 MID；原 Mesh/槽已变时清除自身遗留覆盖，第三方覆盖保持不动。

`UpdateLighting()` 使用显式灯或独立弱缓存的有效 DirectionalLight，向 MID 写方向、颜色、受限强度及角色级射线遮挡。显式灯关闭不回退其他灯；无有效灯时直接光为零。描边按显式材质和开关创建 Leader Pose 壳。组件不参与 ASC InitState，不写 CMC/ASC。详见 [[渲染实现]]。

渲染接口与实现边界统一见 [渲染契约](file:///F:/ue_project/GGYGO/AAADocs/Modules/Character/Rendering/Pyrios_Renderer_Implementation.md)。2026-09-29 的测试、资产保存／冷读与 PIE 接线记录见 [历史验收](file:///F:/ue_project/GGYGO/AAADocs/Modules/Character/Rendering/Pyrios_Renderer_Obsidian_History_20261013.md)；旧版记录不代表当前视觉验收。

地面上的角色阴影来自场景主灯的 VSM，不经角色 Capture。Pyrios Mesh 的包围盒由物理资产算出，只覆盖躯干；武器、斗篷、小腿在动画中远超出去，VSM 按图元包围盒决定缓存页失效，超出部分的旧姿态阴影会残留成地面条纹。因此 `BP_PC_Pyrios` 的 Mesh `BoundsScale` 为 11（逐帧跟踪整段倒下 Montage 所需最大 9.458）。`FGGYGOCharacterShadowCapture` 的对象阴影宽度为 `2 × (SphereRadius / BoundsScale + ObjectMarginCm)`，扩大包围盒不稀释对象阴影图分辨率；`BoundsScale <= 0` 时宽度为 0，被原有校验拒绝。新增动作若让武器或斗篷伸得更远，要重新跟踪倍率。

Pyrois 骨骼模型的 Body 1、Body 2、Weapon 默认槽位已直接绑定三个 Toon MI；`BP_PC_Pyrios` 没有 Mesh 材质覆盖，因此编辑器打开模型或角色蓝图时就能预览表面材质。`BeginPlay` 再为运行时主光参数创建 MID，并创建描边壳。材质球与 BP 的 `EditorPreview` 使用 MI 基准光值；源码已有可选 `bPreviewSceneLighting`（默认关闭），仅关卡 `Editor` 世界通过 CPD 预览场景主光，该路径尚未视觉验收。
