## 10. 移动层重建（D3）

> 本章只讲 **locomotion**（走跑转身）这一层。攻击、闪避、突进这类**动作位移**的驱动方式
> 单独在[第 13 章](#13-动作位移驱动)展开，两者最终都落到 CMC，但决策点完全不同。

### 10.1 为什么移动逻辑必须写在 CMC 内部

在 CMC **外面**驱动移动（每帧覆写 `MaxWalkSpeed`、调 `RequestDirectMove`、
直接改 Actor 朝向）在单机下能跑，联机下必然出错：那些写入发生在
`SavedMove` / `NetworkPrediction` 体系之外，服务器重演客户端的 move 时拿不到它们。

三个后果：

1. **没有移动复制。** `ReplicateMoveToServer` / `ClientAdjustPosition` 被绕过，两端各算各的。
2. **没有客户端预测与纠正。** 高延迟下角色会橡皮筋。
3. **服务器无法验证。** 位置不经校验，作弊客户端可以任意改。

所以速度与状态一律走 CMC 的正规扩展点，见 10.2。

### 10.2 结构与扩展点

```
Character/
  Components/
    GGYGOCharacterMovementComponent.h/.cpp   UCharacterMovementComponent 派生
    GGYGOCurveRootMotionSource.h/.cpp        Stop / TurnBack 曲线速度执行器
  Data/
    GGYGOMovementSet.h/.cpp                  移动参数 DataAsset
    GGYGOLocomotionMotionProfile.h/.cpp      独立曲线数据与纯区间求值
    GGYGOMovementTypes.h                     Gait / Motion / Stop / TurnBack 语义
```

CMC 的主要语义／速度扩展点如下；曲线源还通过原生 Prepare 请求 CMC 实际区间，胶囊物理继续交给引擎：

| 扩展点 | 承担 | 为什么是这里 |
|---|---|---|
| `GetMaxSpeed()` | 速度上限 | CMC 自己在 `CalcVelocity` 里调它，加减速、摩擦、坡度、碰撞全部沿用引擎实现 |
| `UpdateCharacterStateBeforeMovement()` | 普通段解算提交；RMS 段暂存原候选／挂源；回放消费原 Prepared | 在移动计算前准备原 move，不预支整帧 RMS 区间 |
| `PhysicsRotation()` | 转身第一段由曲线驱动朝向 | 绕过 `Super` 就等于这一帧只有曲线在转角色，不必临时关掉自动朝向再恢复 |
| `PrepareLocomotionCurveRootMotion(Source,SimulationTime,MovementTickTime,OutPrepared,OutError)` | 原生 RMS 回调原 CMC；核对 Origin／原 group 后按真实区间求值，输出结果及失败原因 | actual Source 时间和 SimulationTime 决定 RMS 区间，CMC 唯一持有语义／时间并提交；不是另一套 Tick |

移动被禁止时 `GetMaxSpeed()` 返回 0，而不是调 `StopMovementImmediately()`。
返回 0 走的还是 CMC 自己的制动减速度，会平滑压到零；瞬间定住在联机下会与服务器重演结果不一致。

预测数据：步态、走跑计时器、Locomotion 段／时间、WalkRun 相位与转身相位进入 `FSavedMove_GGYGO` 的 `SetMoveFor`／`PrepMoveFor` 并限制合并。曲线 RMS 另在 `PostUpdate` 保存原 move 的 Input／Prepared，`PrepMoveFor` 在 native Super 前安装原回放上下文，Before 只消费原结果一次；结果不是第二准入／FAILED／时钟。MoveData 仍仅发动作段、停止语义、转身相位和序列号提示，Response 沿权威时间基线重放契约；新本地 Origin 不在线上传输，完整 authority／proxy 匹配与校正接续未关闭，不能据这些本地记录声称网络通过。

当前 Walk/Run 不是两个 AnimBP 状态。角色有移动输入时从 Walk 起步，连续保持到
`UGGYGOMovementSet::WalkToRunHoldSeconds`（默认 1.5 秒）后升为 Run，并保持到松开移动；
松手、离地、`Restriction.CantMove`、重装 MovementSet 或按住 ForceWalk 都会清零计时。
`ABP_Pyrios` 在同一个 `WalkRun` BlendSpace1D 内表现这个结果。CMC 独占推进
`WalkRunBlendAlpha`（0=Walk，1=Run），AnimationStateFrame 将其只读发布；当前 ABP 通过
旧序列化字段 `StateMemory.GaitBlendY` 兼容接到 BlendSpace Player 的 X 轴。
`IA_ForceWalk` 只覆盖本次普通移动为 Walk；Sprint 仍由能力语义处理，不增加第三个 locomotion 步态。

用户要求 Gadge 先占位，既有 `GA_Dodge`／Gadget 占位保持；CMC 的 `RequestRunOnNextMove()` 尚无调用方，后续统一做 GAS 时再接入动作结束语义。动画侧 `EnterMove` 和 `Stop` 的 Sequence Player 不循环，避免剩余动画比例过渡错过末尾。公开语义／轴规范名为 `WalkRunBlendAlpha`，旧序列化字段仍为 `GaitBlendY`；已有 UE 回读的生产轴显示仍为旧名，尚未保存修正。Movement 组长只读磁盘 ABP 图／引脚与旧 Git 确认 WalkRun X 接该旧字段、Entry 进入 WalkRun、TurnBack／Stop 保留；不是统筹图验收、新资产保存或当前 Run 证明。

### 10.3 Locomotion 曲线如何接进 CMC

ZZZ 的位移信息存在动画的自定义曲线里（`RootMotion_Speed` / `PosX` / `PosY` / `Dist` /
`Yaw` / `DirX` / `DirY`，另有 `Cfg_*` 常量曲线携带 clip 长度与循环设置），
不是 UE 原生 RootMotion。三种接法：

| 接法 | 机制 | 运行时可干预 | 复杂度 |
|---|---|---|---|
| **a. 离线烘成原生 RootMotion** | 曲线烘进 AnimSequence 的 RootMotion 轨道，CMC 通过 `RootMotionMode` 消费 | 只能整体缩放 | 低（但要处理每个资产） |
| **b. 运行时构造 RootMotionSource** | 采样曲线，输出 `FRootMotionSource_*` 交 `ApplyRootMotionSource()` | 高 | 高（要实现 `NetSerialize` / `Matches` / `PrepareRootMotion`） |
| **c. 采样成速度上限** | 采样曲线，值经 `GetMaxSpeed()` 交给 `CalcVelocity` | 高 | 低 |

当前实现采用独立 `UGGYGOLocomotionMotionProfile`：离线迁移实际动画中的
`RootMotion_Speed / DirX / DirY / Yaw`，由 CMC 用 `EvaluateInterval` 纯求值。
Profile 不持有播放状态；动作段、模拟时间和共享 WalkRun 周期全部由 CMC 持有。

- WalkStart、WalkLoop、RunLoop、StartStop、WalkStop、RunStop、TurnBack 各有明确 Profile 引用；
- WalkRun 仍是一张 BlendSpace1D，CMC 用同一归一化周期分别采 Walk/Run Profile，再按
  `WalkRunBlendAlpha` 混合速度与方向；
- Stop／TurnBack 通过现有 `FRootMotionSource_GGYGOCurve` 请求原 CMC 实际区间结果后执行，普通 WalkRun 仍走 CMC 原生物理；
- 仅显式 `bUseCurveDrivenSpeed=false` 是正常固定速度模式；曲线模式缺失／失败明确拒绝，不回头读AnimInstance或回落固定速度；
- `FGGYGOAnimCurveSampler` 仅保留给历史工具/调查，不再位于 Locomotion 运行链。

本批未写生产 `.uasset`。七份 Profile 的创建、`DA_Movement_Default` 引用和 AnimBP 回读仍需
独占UE资产窗口；曲线模式缺失引用会拒绝，不能为了运行替换固定速度。C37与C38严格Mode／Proof消费已编译，Gate48旧Rearm及新合成Cold／Rearm专项通过；Source发行D12-B Gate49R1已编译，私有原生Source／公开首W已Gate54验，正式Source未验，Hero未接，当前Run未验。Cold仅显式首按一次窗，失败／重绑恢复仍真释放再按，完整契约见[[Movement/结构#显式Cold／Rearm消费（C38）|消费边界]]。

#### 10.3.1 本地 CurveRMS：原资源、实际区间与回放

这是当前**已编码、有限静态接受但未编译**的实现，详细接口输入／产物／清理见 [[Movement/结构#本地 CurveRMS 原资源与实际区间|结构契约]]；流程见 [[GGYGO_流程_移动与位移.canvas|主流程]]。Profile 仍是纯求值数据，RMS 不新增求值器或语义时钟。

1. Before → `TryUpdateLocomotion`：普通 WalkStart／WalkRun 等段纯求值后 Commit；Stop／TurnBack → `StageLocomotionCurveRootMotion(MovementTickTime,Candidate,OutError)`，保存原 move 输入并挂源，不提前推进整帧 RMS 时间。
2. CMC 签发同一共享 Origin：弱原 CMC／原 Set、Binding、真实 InputRequest、执行序号、片段／序列、SourceTimeOrigin／MotionTimeOrigin、入口 yaw／Scale。Clone 保留该引用；名称／LocalID 不认证来源，活引用也须重验原关系。
3. 引擎 → RMS `PrepareRootMotion` → 原 CMC `PrepareLocomotionCurveRootMotion`：`t0 = MotionTimeOrigin + (Source.GetTime() - SourceTimeOrigin)`，`t1 = t0 + SimulationTime`；核对原 Input、tick、group、配置和标量，再 `EvaluateSingleInterval`。合法零 SimulationTime 保留，partial／catchup 不钳为整帧预算。
4. Speed／Direction 保留 t1 端点采样，Yaw 保留累计角／区间差，TurnBack 按实际 SimulationTime 推进。OverrideVelocity 是入口 yaw 旋转后的缩放终点速度，再乘 `SimulationTime / MovementTickTime`；**不声称精确平移积分**。CMC `ConsumeLocomotionCurvePrepared` 去重一次提交完整候选；RMS 仅安装原结果速度、原生时间与退场标志。
5. `HasUsableSpeed` 只用于正常 Brake／RMS 幅值判断，成功来源资格另由原样本／配置／请求判断。合法低速结束、离地保留当前动量；非法依赖／求值不当作自然完成。Completed Origin 阻止同一片段重新挂同一物理源；独立 Action／动画 Root Motion 优先级和原生碰撞执行保持。
6. SavedMove `PostUpdate` 保留原 Input／Prepared 并禁止有关 move 合并；`PrepMoveFor` 先安装原回放上下文，再 native Super，Before 消费原准备结果一次。无原准备区间不制造整帧模拟。Prepared 只是原 move 派生结果，不恢复请求准入、FAILED 或后继资源；普通非 RMS 和权威时间基线沿原契约。

`ReportLocomotionCurveRootMotionFailure(Origin,Reason)` 只失败原当前请求；旧来源退自己的贡献，不清后继或独立 Action。Reset／EndPlay／回放结束和 SavedMove Clear 清各自引用；原生 Prepare 遍历内不结构性移除数组。NetSerialize wire 仍为原基类及 BaseYaw／SpeedScale／bEndOnZeroSpeed，加载清本地 Origin／Prepared／诊断节流；导入来源未认证，authority／proxy／校正接续继续开放。

以下严格场景与旧失败断言继续留账，不删场景、不降断言：partial／zero／catchup 与端点／Yaw语义、同帧失败／SavedMove后继隔离、低速／离地动量、原生碰撞与独立根运动交互、正式七Profile保存／接线、实际Run／物理Hero及网络。当前无这些新运行结果。依用户2026-10-03最新要求，本轮实施门禁只做整链统一编译＋必要UE冒烟，不扩严格专项矩阵，不把未运行专项／完整网络验收作为继续实施的审批停点，也不冒称其通过。Gate54的82无警告成功、2带警告成功、1Fail及FAILED两生产Error／请求3标记保持历史，不套用到新四源。统筹证据为 `Saved/ValidationRecords/MovementActualInterval_20261003_RootAcceptance.json`，项目记录另见 `MovementActualIntervalRecords_20261003_RootAcceptance.json`；本N1只同步图文。

### 10.4 locomotion 状态的新归属

A 身份订阅底层已 Gate53 编译；E1 当时改接 Cache 一次 Prepare、Tag 原 const Ready Getter、EndPlay 先 Release，沿用 A 接口和唯一派生缓存，三文件冻结／统筹静态接受。当时三方法／三注释与其它业务保护不是后继整个 CMC 的永久修改范围；本地 RMS 已另改原 move／Before／清理等路径。E1 与新四源均无新编译／动态；Host／Extension 真实发布及其它消费者须共同进入同一新 DLL／新 World 门禁。接口见 [[Movement/结构#本地ASC身份订阅准备（A：已编译、未接生产）|A 底层与 E1 阶段]]。

locomotion 不需要独立的状态机 —— 它的每一项状态都能从 CMC 或 ASC 直接推导：

| 状态 | 权威来源 |
|---|---|
| 是否在移动 | `CMC->IsMovingHorizontally()`（阈值 10 cm/s，过滤碰撞挤压的残余速度） |
| 是否有移动意图 | `CMC->HasMoveInput()`（读 `Acceleration`，因为它已被 SavedMove 保存） |
| 是否在地面 | `CMC->IsMovingOnGround()` |
| 当前速度 | `CMC->GetHorizontalSpeed()` |
| 步态 | `CMC->GetResolvedGait()` |
| 动作状态（攻击中、受击中） | ASC 的 `State.*` GameplayTag |
| 能否移动 | CMC 直接查 ASC 的 `Restriction.CantMove` |

**为什么不要 Idle/Moving 状态机**：那两个状态本身就是"有无移动输入"的投影 ——
Idle 见到方向就转 Moving，Moving 见到方向归零就转回。多一层间接只是多一处
可能与真实输入不同步的地方。

**不再需要单独的状态机对象。** locomotion 状态是 CMC 数据的派生视图，动作状态是 GAS Tag。

## 13. 动作位移驱动

配套子图：[[GGYGO_流程_移动与位移.canvas]]

本章回答三个问题：攻击动作的位移**用什么机制驱动**、**终点解算写在哪里**、
**动画做成 in-place 还是带 RootMotion**。

### 13.1 先澄清一组容易混的概念

问题里"用 in-place 还是蒙太奇"其实把两个不相干的维度并列了，它们是正交的：

| 维度 | 选项 | 说明 |
|---|---|---|
| **播放方式** | Montage / 直接播 Sequence / AnimBP 状态机 | 动画**怎么播** |
| **位移来源** | 动画自带 RootMotion / 程序驱动位移 | 位移**谁算的** |

一个 Montage 可以带 RootMotion 也可以不带；一个 in-place 动画既能用 Montage 播也能用状态机播。

**播放方式对动作游戏没有选择余地：必须用 Montage。** 原因不是习惯，是功能：
- AnimNotify / NotifyState 打判定窗口、可取消点、连段窗口 —— 只有 Montage 有稳定的时间轴可挂
- Montage Slot 支持上下半身分层，让攻击动作能与 locomotion 混合
- `MontageBlendOut`、`Montage_Stop` 提供被打断时的可控退出
- GAS 的 `PlayMontageAndWait` 与预测/复制链路是配套的

所以真正要选的只有**位移来源**，下面展开。

### 13.2 位移来源的四种做法与取舍

| 做法 | 机制 | 位移可控性 | 脚滑风险 | 联机 | 适用 |
|---|---|---|---|---|---|
| **A. 纯 RootMotion** | 位移烘进动画，`bEnableRootMotion=true`，CMC 通过 `RootMotionMode` 消费 | 无（写死在资产里） | 无 | 自带复制 | 位移固定的动作：起手、收招、翻滚 |
| **B. RootMotion + 缩放** | A 基础上用 `SetRootMotionTranslationScale` 整体缩放 | 只能等比缩放 | 低 | 自带复制 | 需要按角色体型或 Buff 微调幅度 |
| **C. In-place + RootMotionSource** | 动画不带位移，位移由 `FRootMotionSource_*` 程序生成，交 CMC 应用 | **完全可控，可指定终点** | 中（需对齐节奏） | 自带复制与预测 | **需要程序解算终点的动作：突进、位移技、追击** |
| **D. 直接改 Actor 位置** | `SetActorLocation` / `AddActorWorldOffset` | 完全可控 | 高 | **不可用** | 无（联机下不成立，见下） |

**结论：你要的"位移终点程序解算"对应做法 C。** 做法 A 作为不需要解算的动作的默认选择，两者共存。

D 之所以不可用，是它绕过了 CMC 的 `ReplicateMoveToServer` / `ClientAdjustPosition`，
服务器和客户端各算各的必然漂移，且服务器无法验证位置（作弊客户端可任意传送）。

### 13.3 做法 C 的具体实现：GAS 自带的 RootMotion AbilityTask

不需要自己写 RootMotionSource 的接线。UE 5.8 的 GameplayAbilities 插件已经提供了五个 AbilityTask，
位于 `Plugins/Runtime/GameplayAbilities/.../Abilities/Tasks/`：

| AbilityTask | 底层 RootMotionSource | 用途 |
|---|---|---|
| `AbilityTask_ApplyRootMotionMoveToForce` | `FRootMotionSource_MoveToForce` | **移动到一个固定坐标**，指定时长 |
| `AbilityTask_ApplyRootMotionMoveToActorForce` | `FRootMotionSource_MoveToDynamicForce` | **移动到一个 Actor**，目标会动也能跟上 |
| `AbilityTask_ApplyRootMotionConstantForce` | `FRootMotionSource_ConstantForce` | 恒定方向推力，用于击退、滑行 |
| `AbilityTask_ApplyRootMotionRadialForce` | `FRootMotionSource_RadialForce` | 以某点为中心的吸引/排斥，用于吸附、爆炸击飞 |
| `AbilityTask_ApplyRootMotionJumpForce` | `FRootMotionSource_JumpForce` | 抛物线跳跃/跃击 |

这些 Task 全都是 `Replicated` 且带 `TickTask`，走 CMC 的 `FRootMotionSourceGroup`，
因此**网络复制与客户端预测是免费的**——这正是不自己造轮子的关键理由。

#### 三个参数决定手感，值得单独记住

`MoveToActorForce` 的完整签名里有几个参数是做手感的核心：

```cpp
static UAbilityTask_ApplyRootMotionMoveToActorForce* ApplyRootMotionMoveToActorForce(
    UGameplayAbility* OwningAbility,
    FName TaskInstanceName,
    AActor* TargetActor,
    FVector TargetLocationOffset,                    // 停在目标身前而不是身体里
    ERootMotionMoveToActorTargetOffsetType OffsetAlignment,
    float Duration,                                  // 位移总时长，要和 Montage 段落对齐
    UCurveFloat* TargetLerpSpeedHorizontal,
    UCurveFloat* TargetLerpSpeedVertical,
    bool bSetNewMovementMode, EMovementMode MovementMode,
    bool bRestrictSpeedToExpected,
    UCurveVector* PathOffsetCurve,                   // ★ 路径偏移：做弧线、侧滑、抛物
    UCurveFloat* TimeMappingCurve,                   // ★ 时间重映射：做"前段爆发、后段刹停"
    ERootMotionFinishVelocityMode VelocityOnFinishMode,
    FVector SetVelocityOnFinish,                     // 结束瞬间速度，决定收招是否带惯性
    float ClampVelocityOnFinish,
    bool bDisableDestinationReachedInterrupt,
    float ReachedDestinationDistance = 50.0f);       // 到达判定半径
```

- **`TimeMappingCurve` 是解决脚滑的主要手段。** 动画的视觉位移不是线性的（起手慢、突进快、收招停），
  如果程序位移匀速推进，脚步和位移就会错位。把这条曲线画成和动画视觉节奏一致的形状，
  脚滑问题基本消失。这是 in-place 方案能用的前提。
- **`PathOffsetCurve`** 让路径不必是直线，可以做侧向绕行、跃起再落下。
- **`SetVelocityOnFinish`** 决定动作结束时角色是立刻停住还是带一点惯性滑出，影响"重量感"。

另有 `ApplyRootMotionMoveToTargetDataActorForce`，直接从 `FGameplayAbilityTargetDataHandle`
取目标。命中判定已经产出 TargetData 时用它，省一次目标查找。

### 13.4 终点解算写 C++ 还是蓝图

> 本节是设计结论，解算器尚未实现（15.3）。它的形态取决于锁定系统与真实的攻击动作，
> 现在先造一套结构等着被填只会浪费一次返工。

**解算写 C++，参数配在数据资产，蓝图只做表现编排。** 三条理由：

1. **联机确定性。** 突进终点必须在客户端预测和服务器权威上算出**相同结果**，否则会出现
   客户端冲到位、服务器判定没到位，然后被 `ClientAdjustPosition` 拉回去的橡皮筋。
   蓝图容易引入非确定性来源（Tick 顺序依赖、随机、浮点累积路径不一致）；C++ 里可以把解算
   写成纯函数，输入相同必然输出相同。
2. **解算本身是几何与查询问题。** 目标筛选、扇形范围判定、障碍物检测、贴墙修正，
   这些是向量运算加 `SweepSingleByChannel`，在蓝图里连线又长又慢又难调。
3. **可测试。** 纯函数的解算器可以脱离运行时单测，蓝图不行。

但**不要把参数硬编码进 C++**。分工是：

```
C++（解算逻辑，确定性）
  └─ UGGYGOMotionWarpSolver::SolveDashTarget(
         const FGGYGOMotionWarpParams& Params,   ← 参数从资产来
         const FGGYGOMotionWarpContext& Context, ← 运行时上下文
         FGGYGOMotionWarpResult& OutResult)      ← 终点、时长、曲线选择

数据资产（可调参数，美术/策划改）
  └─ UGGYGOMotionWarpParams：最大突进距离、最小距离、停止余量、
                             时长、PathOffsetCurve、TimeMappingCurve

蓝图（表现编排，可选）
  └─ GA 的蓝图子类：串 Montage、Cue、镜头，但不参与终点计算
```

推荐的落地形态是**在 C++ GA 里做解算并启动 AbilityTask**，蓝图子类只覆盖表现部分。
纯蓝图 GA 只适合完全无位移解算的简单能力。

### 13.5 一次攻击的完整时序（做法 C）

```
1. HeroComponent 收到 InputTag.Attack.Light → ASC 缓存句柄   [本地]
2. Controller 的 PostProcessInput → ProcessAbilityInput
     → 组仲裁通过 → TryActivateAbility                      [生成 PredictionKey]
3. GA 的 ActivateAbility                                    [客户端预测 + 服务器]
     ├─ 解算终点/时长/曲线                                   [C++ 纯函数，两端一致]
     ├─ 启动 PlayMontageAndWaitForEvent（in-place 攻击 Montage）
     └─ 启动 ApplyRootMotionMoveToActorForce（或 MoveToForce）
4. CMC 逐帧消费 RootMotionSource 推进位移                    [自带复制与纠正]
5. Montage 上的 AnimNotify 发 GameplayEvent                 [判定窗口开/关]
6. Task 的 EventReceived → MeleeTraceComponent 开窗 → 命中 → 应用伤害 GE
7. GE 触发 GameplayCue → 特效音效震屏
8. Montage 结束或被打断 → EndAbility
     └─ RootMotionSource 随 Task 销毁自动移除
     └─ 相机接管随 EndAbility 自动撤销
```

关键点：**位移和动画是两条并行的轨道，由同一个 GA 启动、共享同一个时长**。
它们不互相驱动，而是各自独立地被对齐到同一个时间基准上。

### 13.6 什么时候用做法 A（纯 RootMotion）

不是所有动作都要程序解算。判断标准很简单：**位移终点是否依赖运行时上下文**。

| 动作 | 位移终点依赖运行时？ | 选择 |
|---|---|---|
| 原地轻攻击 | 否，固定小前冲 | A |
| 翻滚 / 后跳 | 否，固定距离 | A |
| 收招、起手 | 否 | A |
| 突进斩（冲到敌人身前） | **是，依赖目标位置** | C |
| 位移技（冲一段距离但要避开墙） | **是，依赖障碍** | C |
| 追击连段（目标在移动） | **是，依赖目标实时位置** | C（MoveToActorForce） |
| 被击退 | **是，依赖伤害方向与强度** | C（ConstantForce） |

做法 A 的资产要求：动画在 DCC 里保留根骨骼位移，导入时勾 `EnableRootMotion`，
`RootMotionRootLock` 按需设为 `RefPose` 或 `AnimFirstFrame`。

### 13.7 与 ZZZ 曲线位移的关系

第 10.3 节讨论的 Locomotion Profile 曲线服务于普通移动与转身，和本章由 GA 发起的
动作位移是两套东西，不要混：

| | locomotion（第 10 章） | 动作位移（本章） |
|---|---|---|
| 来源 | 普通走跑：CMC 运动参数；转身/刹停：独立 MotionProfile 或原生 RootMotion | 程序解算或动画 RootMotion |
| 驱动 | CMC；必要时由 CMC 按 ProfileId/时间采样并交 RootMotionSource | GAS 的 ApplyRootMotion* Task |
| 发起者 | CMC（AnimBP 只消费状态） | GameplayAbility |
| 是否走 GAS | 否 | 是 |

两者最终进入 CMC 的 `FRootMotionSourceGroup`，其中 Override 按优先级仲裁，Additive 才叠加；不能把所有 source 都理解为相加。原姿态仍含平移而胶囊同时移动，也会产生视觉双位移。

`Restriction.CantMove` 当前限制 `GetMaxSpeed()`，并不能自动终止 Brake/TurnBack RMS。动作曲线通道由 `BeginActionMotion` 显式移除 Locomotion 源，并在自身源在场时暂停 Locomotion Profile 推进/自动旋转；门控从 Handle/RMS 生命周期派生，不由 GA 每帧写另一个移动开关。源到期、取消和离地均释放门控。该增量只用于明确申请动作曲线的调用方；玩家攻击移动策略未在此修改。

### 13.8 已编码增量：显式动作曲线

用户选择 Boss 攻击使用曲线形状。`UGGYGOActionMotionProfile` + CMC `BeginActionMotion(Profile, PlayRate)` / `EndActionMotion(Handle)` + `FRootMotionSource_GGYGOActionCurve` 已编码、待完整构建与实测。Kevin Ice01/02 将以导入后同一条轨迹生成原地 AS 与累计位移 CV；原75个AS保留。具体动作、速率与缩放由 GA 蓝图和资产配置。

接口、生命周期、单位/轴核验与资产状态见 [[Movement/动作曲线执行]]，调用图见 [[GGYGO_流程_动作曲线执行.canvas]]。ActionMotion 与 Locomotion 使用各自的 Profile 和资源句柄；切换 MovementSet 不结束 ActionMotion。13.1–13.6 的目标驱动 Task / 原生 RootMotion 仍是其他动作可选方案，不能视为 Kevin 已使用的实现。

### 13.9 是否需要 Motion Warping 插件

UE 自带 `MotionWarping` 插件，能按 Montage 上的 `MotionWarpingWindow` NotifyState
把动画自带的 RootMotion **重定向**到指定目标点。它和做法 C 的区别：

| | RootMotionSource（做法 C） | Motion Warping |
|---|---|---|
| 位移形状 | 程序生成 | 来自动画 RootMotion，只是被拉伸/旋转到目标 |
| 脚滑 | 靠 TimeMappingCurve 对齐 | 天然较好（形状还是动画的） |
| 精确终点 | 支持 | 支持 |
| 复杂度 | 中 | 需要给每个动画标 Warp 窗口 |

**Motion Warping 更适合"动画已经有很好的位移形状，只需要拉到目标点"的情况**，
这对做法 A 的资产是天然搭配。建议：先用做法 C 把突进跑通（不依赖额外插件），
等攻击动作数量上来、脚滑成为实际问题时再评估引入 Motion Warping。这一项列入待决策。

## 14. 已确认、延期实施：WalkRun 运动偏移

本需求已于 2026-09-30 根据参考视频确认，但按用户要求等待当前全模块优化完成后再进入实现；本节是目标契约，不是当前代码事实。

- Walk 与 Run 共用一套连续转向机制。Walk 强度较低，并随现有 `WalkRunBlendAlpha` 连续增强到 Run 强度。
- Movement 独占目标方向、胶囊朝向、真实速度方向与转向角速度。目标方向变化后，朝向和真实轨迹都平滑追赶并形成弧线；大角度通过曲线提高响应，小角度保持较慢且稳定的修正。
- Movement 后续需要发布同一份只读转向快照，至少能表达有符号方向误差、实际角速度、速度方向误差、WalkRun 强度以及普通转向是否被 `TurnBack` 或动作位移接管。
- [[Camera/结构|Camera]] 只根据快照计算构图侧移和回收，不决定胶囊朝向；[[Animation/结构|Animation]] 只根据快照表现倾身、侧身与恢复，不决定轨迹。
- C++ 负责可预测的运动契约、权威状态与跨模块只读接口；角速度映射曲线、Walk/Run 强度、最大/最小值、镜头偏移和表现幅度放在对应角色/CameraMode/动画配置资产中。
- 实施前必须先拆为 Movement 共享契约与预测、Camera 消费端、Animation 消费端三个文件互斥任务；Movement 契约冻结后才允许另外两组写入，不新建协调模块或第二套帧调度。

参考视频中 9.5–10.5 秒只证明大幅转向期间角色侧身和构图偏离，14.0–14.7 秒只证明恢复过程平滑；视频没有输入叠层，不能据此反推固定世界角速度或唯一 Camera Offset 算法。19.6–21.0 秒特殊高速动作和 23.0–24.0 秒距离/FOV 变化不在当前确认范围。
