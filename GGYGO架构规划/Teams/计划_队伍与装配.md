### 9.1 Lyra 的事实

Lyra 有两套布局：

**布局 1（玩家角色，默认）：ASC 挂 PlayerState**

```
ALyraPlayerState                     ← ASC 的 Owner
  ├─ ULyraAbilitySystemComponent     ← ASC 本体（LyraPlayerState.h:153）
  ├─ ULyraHealthSet / CombatSet
  └─ PawnData (Replicated)
        │ InitAbilityActorInfo(Owner=PlayerState, Avatar=Pawn)
        ▼
ALyraCharacter                       ← Avatar，GetAbilitySystemComponent() 转发到 PlayerState
  ├─ ULyraPawnExtensionComponent     ← InitState 状态机协调初始化顺序
  ├─ ULyraHeroComponent              ← 输入绑定、相机
  └─ ULyraHealthComponent            ← 把 HealthSet 包成组件 API
```

**布局 2（AI/NPC）：ASC 挂 Pawn 自身**

`ALyraCharacterWithAbilities` 自己持有 ASC + HealthSet + CombatSet，`PostInitializeComponents` 里自行 `InitAbilityActorInfo(this, this)`。

### 9.2 为什么布局 1 在 GGYGO 不成立

一个 ASC 只能挂**一套**同类型 AttributeSet。三个角色共用 PlayerState 上的一个 ASC，就是共享同一份 HP、同一份技能冷却——这不是绝区零，是换皮不换数据。

绝区零/原神的实际模型是：**每个角色有独立的 HP、能量、技能冷却、Buff，下场后继续走冷却和回能**。这要求每个角色一套独立的属性和 Ability 状态。

但"每个角色一套"不等于"ASC 必须挂 Pawn"。这两件事被混为一谈会带来 9.3 要解决的时序问题。

Lyra 两套布局的**属性集来路完全不同**，这是照抄时最容易漏掉的一点：

| Lyra 布局 | ASC 宿主 | AttributeSet 从哪来 | 为什么能这样 |
|---|---|---|---|
| 布局 1（`ALyraCharacter`，默认） | PlayerState | `ALyraPlayerState::SetPawnData` 里由 AbilitySet 授予 | PlayerState 先于 Pawn 存在。GameMode 在 Experience 就绪后设 PawnData 并授予，**之后**才生成 Pawn，所以 Pawn 上的 HealthComponent 初始化时属性集必然已在 |
| 布局 2（`ALyraCharacterWithAbilities`） | Pawn 自己 | **角色构造函数里的 `CreateDefaultSubobject`**，不走授予 | 默认子对象在 `InitializeComponent` 阶段被 ASC 自动发现，早于任何 InitState 阶段 |

布局 2 的源码注释把机制说得很直接：

```cpp
// These attribute sets will be detected by AbilitySystemComponent::InitializeComponent.
HealthSet = CreateDefaultSubobject<ULyraHealthSet>(TEXT("HealthSet"));
CombatSet = CreateDefaultSubobject<ULyraCombatSet>(TEXT("CombatSet"));
```

也就是说：**Lyra 在任何布局下都保证"属性集就绪早于读属性的组件初始化"**，只是两种布局靠不同机制达成。
如果采用布局 2 的 ASC 归属，却沿用布局 1 的授予方式，就得到一个两边优势都没有的组合——
属性集晚于 ASC 就绪，而又没有 PlayerState 那样的天然先后关系兜底。

### 9.3 D1 采纳的布局：Slot 持有 ASC 的三层结构

问题的实质不是"ASC 挂哪"，而是**ASC 的生命周期挂在谁身上**。挂 Pawn 意味着属性集的就绪时机
被 Pawn 的初始化流程牵制；而 Pawn 是三层里最"短命"也最复杂的一层（要生成 Mesh、CMC、AnimBP、
等 Controller）。把 ASC 上移一层，交给一个只承载数据的 Slot：

```
AGGYGOPlayerState                     ← 玩家级
  ├─ UGGYGOSquadComponent             ← 名单与出战索引
  │    ├─ Roster                     ← 本局角色意图
  │    ├─ Slots[N]                   ← 唯一实际成员名单
  │    └─ ActiveSlotIndex            ← 唯一出战序号
  └─ 队伍级 ASC                      ← 目标/未实现（共享资源待需求，见 [[计划_实施状态#15.1 与计划的偏离|实施状态 15.1]]）

AGGYGOCharacterSlot（AInfo 派生，无 Mesh、无碰撞、不 Tick）   ← 角色数据层
  ├─ UGGYGOAbilitySystemComponent     ← 该位置的 ASC（Owner=Slot，Avatar=Pawn）
  ├─ UGGYGOHealthSet / CombatSet      ← 构造函数子对象，随 Slot 一同就绪
  └─ PawnData 引用                     ← 这个位置装的是哪个角色

AGGYGOHeroCharacter（Pawn）                                  ← 角色表现层
  ├─ UGGYGOPawnExtensionComponent     ← 协调；ASC 从 Slot 注入而非自己创建
  ├─ UGGYGOCharacterMovementComponent / Mesh / AnimBP
  ├─ UGGYGOHealthComponent            ← 读 Slot 的 HealthSet
  └─ UGGYGOHeroComponent              ← 仅出战角色：输入绑定、相机
```

参考对象仍是 `ALyraCharacterWithAbilities` 的**属性集子对象化**做法，但宿主从 Pawn 换成 Slot。
Slot 用 `AInfo` 派生，可参考 Lyra `Teams/LyraTeamInfoBase` 的复制设置。

这个结构带来四个直接结果：

1. **时序问题在结构上消失。** 属性集是 Slot 的默认子对象，Slot 创建完成即就绪。
   Pawn 上的 HealthComponent 无论在哪个阶段初始化，都不可能"找不到 HealthSet"。
2. **Pawn 可以按需生成销毁。** 下场角色不必常驻带 Mesh 的 Pawn，而 GE 计时、冷却、回能
   继续在 Slot 的 ASC 上跑。这才是 9.4 里那条"轻量角色状态容器"的正解，
   而它同时也是性能优化。
3. **持久 GAS 状态可跨 Pawn 生命周期。** Pawn 销毁后 Slot 的属性与 Buff 仍在；这不表示死亡后自动复活/重新绑定已实现，当前宿主死亡标签会阻止绑定不同新 Pawn。
4. **切人不需要搬运 ASC。** 当前全员常驻路径先走共享 ASC 能力退出并退旧输入，再切 Controller 附身和出战索引；各 Slot 的 Avatar 已在装配时绑定。Controller 变更经 Character/PawnExtension/Host 合法 Refresh；需要替换实体时才走 Attach/Detach，Teams 不直接重设 ActorInfo。

代价是多了一层实体和一次 `InitAbilityActorInfo` 的重设时机，以及下面四条必须处理对的约束。

**约束 1：预测的 Owner 链必须能追到 PlayerController。**
GAS 的客户端预测依赖 `ASC->GetOwnerActor()->GetNetOwningPlayer()`。Slot 的 `SetOwner()`
在当前玩家队伍契约中必须直接指向所属 PlayerController；05a2还会核对PlayerState唯一Squad和该Controller双向身份。设错的症状是
PredictionKey 生成不出来、所有 `LocalPredicted` 能力静默退化为纯服务器执行，
表现为输入延迟一个 RTT，**且不产生任何错误日志**。这是本方案最容易翻车的一处。

**约束 2：Avatar 可能为空，能力要能识别这件事。**
Pawn 按需生成时 Slot 的 Avatar 为 null。纯数值 GE（冷却、回能、Buff 计时）不受影响，
但 Montage、位移、Cue、`MeleeTraceComponent` 全都依赖 Avatar。
统一在 `UGGYGOGameplayAbility::CanActivateAbility` 加一条"本能力需要 Avatar"的前置检查，
不要让每个能力各自判空——那等于把同一个前提复制 N 份。

**约束 3：切 Avatar 时必须重设 ActorInfo 并解绑旧 Pawn。**
创建/替换方只调用宿主`AttachAvatar(NewPawn)`；需要解除指定旧实体时用`DetachAvatar(ExpectedPawn)`。
宿主统一协调复制Avatar、PawnExtension与ActorInfo；PawnExtension按期望ASC解绑，避免旧Pawn仍被当作Avatar或迟到清理破坏后继。
GameMode和Squad不直接调用`InitAbilityActorInfo`复制此执行链。

**约束 4：区分 Actor 相关性、GE 信息模式和属性复制条件。**
当前 Slot 设 `bAlwaysRelevant`，ASC 用 `Mixed`，这两项设置保持不变。

Actor 相关性决定客户端能否接收该 Actor 及其组件的复制。改成 `bOnlyRelevantToOwner` 会使非拥有者失去该 Slot 的相关性，连依赖它的 Tag/Cue 等旁观者表现也受影响；不能为隐藏某些面板数值而裁掉整个 Actor。

ASC 的 `EGameplayEffectReplicationMode` 只规定 **GameplayEffect 信息**的复制模式：`Mixed` 向 owners/autonomous proxies 提供完整 GE 信息，向 simulated proxies 提供最小 GE 信息。它不决定 AttributeSet 各属性的收件条件；属性条件由各 Set 自己的 `GetLifetimeReplicatedProps` 声明。

| 当前属性 | 自身复制条件 | 在相关 Actor 上的收件边界 |
| --- | --- | --- |
| Health / MaxHealth / Poise / MaxPoise | HealthSet 声明 `COND_None` | 没有额外 owner-only 条件，相关客户端仍可收到这些健康/韧性量。 |
| BaseDamage / BaseHeal / BasePoiseDamage | CombatSet 声明 `COND_OwnerOnly` | 按该属性自身声明仅发给拥有连接；不是 Mixed 自动筛出的结果。 |

因此，Actor 相关性、GE 信息模式和属性条件分别负责不同层次，不能互相替代。Slot 不复制 Transform 的轻量宿主设计保留；本轮只据源码纠正语义，没有更改复制策略或完成网络动态验收。

跨级查询规则：角色 Ability 需要读队伍资源时，通过 Slot 的 Owner 链拿到 PlayerState 上的
队伍 ASC，不要把队伍属性复制进角色 AttributeSet。

**队伍规模可配置。** Slot 数量由编队名单决定，不写死。
但保留一个编译期上限常量（`GGYGO_MAX_SQUAD_SIZE`，当前为 4）用于复制数组预分配与配置校验——
运行时长度可变，上限固定，避免配置错误把 12 个 ASC 变成几十个。

#### 编队名单与位置的关系

位置是运行时对象，必须有世界才能生成。但"玩家这局想带谁"这件事在没有关卡、
没有 GameMode 的时候就该能表达（编成界面、存档读取都发生在战斗之外）。
所以从"玩家存了哪几套编队"到"场上的 ASC 宿主"分成三层：

| | 是什么 | 存在哪 | 生命周期 |
|---|---|---|---|
| **编队预设** | 玩家存的 N 套编队 + 选了哪套出战 | `UGGYGOSquadPresets`（`ULocalPlayerSaveGame`，缓存在 `UGGYGOLocalPlayer` 上） | 落盘，跨关卡 |
| **编队名单** | 这一局带谁：出战那套的快照 | `UGGYGOSquadComponent::Roster`（挂 PlayerState，复制给拥有者） | 一局，装配后锁定 |
| **位置** | 照名单造出的 ASC 宿主 | `Slots[]` | 一局 |

编成面板读写最上面一层，装配读中间一层，GAS 只认最下面一层。
面板不碰 `SquadComponent`：面板运行在主菜单，那时没有 World 也没有 PlayerState。

装配时按优先级选择来源，只有明确正常 Unconfigured 才使用默认配置：

```text
已经设好的名单（有流程在装配前调过 SetRoster，例如将来的客户端上报）
  ↓ 为空时
本地玩家存档里的出战编队（UGGYGOSquadPresets 的出战那套）
  ↓ 仅正常 Unconfigured；Invalid 诊断并停止生成
Experience::SquadMembers（玩法配置里的默认编队）
```

**当前接线**：GameMode 已消费 LP TryGet 与解析结果三态；完整 Applied 设置名单，Unconfigured 显式选择 Experience，Invalid（包括次级本地保存拒绝）在 Actor 生成前停止。原始名单 Num 含空项，超限整体拒绝；选定名单为空仍报错。ChoosePlayerStart 必须给有效原 Actor/Root、同 World 与合法真实 Transform，实际原点合法。正常无 LP 的服务器远程 PC 仍是显式 Unconfigured 模式。创建者 A 仅消费未交付原物，不回滚已交付成员；整队成功政策与正式动态仍未闭合。

保留默认编队而不是要求必须先编成，是为了让没有编成界面的场景
（自动化测试、直接从编辑器起某个关卡）也能跑出可操作的角色。
否则每次调试都要先走一遍编成流程。两者都为空时报错并不生成角色。

**局内不能改编队。** `SetRoster` 在装配之后会被拒绝。这不是偷懒，是因为
"换掉某个位置上的角色"没有正确语义：位置的属性集是默认子对象，
换角色时上一个角色的数值会残留在同一批对象里，而"新上来的角色应该多少血"
没有合理答案——保留百分比荒谬，重置满血则可以靠反复换人刷治疗。
已授予的能力与已生效的 Buff 同样无法干净地对应到另一份 PawnData。

要在战斗中换整队或换单人，正确形态是**每个角色常驻一个位置，编队只是对位置的引用列表**，
而不是让位置换角色。当前结构（编队名单 → 装配出位置）可以平滑扩展成那样，
但在有明确需求前不做。

**存档里存的是 `FPrimaryAssetId`，不是资产指针。** 存指针会让反序列化拉起**所有**
编队里的**所有**角色资产，包括这局用不到的那几套，而角色资产带着 AbilitySet、
动画、相机模式，是一整条引用链。存 Id 则只在装配时加载出战那一套。
代价是 `GGYGOPawnData` 必须注册成 PrimaryAssetType，且 `CookRule` 必须是 `AlwaysCook` ——
存档里的 Id 不构成资产引用，没有任何硬引用链会把角色带进包，
漏配的症状是"编辑器里好的，打包后编队解析不出角色"。

**为什么预设要缓存在 `UGGYGOLocalPlayer` 上。** 面板、GameMode与PC应取得原LP的同一份模型，避免各自加载副本形成过期视图；LP跨关卡，PS会重建。当前已接 `TryGetSquadPresets(Out, Error)`，缓存来源记录与模型原生LP/GI/user/index/槽须一致，重入/失效明确失败，不清空后另读、重建或改领另一来源。模型的 `GetForPlayerController` 已移除；模型工厂 `TryLoadForLocalPlayer` 只依赖引擎LP参数，LP自己调用工厂并发布唯一缓存。

**当前持久化政策已明确**：保留原 `GGYGOSquadPresets` 槽，只允许原GI主LP访问/保存；次级本地玩家明确拒绝，不能覆盖主文件。原缺槽可以创建内存候选但工厂不自动保存；检测到非法旧数据则保留文件/字段并返回Invalid，不自动修复/迁移/重置。该政策不把D2每名玩家的本局队伍改为共享一支；将来的次级持久化或远程上报仍需另定入口，不能把次级错误当作普通无LP默认模式。

同步/异步保存 overrides 复用 `RequestSaveForOriginalSource(bAsync)` 校验原主来源后调用Super；请求执行、计数和完成归引擎。PC三个编辑Exec消费native bool：拒绝/失败保留内存编辑，true只报告请求结果，不证明磁盘持久化。完整加载/缓存/保存边界见 [[Teams/结构#主玩家保存与唯一缓存|当前保存契约]]；既有Slot布局与GAS责任不改变。

**尚未接入的两环**：一是编成面板本身（当前只有开发期控制台命令
`GGYGOSetSquadMember` / `GGYGOSetActiveSquadPreset` / `GGYGODumpSquadPresets`
作为入口）；二是联机时远程玩家的编队上报 —— 编队存在客户端自己的磁盘上，
服务器读不到，所以目前联机的远程玩家会走默认编队。
上报接进来时只需要多一条 Server RPC 填第一级来源，位置与 GAS 不用动。

### 9.4 D2 的网络预算

每个玩家各带一支队伍，意味着：

| 项 | 4 人房 × 每队 3 角色 |
|---|---|
| Slot（含角色 ASC） | 12 |
| 队伍 ASC | 4 |
| 常驻角色 Pawn | 4（仅出战）～12（全常驻），由 Pawn 生成策略决定 |

Slot 是轻量 Actor，12 个 Slot 的开销与 12 个带 Mesh 的 Pawn 不在一个量级。
Pawn 的生成策略因此成为一个**可调项而非架构约束**：先按全常驻做（切人零延迟），
压力测试后若需要，改成仅出战角色持有 Pawn，Slot 侧不用改。

以下保留网络预算要求：Mixed / AlwaysRelevant已采用，降频/休眠与压力验收尚未完成，当前Slot仍设100Hz。

1. **下场角色降低复制频率。** 下场 Slot 用 `NetUpdateFrequency` 降频或 `NetDormancy` 休眠；但 GE 计时不能停（冷却、回能要继续），所以是"降低复制"而不是"停止模拟"。
2. **GE 信息复制模式。** `EGameplayEffectReplicationMode` 三选：`Full` 向所有收件客户端提供完整 GE 信息；`Mixed` 向 owners/autonomous proxies 提供完整 GE 信息、向 simulated proxies 提供最小信息；`Minimal` 仅复制最小 GE 信息。当前玩家 Slot 用 `Mixed`，BossState 用 `Minimal`。这些模式不设置 AttributeSet 属性的复制条件。
3. **Slot 相关性与属性条件分别配置。** 当前保持 `bAlwaysRelevant`，让旁观者仍能接收该 Actor 的必要复制；HealthSet 四健康/韧性量按自身 `COND_None`，CombatSet 三基础量按自身 `COND_OwnerOnly`。不能用整个 Actor 的 owner-only 相关性代替单个属性的条件，详见9.3约束4；没有新增降频或网络优化。

出现"给整支队伍或全场角色广播 Buff"的需求时，照抄 Lyra 的 `LyraGlobalAbilitySystem`
（一个 WorldSubsystem，登记所有 ASC 并统一施加/移除），不要手写遍历。

### 9.5 切换角色的流程

以下为C12已实施的服务器组件请求链。Teams负责成员/目标与最后出战提交，ASC负责共享能力退出，GA持政策/生命周期，Hero/ASC分别退原输入；原生PC执行控制，Character→Extension→Host继续负责合法Refresh。没有新切人状态机或帧调度器。

```text
1. SwitchToSlot(Index)：唯一PS/Squad/PC、双方真实绑定/Ready、目标无控制/非死亡、
   旧PC↔Pawn实际关系及非重入准入；捕获原弱对象/双方完整Context，持同步护栏
2. 有旧位：旧ASC TryExitAbilitiesForAvatarSwitch(OldContext, 原请求纯查询)
   全部真实实例先预检，再逐个原Cancel；仅执行Completed、查询Ready允许继续
3. 旧Hero ReleasePlayerInput → 重检 → 旧ASC ClearAbilityInput → 重检
   原绑定/held各归自己的公开入口，不制造物理释放、重按或后继释放
4. 原PC UnPossess → Character/Extension/Host合法sameBinding Refresh → 完整读回
   Deactivate旧 → Activate新，每次外调后重检原布局/端点/Ready/旧能力
5. 原PC Possess新 → PC↔新Pawn双向/旧Pawn无控制及绑定/能力读回
   最后写ActiveSlotIndex → 广播 → 护栏内重检真实新控制 → bool
6. 原Slot/ASC/Avatar不重建不搬运；原Slot继续保有GE、CD、属性
```

默认GA政策Cancel，任一必需Cancel真实NotCancelable在首次取消前拒绝整次请求；显式ContinueInBackground（含不可取消实例）不挡切人。Continue经合法sameBinding Refresh只保留原End资格，不续授ResourceWork、输入、控制、镜头或位移；当前三叶没有覆盖携带这些资源的全能力链。

中途失配/关闭/Busy/真实取消未Completed即停止，明确返回false。已取消GA及退休held不恢复，不自动重新Possess旧Pawn，也不Undo可能属于后继的原生控制；原布局仍在而旧控制丢失时清索引/广播空值。目标未被控制且原请求有效才可撤回自身目标表现。Next/Previous跳过不可出战位，但真实切人尝试失败不转试另一目标。完整输入/返回/失败契约见 [[Teams/结构#C12 切人退出与原生控制契约|C12接口与顺序]]。

**持久归属与原生控制分开。** Slot.Owner保持原PC；APawn.UnPossessed会清Pawn.Owner，待命Pawn不因此丢失Slot/ASC/Avatar绑定。所有外调后仍核原Binding身份与当前完整Context/真实Ready，不将getter快照或取消历史当工作权限。

R4三项Teams真实通过：Cancel/状态保留、全量NotCancelable无副作用拒绝、不可取消Continue切人后原End Completed。夹具用公开借用RegisterSlot并显式PawnClientRestart；它不证明Created完整销毁、自动RPC送达、正式资产、联机或所有失败重入组合。R2/R3失败及实际报告见 [[计划_队伍与装配#C12 门禁、根因与有限验收（2026-10-06）|门禁与有限验收]]。

**顺序必须先 `UnPossess` 再 `Possess`**。反过来的话，`UnPossess` 旧角色时
会把刚建立的附身关系一起清掉。

**`Possess` 只能在服务器执行**，客户端只能预测表现层（相机、UI），不能预测控制权转移。
联机往返及表现补偿仍是待验证的网络需求；C12私有世界三叶没有测量RPC/RTT，也没有接入切人特效或镜头推进。

**全员常驻时生成在同一个出生点**：非出战成员立刻隐藏关碰撞，重叠无害；
分散生成反而有害——切人时角色会从别处瞬移过来。
`SpawnCollisionHandling` 必须用 `AdjustIfPossibleButAlwaysSpawn`，
否则第二、三个成员会因重叠而生成失败。改为按需生成后这条约束自然消失。

把切人做成一个走 GAS 的 GA（可被打断、有 CD、消耗切人能量）是后续的事，
前提是队伍级 ASC 存在（D1，见 [[计划_实施状态#15.1 与计划的偏离|实施状态 15.1]]）。现在切人是组件上的直接调用，没有冷却与消耗。

### 9.6 从"ASC 挂 Pawn"迁移到 Slot 的改动清单

以下保留当时的迁移顺序作为设计背景。当前代码已把 ASC、基础属性和 Avatar
绑定下沉至 `AGGYGOCombatantState`；实际类和接口以 [[Teams/结构]] 为准。
改动按依赖顺序排列，每一步都应能独立编译，便于出错时定位。

**第 1 步：新增 Slot 类型（纯新增，不影响现有代码）**

```
Teams/
  GGYGOCharacterSlot.h/.cpp      AInfo 派生。持有 ASC、HealthSet、CombatSet、PawnData 引用
  GGYGOSquadTypes.h              GGYGO_MAX_SQUAD_SIZE 常量
```

Slot 构造函数里做三件事，顺序不重要但都必须是 `CreateDefaultSubobject`：
ASC、`UGGYGOHealthSet`、`UGGYGOCombatSet`。ASC 的 `ReplicationMode` 设 `Mixed`。
当前实现类上设 `bReplicates = true`、`bAlwaysRelevant = true`、关掉 Tick；
GE 的完整/最小信息分发由 ASC 的 `Mixed` 模式控制；属性复制条件由各 AttributeSet 自己声明，当前 HealthSet 四健康/韧性量为 `COND_None`、CombatSet 三基础量为 `COND_OwnerOnly`。保持 Actor 相关性，不能用 `bOnlyRelevantToOwner` 把旁观者所需的 Cue/Tag 一并裁掉。
实现 `IAbilitySystemInterface::GetAbilitySystemComponent` 返回自己的 ASC。

Slot 有 `InitializeForPawnData(const UGGYGOPawnData*)`；Avatar 绑定已收口到
基类 `AGGYGOCombatantState::AttachAvatar(APawn*)`。后者统一更新复制引用、
PawnExtension 和 AbilityActorInfo，是约束 3 的唯一落点。

**第 2 步：`AGGYGOCharacterBase` 交出 ASC 所有权**

| 位置 | 现在 | 改为 |
|---|---|---|
| 构造函数 | `AbilitySystemComponent = CreateDefaultSubobject<...>` | 删除。Pawn 不再创建 ASC |
| 成员 `AbilitySystemComponent` | `TObjectPtr<UGGYGOAbilitySystemComponent>` | 删除，避免出现两个真值来源 |
| `GetGGYGOAbilitySystemComponent()` | 返回自己的成员 | 转发到 `PawnExtComponent->GetGGYGOAbilitySystemComponent()` |
| `GetAbilitySystemComponent()` | 同上 | 同上 |

**这是一处行为变化，必须记住**：改造前 Pawn 一构造出来就有 ASC；改造后在 Slot 注入之前
返回 nullptr。所有 `GetAbilitySystemComponent()` 的调用点都要判空，
不能再假设它非空。`check(ASC)` 这类断言要改成早退。

**第 3 步：属性集不再经 AbilitySet 授予**

`UGGYGOPawnExtensionComponent::GrantAbilitySets` 保留，但 `UGGYGOAbilitySet` 的
`GrantedAttributes` 不再承载 `HealthSet` / `CombatSet` —— 它们现在是 Slot 的子对象。
字段本身保留：将来某个角色专属的 AttributeSet 仍可能走授予。

相应地 `AGGYGOCharacterBase::OnAbilitySystemInitialized` 里
`HealthComponent->InitializeWithAbilitySystem` 的那段注释要改——
它现在依赖的不再是"AbilitySet 在 DataInitialized 授予"，而是"Slot 构造即就绪"。

`UGGYGOHealthComponent::InitializeWithAbilitySystem` 里找不到 HealthSet 时
把 `AbilitySystemComponent` 置回 nullptr 的那行要删掉。那行的意图是"绑定失败就回滚"，
实际效果是把失败变成静默可重入状态，掩盖了失败本身（Lyra 的版本不这么做）。
属性集就绪问题从结构上解决后，这里应当是硬错误。

**第 4 步：`UGGYGOSquadComponent` 从持有角色改为持有 Slot**

| 现在 | 改为 |
|---|---|
| `TArray<TObjectPtr<AGGYGOCharacterBase>> Members` | `TArray<TObjectPtr<AGGYGOCharacterSlot>> Slots` |
| `RegisterMember(AGGYGOCharacterBase*)` | `RegisterSlot(AGGYGOCharacterSlot*)` |
| `ActiveMemberIndex` | `ActiveSlotIndex`（语义不变，仍复制序号而非指针） |
| `ActivateMember` / `DeactivateMember` | 操作 Slot 的 Avatar 与 Pawn 显隐 |
| `CanMemberBeActive` | 查 Slot 的死亡状态，而不是 Pawn |

`GetActiveCharacter()` 保留（UI 与相机要 Pawn），实现改为 `Slots[Index]->GetAvatarPawn()`。

**第 5 步：`AGGYGOGameMode::SpawnSquadForPlayer` 改为两阶段**

原迁移目标已采用两阶段；创建者 A 已接准备、原资源交付与未交付失败回收。实际输入/输出签名详见 [[Teams/结构#GameMode 创建准备、交付与未交付责任（创建者 A）|创建者 A 契约]]，当前顺序为：

```
0. 固定原 GameMode/World/GF Session/Controller/PlayerState/唯一Squad/Experience资格
   同Controller同步重入或存活拒绝残留时拒绝；选定PawnData复制为本次弱快照
   已有Roster优先；TryApplySavedRoster消费Applied/Unconfigured/Invalid
   仅Unconfigured用Experience，Invalid停止；选定原数组容量先查Num（含空项）
   原StartSpot/Root实际世界Transform须合法，前后原Context/身份复核，无Identity替代
1. SpawnSquadSlot(Context, PawnData, OutActors) → native准备bool
   pre-spawn仅记录实际原Slot；Owner=原Controller；InitializeForPawnData后读回原配置/完成
```
