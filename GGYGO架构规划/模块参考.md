## 1. `System/` —— 全局设施

被所有模块依赖，本身不依赖任何模块。

| 类 | 职责 | 要点 |
|---|---|---|
| `GGYGOGameplayTags` | 全部原生 Tag 的声明与定义 | 用 `UE_DEFINE_GAMEPLAY_TAG` 而非 ini + 字符串查找。同一个 Tag 不能同时在 ini 与原生声明中定义 |
| `UGGYGOAssetManager` | 共享资产的加载与缓存 **[核心]** | 需在 `DefaultEngine.ini` 配 `AssetManagerClassName`。配错时 Error + 兜底实例，不中止（编辑器起不来代价太大） |
| `UGGYGOGameData` | 项目级共享 GE **[数据][待配]** | `Get()` 返回**可空指针**，资产未建时为 null。归属判断见 [[计划_实施状态#15.4 共享资产的归属|实施状态 15.4]] |

Tag 分类：`InputTag.*`　`Intent.*`　`Ability.*`　`AbilityGroup.*`　`State.*`　`Restriction.*`　`Gameplay.*`　`Event.*`　`GameplayCue.*`　`SetByCaller.*`　`InitState.*`　`Cheat.*`

## 2. `AbilitySystem/` —— GAS 扩展

### 2.1 顶层

| 类 | 职责 | 要点 |
|---|---|---|
| `UGGYGOAbilitySystemComponent` | 项目 ASC **[核心]** | 三件事：输入三阶段缓存、组仲裁、Tag 关系扩展 |
| `UGGYGOAbilitySet` | 成组授予能力/效果/属性集 **[数据]** | 授予顺序 AttributeSet → Ability → GE。仅服务器。玩家由 `AGGYGOCharacterSlot` 授予，Boss 由 `AGGYGOBossState` 将全部形态集合去重后一次授予。基础属性集（`HealthSet` / `CombatSet`）**不放这里** |
| `UGGYGOAbilitySystemGlobals` | 替换 GAS 全局对象 | 让所有 EffectContext 都是项目类型，`ExtractEffectContext` 才能稳定拿到扩展字段 |
| `FGGYGOGameplayEffectContext` | 扩展的 EffectContext | 多带能力来源与命中信息。`AbilitySourceObject` 不复制，仅服务器有效 |
| `IGGYGOAbilitySourceInterface` | 伤害衰减的提供方 | 由武器/角色数据资产实现。近战通常两个系数都返回 1 |
| `UGGYGOAbilityTagRelationshipMapping` | Tag 之间的阻断/取消关系 **[数据]** | 表达"语义互斥"，与组仲裁互补而非替代 |

**输入三阶段的必要性**：若 held 先激活了能力，随后 pressed 又把同一次按下当成输入事件发给刚创建的实例，能力会收到一次它不该收到的 InputPressed。所以 held 与 pressed 只收集句柄，第三阶段才统一 `TryActivateAbility`。

**`ProcessAbilityInput` 的驱动方**是 `AGGYGOPlayerController::PostProcessInput`，不是组件 Tick —— 必须在所有输入事件派发完之后消费，否则同帧内后到的按下会被推迟一帧。

### 2.2 `Abilities/`

| 类 | 职责 | 要点 |
|---|---|---|
| `UGGYGOGameplayAbility` | 能力基类 **[核心]** | 激活策略、组身份、优先级、失败反馈、相机接管与镜头微调（见 6.1）、额外消耗 |
| `UGGYGOAbilityCost` | 可组合的额外消耗 | 基础消耗之外的自定义条件，支持"仅命中时扣" |
| `GGYGOAbilityFailureMessages` | 失败反馈的消息通道 | 文本与 Montage 两条通道 |

`EndAbility` 被重写以自动清理相机接管 —— 能力可能被组仲裁取消、被死亡取消、或因 Avatar 销毁而结束，那些路径都不走能力自己的收尾逻辑。

### 2.3 `Groups/` —— 组仲裁

| 类 | 职责 |
|---|---|
| `EGGYGOAbilityGroupRule` | `Coexist` / `SingleInstance` / `SingleInstanceQueued` |
| `EGGYGOAbilitySelfPolicy` | `Coexist` / `Exclusive`（跨组压制低优先级） |
| `EGGYGOAbilityGroupBlockReason` | 拒绝原因，区分"值得重试"与"重试无意义" |
| `UGGYGOAbilityGroupConfig` | GroupTag → 规则映射 **[数据]** |

**三个正交维度**：组身份（配在 GA）、组规则（配在独立 DataAsset）、自身策略与优先级（配在 GA）。

**仲裁两层**：跨组的 `Exclusive` 压制，再查本组规则。阻断阈值与取消阈值严格互补 —— `bNewcomerWinsOnTie` 为真时阻断用 `>` 配取消 `<=`，为假时阻断 `>=` 配取消 `<`。

**`SingleInstanceQueued` 的关键**：不比优先级、**不取消**已有实例，直接拒绝新的。这是连段不被自己打断的保证。"排队"不在 ASC 实现 —— ASC 只给出 `GroupOccupiedQueued` 原因，重试由意图层负责，避免两个队列在"哪个才是真实待激活列表"上产生歧义。

### 2.4 `Attributes/`

| 类 | 职责 | 要点 |
|---|---|---|
| `UGGYGOAttributeSet` | 属性集基类 | 提供 `GetWorld()` 与类型化 ASC 访问 |
| `UGGYGOHealthSet` | 承受侧：生命、韧性 **[核心]** | 元属性 `Damage` / `Healing` / `PoiseDamage`；`OnOutOfHealth` / `OnPoiseBroken` 有边沿锁存只广播一次 |
| `UGGYGOCombatSet` | 输出侧：`BaseDamage` / `BaseHeal` / `BasePoiseDamage` | 与 HealthSet 分开，因为 Execution 要同时捕获"源的输出"与"目标的承受" |

**韧性并入 HealthSet 而非独立属性集**：同一次命中会同时改生命与韧性，拆开要跨 Set 读写。

**免疫穿透**靠 spec 上的 `Gameplay.Damage.SelfDestruct` 动态 Tag，`PreGameplayEffectExecute` 认这个。

### 2.5 `Executions/` / `Cues/` / `Tasks/`

| 类 | 职责 | 要点 |
|---|---|---|
| `UGGYGODamageExecution` | 伤害结算 | 属性捕获用 `bSnapshot=true`，记下**挥刀那一刻**的攻击力（判定与落地隔着若干帧，否则玩家觉得 Buff 白吃） |
| `UGGYGOGameplayCueManager` | Cue 加载策略 **[核心]** | 同步加载恒关（会卡帧）；Dedicated Server 完全跳过；需预热否则首次触发缺特效 |
| `UGGYGOGameplayCueNotify_HitImpact` | 按表面分流的命中特效 **[待配]** | 一个 Cue 内部按 GE 目标 Tag 分流，加表面只需加一行配置 |
| `UGGYGOAbilityTask_PlayMontageAndWaitForEvent` | 播 Montage 并等事件 **[核心]** | 合成一个 Task 而非两个并联，避免 Montage 被打断后事件监听仍在、接到下一个动画的同名事件 |

## 3. `Character/` —— 角色与组件

### 3.1 角色类

| 类 | 挂载的组件 | 用途 |
|---|---|---|
| `AGGYGOCharacterBase` | PawnExtension、Health、CMC（替换默认） | 当前通用 Avatar。自身不持有 ASC，但 PawnExtension 不假设外部宿主一定是 Slot |
| `AGGYGOHeroCharacter` | 上述 + Hero、Camera | 被玩家操控的角色 |
| `AGGYGOCombatantState` | ASC、HealthSet、CombatSet、复制 Avatar | 外置 ASC 的最小抽象宿主；`AttachAvatar` 是唯一装配入口，不包含 PawnData、队伍或 AI 业务 |

**为什么 Hero 单独一个类**：HeroComponent 是 InitState 的一个 feature，若每个 AI 敌人都带一个永远等不到 PlayerController 的 feature，`PawnExtension` 的 `DataInitialized` 要等所有 feature 到达 `DataAvailable`，整个角色的初始化链条会卡住，连动画都起不来。

**当前玩家角色的 ASC 不在角色身上**（决策 D1）：ASC 与属性集归队伍位置 `AGGYGOCharacterSlot`，角色只是它的 Avatar。
`GetAbilitySystemComponent()` 转发到 `PawnExtComponent`，**在位置注入之前返回 nullptr**，调用方必须判空。

不共用 PlayerState 上的一个 ASC，是因为一个 ASC 只能挂一套同类 AttributeSet，多角色共用会共享生命值与冷却。
玩家编队也不挂角色自己 —— 那样属性集只能跟着 Pawn 的初始化流程授予，而读属性的 `HealthComponent`
也在同一段流程里初始化，先后顺序变成靠约定维护的东西。放在位置上，属性集随位置构造即就绪。

### 3.2 `AI/Boss/` —— Boss 最小装配

| 类 | 职责 | 当前边界 |
|---|---|---|
| `UGGYGOBossDefinition` | Form、Phase、持久 AbilitySet 与 BehaviorTree 的静态定义 **[数据]** | 阶段 B 只消费一个初始 Form/Phase；已有 `DA_Boss_Test` 测试配置，多形态切换尚未实现 |
| `AGGYGOBossState` | Minimal ASC、CurrentForm/Phase、全部能力的一次性授予 | 不持有 BT、Controller、仇恨或生成逻辑 |
| `AGGYGOBossCharacter` | 复用 PawnExtension、Health、CMC 的纯 Avatar | 不创建第二套 ASC，不挂 HeroComponent，不自动生成 Controller |
| `AGGYGOBossAIController` | Possess Boss Avatar，启动/暂停同一 Brain | 阶段 D 才加入 Perception、Threat 与 CombatTarget |
| `AGGYGOBossEncounter` | 按定义装配 State、Controller、初始 Avatar | 当前只负责一次生成；不负责奖励、重置、阶段切换或技能选择 |

Boss 装配顺序固定为：State 初始化并一次性授予能力 → Deferred Spawn Avatar 并注入
PawnData/ASC → FinishSpawning → 同一个 Controller Possess。`AAIController` 的
`bStopAILogicOnUnposses` 被关闭，形态交接时只暂停 Brain，避免清空 BT/Blackboard。

引擎内最小样例位于 `/Game/AI/Boss/Test/`：`BP_Boss_Test`、`DA_Pawn_Boss_Test`、
`DA_Boss_Test` 和独立 `L_BossAI_Test` 测试图。单机 PIE 已验证 Boss 生成、Controller Possess、
`State.Boss.Form.Default`、`State.Boss.Phase.One` 与 `Health=100/100`；Cue/单次死亡和 DS 复制仍待验证。

### 3.3 `Components/`

| 类 | 职责 | 要点 |
|---|---|---|
| `UGGYGOPawnExtensionComponent` | 初始化协调者 **[核心]** | 不实现玩法。持有 PawnData 与**外部注入的** ASC，驱动 InitState 四阶段。只分发 PawnData 里属于 Pawn 的部分（MovementSet、Cue 预热）；能力授予与 ASC 侧配置归位置 |
| `UGGYGOHealthComponent` | 生命与韧性门面 | 原生委托转蓝图委托、持有可复制的三阶段死亡状态机、只读转发 |
| `UGGYGOCharacterMovementComponent` | 项目 CMC **[核心]** | 步态权威、Tag 驱动的移动禁用、曲线速度、急停转身 |
| `UGGYGOHeroComponent` | 输入 | 注册 IMC、绑定输入、连段输入缓冲 |
| `FGGYGOAnimCurveSampler` | 曲线采样 | 纯 C++。7 条 `RM_*` 曲线差分出每帧运动量 |

**InitState 的核心**是 `DataInitialized` 依赖 `HaveAllFeaturesReachedInitState` —— 把"等别人就绪"从各组件的手工时序判断变成向 Manager 的一次查询。

**配置分发时机**：`ApplyPawnDataToConsumers` 在 `HandleChangeInitState(DataInitialized)` 调用，而非 `InitializeAbilitySystem`。后者由 Pawn 在 `PostInitializeComponents` 调用，那时运行时生成的角色还没 `SetPawnData`。

**死亡两阶段**（`DeathStarted` → `DeathFinished`）：中间是死亡演出区间，角色还在场、还可能被追打，但不该响应输入。`OnRep_DeathState` 会把跳级变化补成逐级调用 —— 秒死时两次状态变化会合并进同一网络包。

### 3.4 `Data/`

| 类 | 职责 | 要点 |
|---|---|---|
| `UGGYGOPawnData` | 角色定义 **[数据][待配]** | PawnClass、AbilitySets、AbilityGroupConfig、TagRelationshipMapping、MovementSet、InputConfig、DefaultCameraMode、CuesToPreload |
| `UGGYGOMovementSet` | 移动参数 **[数据][待配]** | 速度、走跑切换、加减速、旋转、曲线缩放、转身参数 |
| `EGGYGOGait` / `EGGYGOTurnBackPhase` | 移动层公共枚举 | 单独成文件，因为同时被移动层与表现层引用 |

**为什么 PawnData 存在**：没有它时"角色有哪些能力"只能配在 Pawn 蓝图默认值上，于是想给同一 Pawn 换一套能力就得复制整个蓝图，队伍换人时也拿不到"下一个角色的配置"。

## 4. 移动层细节

### 4.1 CMC 的三个扩展点

| 扩展点 | 承担 |
|---|---|
| `GetMaxSpeed()` | 速度上限。CMC 自己在 `CalcVelocity` 里用它，加减速、摩擦、坡度、碰撞全部沿用引擎实现 |
| `UpdateCharacterStateBeforeMovement()` | 步态解算、转身相位推进、挂/摘曲线位移源 |
| `PhysicsRotation()` | 转身曲线接管段的朝向由 `RootMotion_Yaw` 驱动 |
| `FRootMotionSource_GGYGOCurve` | 动画驱动段（刹停、转身）的位移。Override 模式让引擎整段跳过 `CalcVelocity` |

`GetMaxSpeed()` 的优先级：`Restriction.CantMove` → 0；非地面 → 基类；曲线速度可用 → 曲线速度；否则步态固定速度。

**被禁止移动时返回 0 而不是硬停**：走 `GetMaxSpeed` 这条路，CMC 用自己的制动减速度平滑压到零；`StopMovementImmediately` 会让角色瞬间定住，联机下还会与服务器重演结果不一致。

### 4.2 网络预测

`FSavedMove_GGYGO` 保存步态、走跑计时器、Run 契约、曲线运动量、转身状态。
任何影响移动结果又不在基类里的状态都必须保存，否则回放结果与首次执行不同。

**步态只由本地控制端解算**，经 `CompressedFlags` 的 `FLAG_Custom_0|1` 传给服务器。
若服务器自算，两端对"输入从哪一帧开始"的采样差异会让计时器错开，
升档时机相差若干帧，期间速度上限不同，位置校正持续触发。

代价是客户端理论上可谎报 Run，收益上限仅走跑速差，位置仍受服务器校验。

**转身第一段**用 `FLAG_Custom_2` 同步。只同步这一个 bit 因为只有第一段改变移动行为。
另有一个 `COND_SkipOwner` 的复制属性给模拟代理 —— 压缩标志位只走客户端→服务器一个方向，不转发给其它客户端。

### 4.3 曲线驱动

曲线含义（名字的运行时唯一定义在 `GGYGOAnimCurveSampler.cpp` 的 `GGYGOAnimCurveNames`）：

| 曲线 | 含义 | 用法 |
|---|---|---|
| `RootMotion_Speed` | 该帧速度（cm/s） | 直接作速度，消除脚滑的主值 |
| `RootMotion_PosX` / `PosY` | 从动画段起点累计的位移（厘米） | 相邻帧差分 |
| `RootMotion_Dist` | 累计路程，单调不减 | 回退即表示换段或循环回绕 |
| `RootMotion_Yaw` | 累计转角（度），已解 ±180 折叠 | 差分得本帧转角，绝对值判断转身进度 |
| `RootMotion_DirX` / `DirY` | 烘焙好的速度方向 | 优先于位移差分，低速时位移差分噪声大 |
| `Cfg_ClipLength` | 规范化有效时长（秒） | 兼作"本动画烘焙过曲线"的存在性标记 |
| `Cfg_LoopTime` | 是否循环（0/1） | 循环动画的累计量会在循环点回绕 |

数据来源：逐帧值取自各动作 FBX 的外部 `Root` 节点，标量取自 AnimeStudio 导出的 per-clip JSON 的 `muscleClip`，由 `AAADocs/Scripts/` 的 Python 管线烘焙成 FloatCurve。资产上另有 12 条 `Cfg_*` 常量曲线（loopBlend / keepOriginal / mirror 等），运行时暂未消费。

坐标系：轴序就是 **UE 局部空间（X 前、Y 右、Z 上）**，无需转换。但基准是**动画段起点的朝向**而非角色当前朝向 —— 转身时角色已转过 180 度，而位移分量仍以进入动画那一刻的朝向为基准。需要世界方向的消费方要用"进入该段时记录的朝向"换算。

**段切换检测**用 `RootMotion_Dist` 回退而非位移差分：路程单调不减，位移会来回摆动（转身后半段位移一路减小，拿它判断会每帧误判）。循环动画绕回循环点同样触发，代价是每周期丢一帧增量；速度不经差分，所以无实际后果。

**采样时机**在 `TickComponent`（Super 之前）而非 `UpdateCharacterStateBeforeMovement` —— 后者在 sub-stepping 时一帧调多次，而采样器持有跨帧基线。

实测速度峰值：走跑 < 1000 cm/s，转身 2412，攻击类有瞬移式突进（`Attack_Normal_Enhance_03` 单帧位移 312cm、峰值 18724 cm/s）。`MaxCurveDrivenSpeed` 因此设为 20000。

**两条位移通道。** 曲线消费分成两类，走的路径完全不同：

| 通道 | 谁定方向 | 谁定速度 | 实现 |
|---|---|---|---|
| 输入驱动（走、跑） | 玩家输入 | `GetMaxSpeed()` 返回曲线速度作上限 | `CalcVelocity` |
| 动画驱动（刹停、转身） | 曲线 | 曲线 | `FRootMotionSource_GGYGOCurve`（Override） |

第二类**不能**用 `GetMaxSpeed()` 实现。速度上限只是上限：玩家松手后 `Acceleration` 归零，`CalcVelocity` 会按 `BrakingDecelerationWalking` 主动制动，上限再高也没有东西驱动位移 —— 刹停动画那 330cm 滑行会整段丢失。而伪造一个假 `Acceleration` 去骗过 `CalcVelocity`，又会与真实输入抢同一个通道。

`ERootMotionAccumulateMode::Override` 的源在场时，引擎在 `PhysWalking` 里**整段跳过** `CalcVelocity`（判据 `CurrentRootMotion.HasOverrideVelocity()`），于是制动不发生、输入彻底不参与位移，而位移仍走 `MoveAlongFloor`，碰撞、斜坡、台阶一个不丢。附带好处：优先级仲裁、状态进 `FSavedMove_Character::SavedRootMotion` 参与预测，都是引擎现成的。

`FRootMotionSource_GGYGOCurve`（`Character/Components/GGYGOCurveRootMotionSource.h`）的要点：

```text
PrepareRootMotion(SimulationTime, MovementTickTime, ...):
    if 离地 or 不是本项目 CMC:  FinishPreservingMomentum(); return
    Speed = CurveMotion.Speed * SpeedScale
    if Speed ~= 0:
        if bEndOnZeroSpeed:  FinishPreservingMomentum(); return   // 刹停
        else: RootMotionParams.Set(零速度); return                 // 转身：压住角色
    Dir = Rotate(BaseYaw) × CurveMotion.Direction
    RootMotionParams.Set(Dir * Speed * (SimulationTime / MovementTickTime))
```

- `RootMotionParams` 的 translation 是**速度**（cm/s），不是本帧位移 —— 引擎在 `AccumulateRootMotionVelocityFromSource` 里直接把它赋给 `Velocity`
- `BaseYaw` 由调用方给，**不能**用基类的 `bInLocalSpace`：那个开关用的是**当前**组件旋转，而曲线分量要的是段起点朝向，转身过程中两者差出角色已转过的角度
- `Duration = -1`（无限），结束时机由 `PrepareRootMotion` 自己或相位机决定。曲线什么时候归零取决于当前播哪个动画，提交时无法预知
- `bEndOnZeroSpeed` 区分两种语义：刹停为 `true`（曲线衰减到 0 即滑行结束，自我退场，`CalcVelocity` 随即恢复，玩家输入自然生效，不需要外部状态机）；转身为 `false`（转身中间那几帧曲线速度确实为 0，退场会让正按着反方向键的玩家把角色推走，所以输出零速度压住，生命周期交相位机）
- **离地必须退场**：`PhysFalling` 与 `PhysWalking` 用同一个判据跳过 `CalcVelocity`，Override 源在空中会连重力一起顶掉，角色沿曲线方向平飘
- **退场帧必须原样输出当前速度**，不能置 `Finished` 就直接返回。引擎的 `FRootMotionSourceGroup::PrepareRootMotion` 遍历所有有效源（不看 `Finished` 也不看 `MarkedForRemoval`），并在调用后无条件置 `bHasOverrideSources`。所以那一帧 Override 照样生效，`RootMotionParams` 空着时 translation 为零 → 水平速度被硬清一帧，踏空时表现为原地竖直下落
- `Settings` 带 `IgnoreZAccumulate`：`PrepareRootMotion` 跑在 phys 函数之前，存在"本帧刚离地、源还没退场"的一帧窗口，不保护 Z 的话重力速度会被曲线的 Z=0 抹掉

**刹停（`GGYGO.CurveBrake`，优先级 10）** 的判据只有一条：无移动输入而曲线仍在给速度。除了 `_End` 这类刹停动画，没有别的动画会在无输入时给出非零速度（站立与静止兜底姿势的 `RootMotion_Speed` 恒为 0），所以不需要记"松手那一帧"的下降沿。有输入就摘掉 —— 刹停可随时被打断。

**禁止 move 合并。** 曲线位移源在场时 `FSavedMove_GGYGO::SetMoveFor` 设 `bForceNoCombine = true`。合并会把角色拉回起点重演一次更长的 move，而曲线速度逐帧变化（走路刹停从 459 一路衰减到 0），重演时只剩最后一帧的曲线值。引擎自己的 `CanCombineWith` 只挡 anim montage 的 root motion 不挡 root motion source，而刹停期间两帧的 `Acceleration` 都是零，恰好落在引擎"允许合并"的分支里。

实测参照（用于判断表现是否正确）：`Walk_End` 滑行约 330cm，2.38s 衰减到 0；`Run_End` 约 447cm，**前 0.167s 就走掉 296cm（66%）**，首帧速度 2087、峰值 4279@f2、单帧最大位移 71cm —— 急停会有明显前冲，那是动画本身的设计。

### 4.4 急停转身

相位：`None` → `Turning`（转角在变）→ `Braking`（已转身、倒滑刹车）→ `RunOut`（方向交回输入）→ 松手结束。前两段合称"曲线接管段"（`IsTurnBackCurveDriven()`）。

**相位边界全部从曲线读出**，不配时间点也不用 AnimNotify：曲线本身带着"什么时候转完、什么时候开始跑出"这个信息，换一版转身动画时边界自动跟着变。用固定秒数或 Notify 会形成与曲线并行的第二份时序，两者迟早漂开。

- 反向输入判定：跑动中 + 输入与前向点积 ≤ 阈值（默认 -0.95，约 162 度以上）
- `Turning` → `Braking`：`|YawTotalDegrees| >= TurnBackMinYawDegrees`（90）**且** `|YawDeltaDegrees| <= TurnBackYawSettleDegrees`（0.05）。两个条件都要 —— 只看差分会把基线尚未建立的那一帧（差分恒为 0）误判成转完
- `Braking` → `RunOut`：`Direction.X <= -TurnBackRunOutForwardThreshold`（0.5）**且** `Speed >= TurnBackRunOutMinSpeed`（150）。速度门限用于避开刹车段末速谷底（Pyrios 是 52 cm/s）的方向噪声
- `RunOut` 段**不读曲线方向**：曲线在那一段给的方向恰好是入口朝向的反方向（等于角色转身后的正前方），玩家改了输入就该跟输入走。方向取输入、朝向交回 `Super::PhysicsRotation`、速度仍用曲线
- `TurnBackDurationSeconds`（3.0）只是兜底：相位推进依赖曲线，动画被打断或没烘焙曲线时相位会卡住，进而 `bTurnBackInputLatched` 永不解闩
- `bTurnBackInputLatched` 保证转身结束后仍按着同一方向键不会立刻再触发（那个方向此时已是角色正前方）。`ResetTurnBack()` 刻意不清它
- 朝向用 `PhysicsRotation` 累加转角增量接管而非外部改 Actor 旋转，绕过 `Super` 就等于这一帧只有曲线在转角色，不必临时关掉自动朝向再恢复
- 网络只同步一个 bit（`FLAG_Custom_2` = 曲线是否在接管）：`Turning` 与 `Braking` 的移动行为一致，`RunOut` 与普通移动一致

**位移与朝向走两条不同的路。** 位移由 `GGYGO.CurveTurnBack` 位移源（优先级 20）承担，`BaseYaw` 传 `TurnBackEntryYaw`、`bEndOnZeroSpeed = false`；朝向仍留在 `PhysicsRotation` 里累加 `RootMotion_Yaw` 的增量。`FRootMotionSource` 只有位移通道没有朝向通道，所以这一层没能统一。

挂/摘由 `UpdateTurnBackRootMotion()` 每帧同步（`IsTurnBackCurveDriven()` 为真则挂，否则摘），放在 `UpdateCharacterStateBeforeMovement` 的本地控制判断**之外** —— `UpdateFromCompressedFlags` 已经在服务器与模拟代理上恢复了相位，不挂源那两端会按玩家输入的方向移动，与本地端分歧。

时机上必须在 `UpdateCharacterStateBeforeMovement` 里挂：引擎在 `PerformMovement` 里的顺序是 `CleanUpInvalidRootMotion` → `UpdateCharacterStateBeforeMovement` → `CurrentRootMotion.PrepareRootMotion` → `StartNewPhysics`，晚一步挂的源要等下一帧才生效。

### 4.5 动画资产的 in-place 化（曲线驱动的前置条件）

`UAnimRootMotionTools::StripRootMotionFromBone`，控制台命令 `ZZZStripRootMotion <MotionBone> <RootBone> <AlignToOrigin 0|1> <DryRun 0|1> <路径...>`。

原资产在 Unity 侧靠 Mecanim 处理整体运动：Animator 从 rootMotionBone 提取位移与转身，姿势里只留局部动作。导出 FBX 时没有这一步 —— 提取前的完整姿势写进 `Bip001`，提取出的 root motion 单独写进外部 Null 节点 `Root`（导入 UE 后成为骨架末尾的一根骨骼）。两者携带同一份位移，所以不处理的话姿势里的整体运动会与移动层的曲线驱动叠加：转身转 360 度、位移走双倍。

工具在骨骼 component 空间做 `NewPose = OldPose * RootMotion.Inverse()`，`RootMotion` 取 `Root` 骨骼**相对首帧**的增量，只保留水平位移与 yaw。

用 `Root` 骨骼而不是 `RootMotion_*` 曲线作为扣除量，是因为两根骨骼在同一套 component 空间里，相减是纯 transform 运算；曲线经过 FBX→UE 轴变换与 ±180 解折叠，拿它去扣骨骼轨道要把那套变换反推回来，而轴向随骨架而变。

坐标系分层（Pyrios 实测，是上面这个选择的依据）：FBX Y-up → UE Z-up 的转换**烘在根骨骼** `Avatar_..._Model` 的 `Roll 90°` 上，`Bone_Root` 恒为单位变换，所以 `Bip001` 的 **local 轴向仍是 FBX 的**（前进落在它的 Z 轴），只有 component 空间才是 UE 轴序（前进落在 Y 轴、高度在 Z）。

两个容易搞错的地方：
- 扣除量必须取**相对首帧的增量**。直接用 component 变换会把首帧那份 `Roll 90°` 一起扣掉，角色躺倒。
- 顺序不能反。`comp * 首帧逆` 是「在首帧局部空间里表达当前姿态」，会把水平位移旋到 Z 轴，随后被去高度步骤清零，扣除量整体变成 0。
- `bAlignToOrigin` 处理两类动画基准不同：走跑循环与转身的首帧本就在原点附近（偏移 1~6cm），而收招类（`Walk_End` / `Run_End`）是「从远处走过来停在原点」，首帧在 -330cm，只做扣除会让整段停在原点后方 3.3 米处。

**本函数不幂等**，重复执行会把同一份 root motion 扣第二次，动画朝反方向漂。已处理的资产要自己记录。

已完成 in-place 化的 7 个 locomotion 动画：`TurnBack`、`Walk_Loop`、`Run_Loop`、`Walk_Start`（这四个 `bAlignToOrigin=0`，首帧偏移本来就只有几厘米）、`Walk_End`、`Run_End`、`Walk_Start_End`（这三个 `bAlignToOrigin=1`）。其余 112 个动画尚未处理。

缺口：Yaw 符号尚未在 PIE 实测。曲线来源、统一采样与消费边界见 [[GGYGO_模块_动画曲线.canvas|动画曲线总览]]。

### 4.6 `_End` 类动画的结构

`Walk_End` 标称 5.6167s，但位移在 2.533s 就结束，之后 3s 是站立姿势；`Run_End` 2.483s 结束；`Walk_Start_End` 只走 0.167s（96% 是静止）。

判据：位移类动画（走跑循环、起步、转身、攻击本体，共 21 个）的「尾巴」恰好是 -0.017s，也就是那一帧末尾重复帧，位移一直走到 clip 末尾；有长尾巴的 50 个全是 `_End` / `Hit` / `Evade` / `ParryAid`，且长度散乱（0.5~4.6s，只有零星同值），不是统一约定。所以长静止段只出现在收招/受击类，是这类动作的固有结构。

这些动画本身就是「短促动作 + 长静止兜底姿势」的结构，留长是为了让状态机自己决定何时切走 —— Unity 那边靠 Animator transition 的 `exitTime` 在中途切走，而导出时 `controllerIsNull=true`，那些时间点丢了。播完只是站着不动，不会错位，所以不是 bug，只是浪费；AnimBP 里可以按「`RootMotion_Speed` 归零」提前转 Idle。

分析脚本：`AAADocs/Scripts/analyze_tails.py`。

### 4.7 走跑 BlendSpace

`BS_Pyrios_WalkRun` 是 **BlendSpace1D**，轴对应 `FZZZAnimStateMemory::GaitBlendY`（0=Walk，1=Run），样本 `Walk_Loop`@0 / `Run_Loop`@1。

选 1D 而不是 2D：Pyrios 只有 `Walk_Loop` / `Run_Loop` 两个移动循环动画，没有侧向或后退的循环，2D 的另一个轴无从填充。ZZZ 的移动方向靠 Actor 转向解决，混合只需要表达速度档位。

BlendSpace 的**默认轴范围是 0..100**，不显式改成 0..1 的话两个样本会挤在轴的最左 1%，混合权重永远停在 Walk。创建脚本 `create_walkrun_blendspace.py` 与轴修正脚本 `fix_blendspace_axis.py` 都在 `AAADocs/Scripts/`。

BlendSpace 自己不做平滑（插值时间 0）：`GaitBlendY` 已由 `FZZZLocomotionEvents::AdvanceGaitBlend` 用 `FInterpConstantTo` 平滑推进，两级平滑串联会让混合明显滞后于实际步态切换。

### 5.1 ABP_Pyrios 的实际拓扑

状态机嵌套 `MainStateMachine → MainGroundState → LocomotionState`，最内层五状态 + 一个 Conduit：

```text
NotMoving ─NotMoving_To_Conduit─┐
Stop ─────Stop_To_Conduit───────┤
                            Conduit
            ┌─Conduit_To_EnterMove─────→ EnterMove
            └─Conduit_To_Moving_Direct─→ Moving
EnterMove ─动画剩余 <= 0.03─→ Moving
EnterMove ─EnterMove_To_Stop─→ Stop
Moving ───Moving_To_Stop────→ Stop
Stop ─────动画剩余 <= 0.5───→ NotMoving

Moving 内层：WalkRun ─WalkRun_To_TurnBack─→ TurnBack
                     ←──动画剩余 <= 0.03──┘
```

七条逻辑过渡由 `FZZZLocomotionDecisions` 提供；三条纯动画时序过渡（EnterMove → Moving、TurnBack → WalkRun、Stop → NotMoving）由 AnimBP 自己用 `Time Remaining (ratio)` 判定。

资产取用：`NotMoving` = `IdleLoop`，`EnterMove` = `WalkStart`，`TurnBack` = `TurnBack`，`Stop` 用 `StateMemory.StopValue` 在 `WalkStartEnd` / `WalkEnd` / `RunEnd` 之间 Select，`WalkRun` 用 `WalkRun` BlendSpace 并由 `StateMemory.GaitBlendY` 驱动它的 **X 轴**。

**BlendSpace1D 的单轴是 X。** 把 `GaitBlendY` 接到 BlendSpacePlayer 的 Y 引脚不会报错，只会表现为「一直播走路、跑不起来」，因为值传不进去。

AnimGraph 顶层在状态机之后还接了一个作用于 `Bip001` 的 `Transform (Modify) Bone`（组件空间、只有 Z 平移 50.802，用于把骨架对齐胶囊体）与一个惯性化节点。两者与 root motion 无关 —— in-place 化只扣水平位移与 yaw，不动高度。

**蓝图实际只读两个成员**：`StateMemory.GaitBlendY` 与 `StateMemory.StopValue`，加上 `GetSeqByKey` / `GetBlendSpaceByKey` 两个查表函数。`AnimBlendX/Y`、`ActualVelocity*`、`AnimCurveVelocity*`、`bTurnBackRunOut` 目前都没有 AnimGraph 节点消费；前两组要等有了侧向/后退循环动画换成二维 BlendSpace 才有去处。

`WalkRun → TurnBack` 只认曲线接管段（`Turning` / `Braking`），**不含 `RunOut`**。把 `RunOut` 算进去的话，AnimBP 靠动画播完切回 WalkRun 之后条件又成立，会立刻退回 TurnBack 从头播，转身动画无限循环直到相位超时。`FZZZLocomotionEvents::SynchronizeMovingSubState` 的投影口径与它保持一致。

反向输入阈值只有移动层一份（`UGGYGOMovementSet::TurnBackReverseInputDotThreshold`）。动画层不存这个配置 —— 存了也不会生效，却看不出来。

`Animation/AnimSyncMarkerTools` 是编辑器离线工具（只写 `AuthoredSyncMarkers`），运行时零引用。之所以要绕到 C++，是因为 `AuthoredSyncMarkers` 未向 Python 反射暴露。root motion 曲线的烘焙在 `AAADocs/Scripts/` 的 Python 管线里。

## 6. `Camera/` —— 相机

| 类 | 职责 |
|---|---|
| `FGGYGOCameraModeView` | 一个模式算出的视角 |
| `UGGYGOCameraMode` | 模式基类，派生类只实现 `UpdateView` |
| `UGGYGOCameraMode_ThirdPerson` | 第三人称跟随 + 穿墙规避 |
| `UGGYGOCameraModeStack` | 模式栈与加权混合 |
| `UGGYGOCameraComponent` | 求值栈、叠加镜头微调、写回 Controller 的控制朝向 |
| `UGGYGOHeroComponent` | 仲裁 PawnData 默认模式与 AbilityCameraMode，并维护按 Ability SpecHandle 标识的覆盖栈 |
| `FGGYGOCameraOffset` | 叠加在求值结果上的镜头微调（位置偏移 + FOV 增量 + 进入/回落时间） |

**为什么用栈**：相机状态是叠加的 —— 锁定期间放大招，结束后应回到锁定而非常规跟随。单个"当前模式"变量表达不了嵌套，调用方只能自己记住"之前是什么模式"，而那份记录会在能力被打断时失效。

**有效模式仲裁与自动恢复**：引擎每次通过 `GetCameraView` 拉取视角，`UGGYGOCameraComponent` 都向 HeroComponent 查询一次“当前有效模式”。有能力接管时返回 `AbilityCameraMode`，否则返回 PawnData 的 `DefaultCameraMode`。能力结束后有效模式自然切回默认模式，模式栈只负责把两者平滑混合，不负责推断能力生命周期。

能力接管带 `FGameplayAbilitySpecHandle` 所有权，并保留所有仍激活的覆盖。后激活的能力位于覆盖栈顶；任意能力结束只移除自己的条目。于是 A 镜头期间临时进入 B，B 结束会恢复仍激活的 A，A 提前结束也不会误清 B。

**引擎集成约束**：ViewTarget 上只能保留一个激活的 CameraComponent。UE 的 `AActor::CalcCamera` 会使用枚举到的第一个激活 CameraComponent；若蓝图里还留着旧 `SpringArm + Camera`，引擎可能绕过整个模式栈。`BP_PC_Pyrios` 已删除旧组件，只保留继承的 `UGGYGOCameraComponent`。

PawnData 尚未到达、模式栈为空时，组件调用 `UCameraComponent::GetCameraView` 使用当前组件视图兜底，不再把默认构造的零坐标写进最终镜头。

`Rotation` 与 `ControlRotation` 分开：前者决定画面看向哪，后者决定"前"是哪个方向。演出镜头因此可以任意摆位而不打乱玩家的方向感。

### 6.1 能力怎么改镜头：按幅度分三层

| 需求 | 用什么 | 配在哪 |
|---|---|---|
| 每段攻击的镜头微调（收 FOV、拉近一点） | `FGGYGOCameraOffset` | `UGGYGOGameplayAbility::CameraOffset`，每个能力一份 |
| 换机位（大招演出、处决特写、锁定） | `UGGYGOCameraMode` 子类 | `UGGYGOGameplayAbility::AbilityCameraMode` |
| 过场动画 | LevelSequence + `SetViewTarget` | 不进相机模式栈 |

**微调为什么不用换模式**：换模式会丢掉当前模式的内部状态（锁定的目标、穿墙规避的臂长恢复进度），
而且模式栈按整份视角混合，连段中反复换模式会让镜头在两份视角之间来回过渡。
微调走独立通道：当前模式照常求值，结果再被偏移一次。于是"重攻击收 5 度 FOV"不需要新建一个类，
十段攻击也就是十份结构体配置。

**微调同一时刻只保留一份**，再次施加直接替换。多份叠加需要引用计数与撤销顺序，
而实际需求是互斥的：两个都要改镜头的能力同时激活时，后者应当覆盖前者而不是两份相加。
alpha 不在替换时归零，从当前强度继续过渡，避免上一份还没回落完就跳变。

**位置偏移在相机局部空间**，同一份配置在角色朝任何方向时观感一致。
FOV 叠加后钳制在 [5, 170]，误填大值会算出 0 或负数让投影矩阵失效。

**换机位与微调可以同时用**：`AbilityCameraMode` 换掉机位，`CameraOffset` 再在那个机位上偏移。

**配置字段与运行时状态必须分开**：`AbilityCameraMode` 是配置，`ActiveCameraMode` 是运行时标记。
`UGGYGOGameplayAbility` 是 `InstancedPerActor`，实例会复用，而 `ClearCameraMode` 要清接管状态 ——
两者共用一个字段时，第一次结束就把配置一起清掉，之后这个能力永远不再接管相机。

两者都在 `ActivateAbility` 里自动应用：配了就生效，不需要每个能力蓝图再写一遍调用。
`EndAbility` 统一撤销，覆盖被组仲裁取消、被死亡取消、Avatar 销毁这些不走正常收尾的路径。

## 7. `Input/` —— 输入

| 类 | 职责 | 要点 |
|---|---|---|
| `UGGYGOInputConfig` | InputTag ↔ InputAction 映射 **[数据][待配]** | 分 Native（直绑 C++，需连续轴值）与 Ability（翻译成 Tag 交 ASC）两组 |
| `UGGYGOInputComponent` | 按 Tag 批量绑定 | 需在 `DefaultInput.ini` 配 `DefaultInputComponentClass`。收集句柄以便换角色时整批解绑 |

查找用 `MatchesTagExact` 而非层级匹配：`InputTag.Look.Mouse` 与 `InputTag.Look.Stick` 需要不同灵敏度处理，宽松匹配会让前者接管后者。

**连段输入缓冲**在 HeroComponent：订阅 ASC 的 `OnAbilityInputRetryable`，被拒的请求存进缓冲，在 `OnAbilityGroupFreed` 时重试。
- 用数组而非单槽位：玩家可能先按普攻再按闪避，两者属不同组、空出时机不同
- 同一 Tag 重复缓冲只刷新时间戳，否则连按三次会在一次组空出时连出三段
- 重试不按 GroupTag 筛选：一个 InputTag 可能对应多个能力分属不同组，意图层无从判断该等哪个组，全部重试由 ASC 仲裁决定

## 9. `Teams/` / `Player/` / `GameModes/`

| 类 | 职责 | 要点 |
|---|---|---|
| `AGGYGOCharacterSlot` | 队伍中一个位置的角色数据宿主 **[核心]** | `AInfo` 派生。持有该角色的 ASC 与 `HealthSet`/`CombatSet`（均为默认子对象），授予 AbilitySet，Pawn 只是它的 Avatar |
| `UGGYGOSquadComponent` | 编队名单、队伍与出战切换 | 挂 PlayerState。持有两层：`Roster`（编队意图，装配前填）与 `Slots`（装配结果，装的是**位置**而非角色）；切人只换 Controller 的附身目标 |
| `UGGYGOSquadPresets` | 玩家存的 N 套编队与出战选择 **[存档]** | `ULocalPlayerSaveGame` 派生。成员存 `FPrimaryAssetId`；编辑接口不自动落盘，由调用方显式保存 |
| `UGGYGOLocalPlayer` | 编队预设的缓存点 | 存在的唯一理由：`LoadOrCreateSaveGameForLocalPlayer` 每次返回新对象，没有缓存会让各调用方互相覆盖 |
| `AGGYGOPlayerState` | 队伍宿主 | 跨越角色死亡与重生而存在 |
| `AGGYGOPlayerController` | 驱动 `ProcessAbilityInput` | `PostProcessInput` 是唯一能保证"本帧输入全部处理完"的时机。另带编队的开发期 Exec 命令 |
| `UGGYGOExperienceDefinition` | 一局的玩法定义 **[数据][待配]** | GameFeature 列表 + **默认编队**（仅在玩家没编成时使用） |
| `AGGYGOGameMode` | 按 Experience 装配 | 接管角色生成，不调 Super 的 `HandleStartingNewPlayer`；装配等 GameFeature 激活完成 |

**待命角色的 GAS 状态不受影响**是队伍制的核心：冷却要继续走、Buff 要继续计时、血量要保留。
这些状态都在位置上而不在 Pawn 上，所以它与 Pawn 的显隐、甚至 Pawn 是否存在都无关 ——
将来改成待命时不生成 Pawn，这条依然成立。

**Slot 的 Owner 必须是 PlayerController**：GAS 的客户端预测靠
`ASC->GetOwnerActor()->GetNetOwningPlayer()` 找到玩家连接。设错时 PredictionKey 生成不出来，
所有 `LocalPredicted` 能力退化为纯服务器执行（输入延迟一个 RTT），**且不报任何错**。

**Slot 用 `bAlwaysRelevant` + `Mixed` 复制模式，不用 `bOnlyRelevantToOwner`**：
相关性是全有或全无的，位置一旦对旁观者不相关，他们连该角色的 Cue 与 Tag 都收不到。
"属性只给自己、GE 与 Cue 给所有人"由复制模式负责，不能用相关性替代。

**编队分三层**：`UGGYGOSquadPresets`（玩家存的 N 套编队 + 出战选择，落盘跨关卡）
→ `Roster`（这一局带谁，出战那套的快照）→ `Slots`（ASC 宿主）。
编成面板只碰最上层，它运行在主菜单，那时没有 World 也没有 PlayerState。

装配取名单按三级回落：已设好的 `Roster`（将来的客户端上报走这里）→
本地玩家存档里的出战编队 → `Experience::SquadMembers`。
保留最后一级是为了让自动化测试和直接起关卡也能跑出可操作角色；全空则报错不生成。

**局内不能改编队**：`SetRoster` 在 `Slots` 非空（已装配）后会被拒绝。位置的属性集是默认子对象，
换角色时旧数值会残留在同一批对象里，而"新角色应该多少血"没有正确答案 ——
保留百分比荒谬，重置满血可以靠反复换人刷治疗。要战斗中换人，正确形态是
每个角色常驻一个位置、编队只是对位置的引用列表，而不是让位置换角色。

**存档存 `FPrimaryAssetId` 而非资产指针**：存指针会让反序列化拉起所有编队里所有角色的
引用链（AbilitySet、动画、相机模式）。代价是 `GGYGOPawnData` 要注册成 PrimaryAssetType，
且 `CookRule=AlwaysCook` —— 存档里的 Id 不是资产引用，没有硬引用链会把角色带进包。

**预设必须缓存在 `UGGYGOLocalPlayer` 上**：`LoadOrCreateSaveGameForLocalPlayer` 每次调用
返回新对象，面板与装配各持一份副本时，一边的存盘会覆盖另一边，症状是
"编好的队不生效"且不报错。缓存点不选 GameInstance（分屏会互相覆盖）也不选
PlayerState（每次切关卡重建）。同 Lyra 把 `ULyraSettingsShared` 挂 `ULyraLocalPlayer`。

**联机的远程玩家目前走默认编队**：编队存在客户端自己的磁盘上，服务器读不到，
需要一条 Server RPC 上报（未实现）。上报只填三级来源里的第一级，位置与 GAS 不用动。

**装配等 GameFeature 激活完成**：`PendingGameFeatureCount` 非零时 `HandleStartingNewPlayer`
不生成队伍，最后一个插件回调归零后补做。否则插件里注入组件、授予能力的 Action
可能晚于角色生成，角色少了内容却不报错。插件列表为空时计数恒为零，路径不变。
加载失败也照常递减放行 —— 一个装不上的插件不该让所有玩家卡在没有角色的状态。

**装配分两阶段**：先为每份 PawnData 建位置（此时属性与能力已就绪），再生成 Pawn 并
`InitializeAbilitySystem(位置的 ASC, 位置)` + `Slot->SetAvatar(Pawn)`。
顺序反过来就回到了"属性集晚于读它的组件"的老问题。

**换人顺序**：先 `UnPossess` 旧的再 `Possess` 新的。反过来会让 `UnPossess` 清掉刚建立的附身关系。

**全员生成在同一出生点**：非出战成员立刻隐藏关碰撞所以重叠无害；分散生成反而有害，切人时角色会从别处瞬移过来。`SpawnCollisionHandling` 用 `AdjustIfPossibleButAlwaysSpawn`，否则第二三个成员会因重叠生成失败。

## 10. 关键约束速查

改动这些地方前先确认影响：

| 约束 | 后果 |
|---|---|
| 同一个 Tag 不能同时在 ini 与原生声明中定义 | 启动时报重复定义 |
| `TMap<Tag, TArray<...>>` 不被 UPROPERTY 反射支持 | 编译失败 |
| 两个头文件不能定义同名 `ATTRIBUTE_ACCESSORS` 宏 | unity build 下重定义（已用 `ifndef` 保护） |
| UHT 不允许两个同名头文件 | 编译失败。新建文件前先确认模块内无同名 |
| 新增文件会改变 unity build 分组 | 可能暴露匿名命名空间重名、缺失的 include |
| Cue 资产必须放 `Content/GameplayCues/` | 放别处不报错但所有 Cue 静默不播 |
| `UGGYGOGameData::Get()` 可能返回 null | 资产未建时依赖它的功能失效 |
| `AGGYGOCharacterSlot` 的 Owner 必须是 PlayerController | 预测键失效，能力退化为纯服务器执行，输入慢一个 RTT，**不报错** |
| Pawn 的 `GetAbilitySystemComponent()` 在位置注入前为 null | 沿用"角色一定有 ASC"的旧假设会空指针 |
| 基础属性集不能同时配在 AbilitySet 与位置上 | 同一 ASC 上两份同类属性集，`GetSet` 返回的与 GE 改的可能不是同一份 |
