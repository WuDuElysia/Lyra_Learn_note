## 1. `System/` —— 全局设施

被所有模块依赖，本身不依赖任何模块。

| 类 | 职责 | 要点 |
|---|---|---|
| `GGYGOGameplayTags` | 全部原生 Tag 的声明与定义 | 用 `UE_DEFINE_GAMEPLAY_TAG` 而非 ini + 字符串查找。同一个 Tag 不能同时在 ini 与原生声明中定义 |

| `UGGYGOAssetManager` | 启动预载及共享资产宿主 **[核心]** | `TryGet()`只返回引擎实际持有实例或空，不创建兜底；`StartInitialLoading`父类索引后预载GameData与三GE，UPROPERTY强引用，逐项状态；getter只读已完成快照、限游戏线程。15A/B完整构建通过，尚无GC/逐项失败等专项实测 |

**为什么 Hero 单独一个类**：HeroComponent 是 InitState 的一个 feature，若每个 AI 敌人都带一个永远等不到 PlayerController 的 feature，`PawnExtension` 的 `DataInitialized` 要等所有 feature 到达 `DataAvailable`，整个角色的初始化链条会卡住，连动画都起不来。

**当前玩家角色的 ASC 不在角色身上**（决策 D1）：ASC 与属性集归队伍位置 `AGGYGOCharacterSlot`，角色只是它的 Avatar。
`GetAbilitySystemComponent()` 转发到 `PawnExtComponent`，**在位置注入之前返回 nullptr**，调用方必须判空。

不共用 PlayerState 上的一个 ASC，是因为一个 ASC 只能挂一套同类 AttributeSet，多角色共用会共享生命值与冷却。
玩家编队也不挂角色自己 —— 那样属性集只能跟着 Pawn 的初始化流程授予，而读属性的 `HealthComponent`
也在同一段流程里初始化，先后顺序变成靠约定维护的东西。放在位置上，属性集随位置构造即就绪。

## 4. 移动层细节

### 4.1 CMC 的关键执行接口

| 扩展点 | 承担 |
|---|---|
| `GetMaxSpeed()` | 速度上限。CMC 自己在 `CalcVelocity` 里用它，加减速、摩擦、坡度、碰撞全部沿用引擎实现 |
| `UpdateCharacterStateBeforeMovement()` | 普通段解算并提交；Stop／TurnBack先暂存原请求候选并挂原曲线源，不预支整帧RMS时间；同Origin物理已结束时仅走剩余clip普通分支、不重挂；回放消费原move派生结果 |
| `CalcVelocity / UpdateVelocityBeforeMovement / ApplyRootMotionToVelocity` | 新请求准入与原生已产生动量分开：无有效来源不得消费Acceleration/RequestedVelocity/未知RMS，但同胶囊的真实物理结果仍按原生制动。覆盖UE物理前直接累加Override入口；有限当前move快照不恢复上帧速度、不删除他人RMS。 |
| `UpdateCharacterStateAfterMovement / StopMovementImmediately` | 物理结束、外部movement委托前保存有限派生结果身份；显式停止、角色/胶囊换代与EndPlay使其失效。该记录不是输入准入、动作状态或第二执行器。 |
| `PrepareLocomotionCurveRootMotion(Source, SimulationTime, MovementTickTime, OutPrepared, OutError)` | 原RMS在原生Prepare内请求；CMC核验原Origin及请求，按实际原生区间求值／提交，返回只读Prepared或明确失败／旧来源退场 |
| `BeginActionMotion(Profile, PlayRate)` / `EndActionMotion(Handle)` | 服务器显式申请/释放独立动作曲线；失败返回 INDEX_NONE，旧Handle不能终止新动作；自然到期由CMC释放门控。第33/34次TimingAndOwnership有限专项已通过，生产资产、碰撞和网络仍待验。 |
| `PhysicsRotation()` | 转身曲线接管段的朝向由 `RootMotion_Yaw` 驱动 |
| `FRootMotionSource_GGYGOCurve` | 动画驱动段（刹停、转身）的位移。Override 模式让引擎整段跳过 `CalcVelocity` |

`GetMaxSpeed()`当前源码优先级：`Restriction.CantMove` → 0；非地面 → 基类；未接受MovementSet、请求失败门禁或无归属曲线地面移动 → 0；显式`bUseCurveDrivenSpeed=false`才取配置固定步态速度；曲线模式的成功来源提供真实Speed×RootMotionScale（ForceWalk只限Walk上界），包括合法零／极小正速／零Scale；曲线模式无成功来源 → 0，不回落固定Walk／Run。C26与第35次有限专项是历史证据；C37已关闭此前固定分支的失败回落。本地RMS实际区间／原move重放六相关源已由统筹核对当前hash与Gate59构建快照一致，该版本统一Editor编译通过；Gate59 Camera叶不是RMS冒烟，首帧／部分／零／追帧及正式移动动态仍未验。

**被禁止移动时返回 0 而不是硬停**：走 `GetMaxSpeed` 这条路，CMC 用自己的制动减速度平滑压到零；`StopMovementImmediately` 会让角色瞬间定住，联机下还会与服务器重演结果不一致。

### 4.2 网络预测

`FSavedMove_GGYGO::SetMoveFor`保存步态、走跑计时、ForceWalk、输入／限制边沿、Run请求、动作段／停止类型、段时间、共循环相位、混合权重、序号和转身入口／相位。普通非RMS段仍按恢复的语义基线求值；曲线RMS另由`PostUpdate`保存原move的只读Input／Prepared派生记录。`PrepMoveFor`在原生`Super::PrepMoveFor`前安装原回放记录，原生调用之后由`UpdateCharacterStateBeforeMovement`消费同一Prepared一次，不能把重放结果写成第二份请求准入／FAILED权威。权威校正的连续时间仍沿用原响应契约，不以旧预测时钟覆盖。

当前`UpdateFromCompressedFlags`只消费ForceWalk输入位；服务器依据同一Acceleration和自身MovementSet推进步态、相位与曲线，不接受客户端指定Profile/速度/时间。`FCharacterNetworkMoveData_GGYGO::ClientFillNetworkMoveData/Serialize`发送动作段、停止类型、转身相位和序号，供`ValidateClientLocomotionHint`发现分歧；它们不是服务器玩法权威。`FCharacterMoveResponseDataContainer_GGYGO`在校正响应中回传权威语义与时间。模拟代理使用复制步态/转身布尔及引擎网络移动，不独立安装本地TurnBack源或累计曲线Yaw。

上述Input／Prepared及Origin仅证明本地原资源接缝；`FRootMotionSource_GGYGOCurve::NetSerialize`载入时清除本地派生Origin／Prepared，不能把导入源冒充原本地请求。现有MoveData已携带v1 `FGGYGOMovementInputSourceCheckpoint`：原绑定/会话/请求/事件与真实释放/中立锚点在`SetMoveFor`捕获，发送只复制原值；运输及后续原Owner/M3生产消费已实施并整链编译；服务端网络执行仍未动态验收。M2又增加v2原Owner nonce/generation运输、ACK/correction原响应及精确Scope通知，已有限静态接受并随Gate69R1编译Succeeded；Gate69私有Notice字段读取失败及既有getter修正留账，编译不证明M2原生同步/网络动态。`GetMovementOwnerSyncScope`/`SubscribeMovementOwnerSync`安装原订阅并同步回放，`UnsubscribeMovementOwnerSync`只退原Observer，包括在途Invalidated；Ready只证明原Owner同步，不能重发Started、补写旧SavedMove或授移动执行。`TryAdmitInitialMovementInputRequest`已有实现，Hero1首次等待消费者已接；只接受原Waiting/绑定/Ready和真实held，不重发Started、不替后继请求准入。既有SavedMove和AuthorityAndMapping只提供有限本地证据，Dedicated Server、多客户端、延迟/丢包、代理及完整预测一致性未验。

### 4.3 曲线驱动

动画资产是Locomotion曲线唯一编辑来源，不另复制成DA。Animation从实际AnimSet解析五单次序列及WalkRun BS样本，发布不可变源绑定；Movement纯数学读取原源曲线并混合，CMC唯一持有步态/相位/时间/请求，RMS仍走原生胶囊物理。CMC不反查当前AnimInstance/AnimSet，也不读取最终AnimGraph混合曲线；现有ABP播放器/可见相位未迁，不承诺姿态与物理同clock。2026-10-05七旧DA已备份删除，默认Set七废弃引用清空/十九参数保持，fresh Registry和Set冷读通过。当前曲线含义与历史附加数据如下：

| 曲线 | 含义 | 用法 |
|---|---|---|
| `RootMotion_Speed` | 该帧速度（cm/s） | 源区间端点速度，按实际播放速率换算；Player相位未迁，不保证无脚滑 |
| `RootMotion_PosX` / `RootMotion_PosY` | 从动画段起点累计的位移（厘米） | 历史Sampler作差分，当前Locomotion源求值不消费 |
| `RootMotion_Dist` | 累计路程，单调不减 | 旧Sampler检测回退；当前CMC用自己的语义段/时钟 |
| `RootMotion_Yaw` | 累计转角（度），已解 ±180 折叠 | 原源[t0,t1]增量与终点累计角，循环跨界解绕 |
| `RootMotion_DirX` / `RootMotion_DirY` | UE局部平面方向 | 原源终点方向/速度；有限非零方向真实归一，混合相消可合法为零，非法方向失败 |
| `Cfg_ClipLength` / `Cfg_LoopTime` | 历史烘焙时长与循环标记 | 旧Sampler消费；当前绑定用实际序列时长/速率及明确Loop，不凭非零信号猜来源 |

数据来源：逐帧值取自各动作 FBX 的外部 `Root` 节点，标量取自 AnimeStudio 导出的 per-clip JSON 的 `muscleClip`，由 `AAADocs/Scripts/` 的 Python 管线烘焙成 FloatCurve。资产上另有 12 条 `Cfg_*` 常量曲线（loopBlend / keepOriginal / mirror 等），运行时暂未消费。

坐标系：轴序就是 **UE 局部空间（X 前、Y 右、Z 上）**，无需转换。但基准是**动画段起点的朝向**而非角色当前朝向 —— 转身时角色已转过 180 度，而位移分量仍以进入动画那一刻的朝向为基准。需要世界方向的消费方要用"进入该段时记录的朝向"换算。

**当前求值链分两支。** 普通段由`UpdateCharacterStateBeforeMovement → TryUpdateLocomotion → EvaluateLocomotionSource/EvaluateWalkRunSource → CommitLocomotionCandidate`；Stop/TurnBack由`StageLocomotionCurveRootMotion`暂存原Input/绑定并挂源，原生CurveRMS把真实SimulationTime交`PrepareLocomotionCurveRootMotion`，CMC按原绑定求值/唯一提交并返回Prepared。非循环钳真实序列范围，循环按周期累计Yaw；纯数学/绑定/RMS不建立第二语义时钟。成功才提交来源，失败锁原请求；TickComponent不调用旧SampleAnimCurves，不需要Sampler前帧基线。

WalkRun使用共循环相位，实际BS权重与各样本/序列速率参与有效周期；分别求原源区间后混合速度/Yaw，时间和回绕只由CMC提交。单源或混合失败不推进、不拿默认或另一Loop替代。RMS仍是终点速度贡献与区间Yaw，不是精确平移积分。SavedMove/Origin/Input保原绑定；authority校正按修正基线重算，不能重用旧Prepared。历史Sampler无当前CMC调用，不把其回退/首帧差分画成现行机制。Gate91原权威回放叶通过；后继Gate101-R2真实Run有限通过，完整网络未验。

历史烘焙分析速度峰值：走跑<1000 cm/s、转身2412，攻击`Attack_Normal_Enhance_03`峰值18724 cm/s；这些不是当前网络速度兜底的授权。根因整改不得用固定速度或MaxCurveDrivenSpeed掩盖缺源。

**两条位移通道。** 曲线消费分成两类，走的路径完全不同：

| 通道 | 谁定方向 | 谁定速度 | 实现 |
|---|---|---|---|
| 输入驱动（走、跑） | 玩家输入 | `GetMaxSpeed()` 返回曲线速度作上限 | `CalcVelocity` |
| 动画驱动（刹停、转身） | 曲线 | 曲线 | `FRootMotionSource_GGYGOCurve`（Override） |

第二类**不能**用 `GetMaxSpeed()` 实现。速度上限只是上限：玩家松手后 `Acceleration` 归零，`CalcVelocity` 会按 `BrakingDecelerationWalking` 主动制动，上限再高也没有东西驱动位移 —— 刹停动画那 330cm 滑行会整段丢失。而伪造一个假 `Acceleration` 去骗过 `CalcVelocity`，又会与真实输入抢同一个通道。

`ERootMotionAccumulateMode::Override` 的源在场时，引擎在 `PhysWalking` 里**整段跳过** `CalcVelocity`（判据 `CurrentRootMotion.HasOverrideVelocity()`），于是制动不发生、输入彻底不参与位移，而位移仍走 `MoveAlongFloor`，碰撞、斜坡、台阶一个不丢。附带好处：优先级仲裁、状态进 `FSavedMove_Character::SavedRootMotion` 参与预测，都是引擎现成的。

`FRootMotionSource_GGYGOCurve`（`Character/Components/GGYGOCurveRootMotionSource.h`）的要点：

```text
PrepareRootMotion(SimulationTime, MovementTickTime, ...):
    核验原Owner是Character的实际CMC，且同传入MoveComponent
    请求原CMC.PrepareLocomotionCurveRootMotion(原Source, 实际区间, ...)
    CMC核验同一Origin引用、绑定／输入请求／执行请求／原MovementSet
    t0 = MotionTimeOrigin + (Source.GetTime() - SourceTimeOrigin)
    t1 = t0 + SimulationTime   // 不钳成整帧；候选成功后由CMC提交
    Prepared.OverrideVelocity = Rotate(BaseYaw) × 终点方向 × 缩放速度
                                × (SimulationTime / MovementTickTime)
    RMS仅消费原Prepared的速度、时间及退场结果
    原失败只失败原请求；旧来源标记退场且不污染后继，不改用默认方向／速度
```

- `RootMotionParams` 的 translation 是**速度**（cm/s），不是本帧位移 —— 引擎在 `AccumulateRootMotionVelocityFromSource` 里直接把它赋给 `Velocity`
- `BaseYaw` 由调用方给，**不能**用基类的 `bInLocalSpace`：那个开关用的是**当前**组件旋转，而曲线分量要的是段起点朝向，转身过程中两者差出角色已转过的角度
- `Duration = -1`（无限），结束时机由原CMC给出的Prepared退场语义或相位机决定；CMC按真实Prepare区间提供派生结果，不取决于AnimInstance播放器或整帧预算样本。
- `bEndOnZeroSpeed` 区分两种语义：刹停为 `true`（曲线衰减到 0 即滑行结束，自我退场，`CalcVelocity` 随即恢复，玩家输入自然生效，不需要外部状态机）；转身为 `false`（转身中间那几帧曲线速度确实为 0，退场会让正按着反方向键的玩家把角色推走，所以输出零速度压住，生命周期交相位机）
- **离地必须退场**：`PhysFalling` 与 `PhysWalking` 用同一个判据跳过 `CalcVelocity`，Override 源在空中会连重力一起顶掉，角色沿曲线方向平飘
- **合法低速结束／离地退场保留当前动量；原失败不能冒充合法退场。** 原生group在Prepare遍历中标记Finished／Removal后，本轮仍可能积累Override；因此不在遍历中移除数组。合法退出消费CMC明确的动量结果；非法原请求清自己的贡献并失败，旧资源只退自己的身份，不影响独立优先级100的ActionMotion。
- `Settings` 带 `IgnoreZAccumulate`：`PrepareRootMotion` 跑在 phys 函数之前，存在"本帧刚离地、源还没退场"的一帧窗口，不保护 Z 的话重力速度会被曲线的 Z=0 抹掉

**刹停（`GGYGO.CurveBrake`，优先级10）**：CMC从原绑定选StartStop/WalkStop/RunStop序列并建立Origin，先挂源，真实Prepare区间才求值；恢复输入或原资源失效时退场。当前原生Prepare只在正模拟区间且原Sample.Speed恰为0时自然结束（缩放前）；微小正值或Scale=0不提前结束，不用`HasUsableSpeed`阈值替代该规则或来源资格。缺方向/非法缩放或世界速度明确失败，不换角色前方或固定速度。Run_End83/99、Walk_End151三个现有DirX.Value已0→1精确保存并冷对照，其余已约定曲线/元信息保持；raw骨键/底层Channel、正式Run/完整网络仍未验。

**禁止有关move合并。** 曲线RMS在场时`FSavedMove_GGYGO::SetMoveFor`置bForceNoCombine；动作段／序号等变化也限制合并。终点速度下，合成长move不等价于原move分别求值／应用。保存的原Input／Prepared是一次move的有身份派生证据，回放只能按原身份消费一次，不是另一份实时准入／失败状态，也不能充当服务端来源证明。实现细节见 [[Movement/结构]]、[[Movement/计划_移动与动作位移#10.3.1 Stop／TurnBack：原资源、实际区间与权威重算]]；统筹静态接受证据`Saved/ValidationRecords/MovementActualInterval_20261003_RootAcceptance.json`。

实测参照（用于判断表现是否正确）：`Walk_End` 滑行约 330cm，2.38s 衰减到 0；`Run_End` 约 447cm，**前 0.167s 就走掉 296cm（66%）**，首帧速度 2087、峰值 4279@f2、单帧最大位移 71cm —— 急停会有明显前冲，那是动画本身的设计。

### 4.4 急停转身

相位：`None` → `Turning`（转角在变）→ `Braking`（已转身、倒滑刹车）→ `RunOut`（方向交回输入）→ 松手结束。前两段合称"曲线接管段"（`IsTurnBackCurveDriven()`）。

正常Turning/Braking/RunOut边界依据Profile累计Yaw、区间增量、方向和速度阈值推进，配置归MovementSet；AnimBP选择表现，不用AnimNotify驱动第二份移动相位机。当前累计时间上限的异常退场行为仍存在，见下列待修项，不能宣称所有阶段都已可靠处理失败。

- 反向输入判定：跑动中 + 输入与前向点积 ≤ 阈值（默认 -0.95，约 162 度以上）
- `Turning` → `Braking`：`|YawTotalDegrees| >= TurnBackMinYawDegrees`（90）**且** `|YawDeltaDegrees| <= TurnBackYawSettleDegrees`（0.05）。累计转身进度与本求值区间增量同时成立，不是旧Sampler的跨帧基线判断。
- `Braking` → `RunOut`：`Direction.X <= -TurnBackRunOutForwardThreshold`（0.5）**且** `Speed >= TurnBackRunOutMinSpeed`（150）。速度门限用于避开刹车段末速谷底（Pyrios 是 52 cm/s）的方向噪声
- `RunOut` 段**不读曲线方向**：曲线在那一段给的方向恰好是入口朝向的反方向（等于角色转身后的正前方），玩家改了输入就该跟输入走。方向取输入、朝向交回 `Super::PhysicsRotation`、速度仍用曲线
- 当前`TurnBackDurationSeconds`（3.0）仍会在超时后ResetTurnBack；不能用它掩盖缺Profile/求值失败。失败传播、明确中止和诊断尚未根治，这个现存行为不等于用户认可业务兜底。
- `bTurnBackInputLatched` 保证转身结束后仍按着同一方向键不会立刻再触发（那个方向此时已是角色正前方）。`ResetTurnBack()` 刻意不清它
- 朝向用 `PhysicsRotation` 累加转角增量接管而非外部改 Actor 旋转，绕过 `Super` 就等于这一帧只有曲线在转角色，不必临时关掉自动朝向再恢复
- 网络语义通过自定义MoveData/校正Response及代理复制传递，服务器自己推进；不能再描述为仅靠FLAG_Custom_2决定权威转身。

**位移与朝向走两条不同的路。** 位移由 `GGYGO.CurveTurnBack` 位移源（优先级 20）承担，`BaseYaw` 传 `TurnBackEntryYaw`、`bEndOnZeroSpeed = false`；朝向仍留在 `PhysicsRotation` 里累加 `RootMotion_Yaw` 的增量。`FRootMotionSource` 只有位移通道没有朝向通道，所以这一层没能统一。

挂/摘由`UpdateTurnBackRootMotion()`在移动前同步；权威端与自主预测端使用自身求值相位，模拟代理直接返回，不自行安装源。`PhysicsRotation`同样只在非模拟代理的曲线接管阶段消费YawDelta；代理朝向由网络移动维护。

时机上必须在 `UpdateCharacterStateBeforeMovement` 里挂：引擎在 `PerformMovement` 里的顺序是 `CleanUpInvalidRootMotion` → `UpdateCharacterStateBeforeMovement` → `CurrentRootMotion.PrepareRootMotion` → `StartNewPhysics`，晚一步挂的源要等下一帧才生效。

### 4.5 动画资产的 in-place 化（曲线驱动的前置条件）

`UAnimRootMotionTools::StripRootMotionFromBone`，控制台命令 `ZZZStripRootMotion <MotionBone> <RootBone> <AlignToOrigin 0|1> <DryRun 0|1> <路径...>`。

原资产在 Unity 侧靠 Mecanim 处理整体运动：Animator 从 rootMotionBone 提取位移与转身，姿势里只留局部动作。导出 FBX 时没有这一步 —— 提取前的完整姿势写进 `Bip001`，提取出的 root motion 单独写进外部 Null 节点 `Root`（导入 UE 后成为骨架末尾的一根骨骼）。两者携带同一份位移，所以不处理的话姿势里的整体运动会与移动层的曲线驱动叠加：转身转 360 度、位移走双倍。

工具在骨骼 component 空间做 `NewPose = OldPose * RootMotion.Inverse()`，`RootMotion` 取 `Root` 骨骼**相对首帧**的增量，只保留水平位移与 yaw。

用 `Root` 骨骼而不是 `RootMotion_*` 曲线作为扣除量，是因为两根骨骼在同一套 component 空间里，相减是纯 transform 运算；曲线经过 FBX→UE 轴变换与 ±180 解折叠，拿它去扣骨骼轨道要把那套变换反推回来，而轴向随骨架而变。

坐标系分层（Pyrios 实测，是上面这个选择的依据）：FBX Y-up → UE Z-up 的转换**烘在根骨骼** `Avatar_..._Model` 的 `Roll 90°` 上，`Bone_Root` 恒为单位变换，所以 `Bip001` 的 **local 轴向仍是 FBX 的**（前进落在它的 Z 轴），只有 component 空间才是 UE 轴序（前进落在 Y 轴、高度在 Z）。

两个容易搞错的地方：
- 扣除量必须取**相对首帧的增量**。直接用 component 变换会把首帧那份 `Roll 90°` 一起扣掉，角色躺倒。
- 顺序不能反。`comp * 首帧逆` 是「在首帧局部空间里表达当前姿态」，会把水平位移旋到 Z 轴，随后被去高度步骤清零，扣除量整体变成 0。
- `bAlignToOrigin` 处理两类动画基准不同：走跑循环与转身的首帧本就在原点附近（偏移 1~6cm），而收招类（`Walk_End` / `Run_End`）是「从远处走过来停在原点」，首帧在 -330cm，只做扣除会让整段停在原点后方 3.3 米处。

**本函数不幂等**，重复执行会把同一份 root motion 扣第二次，动画朝反方向漂。已处理的资产要自己记录。

已完成 in-place 化的 7 个 locomotion 动画：`TurnBack`、`Walk_Loop`、`Run_Loop`、`Walk_Start`（这四个 `bAlignToOrigin=0`，首帧偏移本来就只有几厘米）、`Walk_End`、`Run_End`、`Walk_Start_End`（这三个 `bAlignToOrigin=1`）。其余 112 个动画尚未处理。

缺口：Yaw 符号尚未在 PIE 实测。曲线来源、统一采样与消费边界见 [[GGYGO_流程_动画曲线处理.canvas|动画曲线总览]]。

### 4.6 `_End` 类动画的结构

`Walk_End` 标称 5.6167s，但位移在 2.533s 就结束，之后 3s 是站立姿势；`Run_End` 2.483s 结束；`Walk_Start_End` 只走 0.167s（96% 是静止）。

判据：位移类动画（走跑循环、起步、转身、攻击本体，共 21 个）的「尾巴」恰好是 -0.017s，也就是那一帧末尾重复帧，位移一直走到 clip 末尾；有长尾巴的 50 个全是 `_End` / `Hit` / `Evade` / `ParryAid`，且长度散乱（0.5~4.6s，只有零星同值），不是统一约定。所以长静止段只出现在收招/受击类，是这类动作的固有结构。

这些动画本身就是「短促动作 + 长静止兜底姿势」的结构，留长是为了让状态机自己决定何时切走 —— Unity 那边靠 Animator transition 的 `exitTime` 在中途切走，而导出时 `controllerIsNull=true`，那些时间点丢了。播完只是站着不动，不会错位，所以不是 bug，只是浪费；AnimBP 里可以按「`RootMotion_Speed` 归零」提前转 Idle。

分析脚本：`AAADocs/Scripts/analyze_tails.py`。

### 4.7 走跑 BlendSpace

`BS_Pyrios_WalkRun` 是 **BlendSpace1D**，轴对应 `FZZZAnimStateMemory::GaitBlendY`（0=Walk，1=Run），样本 `Walk_Loop`@0 / `Run_Loop`@1。

成员在蓝图中显示为`Walk Run Blend Alpha`；C++/序列化仍保留`GaitBlendY`，避免已有拆分引脚失效。BlendSpace资产轴显示名`GaitBlendY → WalkRunBlendAlpha`尚未保存迁移，不能写成已修改；旧名字不代表使用Y轴。

当前步态切换链是：CMC持续移动满`MovementSet.WalkToRunHoldSeconds`（默认1.5秒）后写ResolvedGait::Run，`UpdateWalkRunBlend`按MovementSet的速率推进WalkRunBlendAlpha；AnimationStateCapture抓取只读StateFrame，`FZZZLocomotionEvents::MapMovementState`直接复制到旧GaitBlendY，ABP的WalkRun BlendSpacePlayer使用X轴。Animation不再解算目标或推进第二份插值，Run没有独立AnimBP状态。七旧Profile已退役，不再要求配置；Gate101-R2正式End后真实Run/曲线速度与XY位移有限通过，全部表现/网络未验。

选 1D 而不是 2D：Pyrios 只有 `Walk_Loop` / `Run_Loop` 两个移动循环动画，没有侧向或后退的循环，2D 的另一个轴无从填充。ZZZ 的移动方向靠 Actor 转向解决，混合只需要表达速度档位。

BlendSpace 的**默认轴范围是 0..100**，不显式改成 0..1 的话两个样本会挤在轴的最左 1%，混合权重永远停在 Walk。创建脚本 `create_walkrun_blendspace.py` 与轴修正脚本 `fix_blendspace_axis.py` 都在 `AAADocs/Scripts/`。

BlendSpace插值配置应与Movement已有WalkRunBlendAlpha一致；当前C++只在CMC用FInterpConstantTo推进，兼容动画层MapMovementState直接映射。旧AdvanceGaitBlend描述已失效，资产是否仍存在额外平滑须在生产接线时实际回读，不能把源码无第二插值当资产已经正确。

### 5.1 ABP_Pyrios 的实际拓扑

状态机嵌套 `MainStateMachine → MainGroundState → LocomotionState`，最内层五状态 + 一个 Conduit：

```text
NotMoving ─bHasMoveInput────────┐
Stop ─────bHasMoveInput─────────┤
                            Conduit
            ┌─!IsAnimationRunGait──────→ EnterMove
            └─ IsAnimationRunGait──────→ Moving
EnterMove ─动画剩余 <= 0.03─→ Moving
EnterMove ─!bHasMoveInput────→ Stop
Moving ───!bHasMoveInput && !IsTurnBackCurveDriven─→ Stop
Stop ─────动画剩余 <= 0.5───→ NotMoving

Moving 内层：WalkRun ─IsTurnBackCurveDriven─→ TurnBack
                     ←──动画剩余 <= 0.03──┘
```

七条逻辑过渡由 AnimBP 组合语义事实；三条纯动画时序过渡（EnterMove → Moving、TurnBack → WalkRun、Stop → NotMoving）仍由 AnimBP 用 `Time Remaining (ratio)` 判定。C++ 不再知道这些状态名或连线。

`EnterMove`、`Stop`、`TurnBack` 的 Sequence Player 均关闭 `Loop Animation`，只有 Idle 与 WalkRun 循环。否则单次序列回绕可能跨过剩余比例阈值，表现为 CMC 已 Run、混合权重已 1，但仍重复起步动画。

资产取用：`NotMoving` = `IdleLoop`，`EnterMove` = `WalkStart`，`TurnBack` = `TurnBack`，`Stop` 用 `StateMemory.StopValue` 在 `WalkStartEnd` / `WalkEnd` / `RunEnd` 之间 Select，`WalkRun` 用 `WalkRun` BlendSpace 并由 `StateMemory.GaitBlendY` 驱动它的 **X 轴**。

**BlendSpace1D 的单轴是 X。** 把 `GaitBlendY` 接到 BlendSpacePlayer 的 Y 引脚不会报错，只会表现为「一直播走路、跑不起来」，因为值传不进去。

AnimGraph 顶层现为 `MainStateMachine → ActionPoseSlot → LocalToCS → CSToLocal → Inertialization → Root`；旧FullBody Slot与全轴Replace的ModifyBone已移除，不双重校正。节点FullBody、AlwaysUpdateSourcePose=true、Bip001/Root、ComponentAlignment=(0,0,50.802)，Guard RequiredPoseCorrectionSlot=FullBody。它按实际姿态/原生Slot权重对齐Body XY并保留身体Z、消除辅助轨迹重复贡献；胶囊XYZ仍归CMC，不用骨起伏伪造位移。旧固定Z会压平动画，这是替换它的根因。Normal01 Main有限最终姿态采样证明BodyZ起伏31.776cm；End/完整混合未验。

**蓝图实际读取**：过渡图读取 `AnimationState.bHasMoveInput`、`IsAnimationRunGait()`、`IsTurnBackCurveDriven()`；状态图读取 `StateMemory.GaitBlendY`、`StateMemory.StopValue`，以及 `GetSeqByKey` / `GetBlendSpaceByKey` 两个查表函数。`AnimBlendX/Y`、`ActualVelocity*`、`AnimCurveVelocity*`、`bTurnBackRunOut` 目前都没有 AnimGraph 节点消费；前两组要等有了侧向/后退循环动画换成二维 BlendSpace 才有去处。

`WalkRun → TurnBack` 只认 `IsTurnBackCurveDriven()`（`Turning` / `Braking`），**不含 `RunOut`**。把 `RunOut` 算进去的话，AnimBP 靠动画播完切回 WalkRun 之后条件又成立，会立刻退回 TurnBack 从头播，转身动画无限循环直到相位超时。旧 `MovingSubState` 投影已经删除。

反向输入阈值只有移动层一份（`UGGYGOMovementSet::TurnBackReverseInputDotThreshold`）。动画层不存这个配置 —— 存了也不会生效，却看不出来。

`Animation/AnimSyncMarkerTools` 是编辑器离线工具（只写 `AuthoredSyncMarkers`），运行时零引用。之所以要绕到 C++，是因为 `AuthoredSyncMarkers` 未向 Python 反射暴露。root motion 曲线的烘焙在 `AAADocs/Scripts/` 的 Python 管线里。

| `FGGYGOCameraOffset` | 叠加在求值结果上的镜头微调（位置偏移 + FOV 增量 + 进入/回落时间） |

**为什么用栈**：相机状态是叠加的 —— 锁定期间放大招，结束后应回到锁定而非常规跟随。单个"当前模式"变量表达不了嵌套，调用方只能自己记住"之前是什么模式"，而那份记录会在能力被打断时失效。

**有效模式仲裁与自动恢复**：引擎每次通过 `GetCameraView` 拉取视角，`UGGYGOCameraComponent` 都向 HeroComponent 查询一次“当前有效模式”。有能力接管时返回 `AbilityCameraMode`，否则返回 PawnData 的 `DefaultCameraMode`。能力结束后有效模式自然切回默认模式，模式栈只负责把两者平滑混合，不负责推断能力生命周期。

能力接管带 `FGameplayAbilitySpecHandle` 与请求代次，GA保存激活时实际Hero接收者及CameraComponent/token。后激活覆盖在栈顶；结束只清原接收者的匹配请求，不通过当前Avatar寻找新接收者。A结束不误清B，Avatar切换或SurvivesDeath不自动把旧镜头请求重放到新Avatar。PawnExtension的匹配本地缓存清除会广播解绑，即便共享ASC已改Avatar；共享ASC/input/cue/detach仍须当前Avatar身份匹配。Hero正常释放受身份/会话guard约束，EndPlay走自身清理；有限真实解绑测试22 Success不证明Input/IMC重入或全部B6。详见[[Camera/结构|接口与边界]]。

**引擎集成约束**：ViewTarget 上只能保留一个激活的 CameraComponent。UE 的 `AActor::CalcCamera` 会使用枚举到的第一个激活 CameraComponent；若蓝图里还留着旧 `SpringArm + Camera`，引擎可能绕过整个模式栈。`BP_PC_Pyrios` 已删除旧组件，只保留继承的 `UGGYGOCameraComponent`。

当前不再以空模式保留旧栈或调用Super视图掩盖错误。Component `PrepareCameraView`给出明确Result和带原来源的Prepared；Manager核本次ViewTarget/Component并一次`CommitPreparedCameraView`后，才沿原生缓存发布。非法配置明确停止更新，保留最后有效原生画面；首帧非法拒绝启用，修好后须明确重启，不自动恢复。此集成已Gate66/67编译；新Manager首帧、停更重启与Hero/LocalPlayer联合取景仍未动态验证，见[[Camera/结构|接口与边界]]。

`Rotation` 与 `ControlRotation` 分开：前者决定画面看向哪，后者决定"前"是哪个方向。演出镜头因此可以任意摆位而不打乱玩家的方向感。

### 6.1 能力怎么改镜头：按幅度分三层

| 需求 | 用什么 | 配在哪 |
|---|---|---|
| 每段攻击的镜头微调（收 FOV、拉近一点） | `FGGYGOCameraOffset` | `UGGYGOGameplayAbility::CameraOffset`，每个能力一份 |
| 换机位（大招演出、处决特写、锁定） | `UGGYGOCameraMode` 子类 | `UGGYGOGameplayAbility::AbilityCameraMode` |
| 过场动画 | LevelSequence + `SetViewTarget` | 不进相机模式栈 |

**微调为什么不用换模式**：换模式会丢掉当前模式的内部状态（锁定的目标、穿墙规避的臂长恢复进度），
而且模式栈按整份视角混合，连段中反复换模式会让镜头在两份视角之间来回过渡。
微调走独立通道：当前模式照常求值，结果再被偏移一次。于是"重攻击收 5 度 FOV"不需要新建一个类，
十段攻击也就是十份结构体配置。

**微调同一时刻只保留一份**，再次施加直接替换。多份叠加需要引用计数与撤销顺序，
而实际需求是互斥的：两个都要改镜头的能力同时激活时，后者应当覆盖前者而不是两份相加。
alpha不在有效替换时归零，从当前强度继续过渡。05-B5-StrictInput-I已实现非法Offset前置拒绝：XYZ/FOV必须有限、BlendIn/Out还须非负；失败单条可定位Error、返回Invalid，不发号或改变入口旧状态。合法零值/零时间可用，安全碰撞与FOV保护保持。I/T均已根审查冻结并第26次完整构建通过；四Camera叶Success，OffsetOwnership实际44次精确拒绝及入口状态/旧句柄/下一token/合法零值断言通过。耗尽仅静态，GA调用前已主动Clear的自身请求不在Setter原子保持范围；完整Input重入、生产资产/PIE/网络仍未全面证明。

**位置偏移在相机局部空间**，同一份配置在角色朝任何方向时观感一致。
FOV 叠加后钳制在 [5, 170]，误填大值会算出 0 或负数让投影矩阵失效。

**换机位与微调可以同时用**：`AbilityCameraMode` 换掉机位，`CameraOffset` 再在那个机位上偏移。

**配置字段与运行时状态必须分开**：`AbilityCameraMode` 是配置，`ActiveCameraMode` 是运行时标记。
`UGGYGOGameplayAbility` 是 `InstancedPerActor`，实例会复用，而 `ClearCameraMode` 要清接管状态 ——
两者共用一个字段时，第一次结束就把配置一起清掉，之后这个能力永远不再接管相机。

两者都在 `ActivateAbility` 里自动应用：配了就生效，不需要每个能力蓝图再写一遍调用。
受控终止先捕原camera资源，`CleanupAbilityResourcesForTermination`只归还原接收者/token，不按新Avatar清后继；Combo/Boss派生迁移已实现并编译。普通资源收尾有必要冒烟证据，legacy/raw入口、正式镜头资产及极端重入/网络边界仍不能宣称全部通过。

**待命角色的 GAS 状态不受影响**是队伍制的核心：冷却要继续走、Buff 要继续计时、血量要保留。
这些状态都在位置上而不在 Pawn 上，所以它与 Pawn 的显隐、甚至 Pawn 是否存在都无关 ——
将来改成待命时不生成 Pawn，这条依然成立。

**Slot 的 Owner 必须是 PlayerController**：GAS 的客户端预测靠
`ASC->GetOwnerActor()->GetNetOwningPlayer()` 找到玩家连接。设错时 PredictionKey 生成不出来，
所有 `LocalPredicted` 能力退化为纯服务器执行（输入延迟一个 RTT），**且不报任何错**。

**Slot 用 `bAlwaysRelevant` + `Mixed` 复制模式，不用 `bOnlyRelevantToOwner`**：
相关性是全有或全无的，位置一旦对旁观者不相关，他们连该角色的 Cue 与 Tag 都收不到。
ASC的`Mixed`是GameplayEffect信息复制模式，不是属性收件人开关。当前Health/MaxHealth/Poise/MaxPoise按`COND_None`复制，Combat三个基础量按`COND_OwnerOnly`复制，分别由AttributeSet的声明决定；Actor相关性、GE模式和属性条件不能互相替代。这是源码事实，尚不表示网络动态验收通过。

**编队分三层**：`UGGYGOSquadPresets`（玩家存的 N 套编队 + 出战选择，落盘跨关卡）
→ `Roster`（这一局带谁，出战那套的快照）→ `Slots`（ASC 宿主）。
编成面板只碰最上层，它运行在主菜单，那时没有 World 也没有 PlayerState。

装配来源顺序为已设`Roster`→本地预设解析→`Experience::SquadMembers`。仅前项明确正常`Unconfigured`才选择下一配置模式；坏档、非法成员或失效来源明确拒绝，不用Experience掩盖错误。全空报错不生成，客户端名单上报仍未实现。

**局内不能改编队**：`SetRoster` 在 `Slots` 非空（已装配）后会被拒绝。位置的属性集是默认子对象，
换角色时旧数值会残留在同一批对象里，而"新角色应该多少血"没有正确答案 ——
保留百分比荒谬，重置满血可以靠反复换人刷治疗。要战斗中换人，正确形态是
每个角色常驻一个位置、编队只是对位置的引用列表，而不是让位置换角色。

**存档存 `FPrimaryAssetId` 而非资产指针**：存指针会让反序列化拉起所有编队里所有角色的
引用链（AbilitySet、动画、相机模式）。代价是 `GGYGOPawnData` 要注册成 PrimaryAssetType，
且 `CookRule=AlwaysCook` —— 存档里的 Id 不是资产引用，没有硬引用链会把角色带进包。

**预设唯一缓存位于 `UGGYGOLocalPlayer`**：`TryGetSquadPresets(Out, Error)`消费`TryLoadForLocalPlayer`的原来源结果，区分Loaded/CreatedMissing/Invalid；坏档保留并报错，不自动重置。Windows当前单slot政策只允许主本地玩家持久化，次级明确拒绝，不假设UserIndex会隔离磁盘文件。缓存避免面板/装配各持可写副本；来源失效精确清原缓存。实际存档/分屏动态仍未验，见[[Teams/结构|Teams接口]]。

**联机的远程玩家目前走默认编队**：编队存在客户端自己的磁盘上，服务器读不到，
需要一条 Server RPC 上报（未实现）。上报只填三级来源里的第一级，位置与 GAS 不用动。

**GameFeature装配门禁已消费原Session**：`AreGameFeaturesReady`查询原World Session的`IsReadyFor`，必需激活失败明确拒绝装配，pending结清不等于成功。成功转换后的两空列表是显式无GF模式，不是缺依赖兜底。旧`PendingGameFeatureCount`失败递减放行属于已移除的历史实现；当前Loaded/Session/GameMode已统一编译，正式插件动态与生产接线未验，见[[GameFeature/结构|当前链路与缺口]]。

GameFeature当前图文与源码（2026-10-04）：Loaded／GI／Experience／不可变激活URL及原World Session已实施并随Gate68统一Editor编译，N3四图文历史静态证据保留。Session唯一管原Active handle/pending与native返回，GI保跨图Loaded，维持用户选择的只停用、不卸载生命周期；GameMode已消费Session并补Destroyed/EndPlay原资源关闭，Creator已Gate67编译。当前默认配置两列表为空仅证明显式无GF模式，不证明真实插件激活/停用或跨图；正式来源资产、C15及Teams实景仍开放。接口见[[GameFeature/结构]]；普通冒烟不覆盖这些动态，无原生Obsidian UI验收。

**装配分两阶段**：先为每份 PawnData 建位置（此时属性与能力已就绪），再生成 Pawn 并
`Slot->AttachAvatar(Pawn)`；公共宿主内部统一调用 PawnExtension 的
`InitializeAbilitySystem(位置的 ASC, 位置)`，避免装配方和宿主各写一遍绑定。
顺序反过来就回到了"属性集晚于读它的组件"的老问题。

**换人顺序**：先 `UnPossess` 旧的再 `Possess` 新的。反过来会让 `UnPossess` 清掉刚建立的附身关系。

**全员生成在同一出生点**：非出战成员立刻隐藏关碰撞所以重叠无害；分散生成反而有害，切人时角色会从别处瞬移过来。`SpawnCollisionHandling` 用 `AdjustIfPossibleButAlwaysSpawn`，否则第二三个成员会因重叠生成失败。

## 10. 关键约束速查

改动这些地方前先确认影响：

| 约束 | 后果 |
|---|---|
| 同一个 Tag 不能同时在 ini 与原生声明中定义 | 启动时报重复定义 |
| `TMap<Tag, TArray<...>>` 不被 UPROPERTY 反射支持 | 编译失败 |
| 两个头文件不能定义同名 `ATTRIBUTE_ACCESSORS` 宏 | unity build 下重定义（已用 `ifndef` 保护） |
| UHT 不允许两个同名头文件 | 编译失败。新建文件前先确认模块内无同名 |
| 新增文件会改变 unity build 分组 | 可能暴露匿名命名空间重名、缺失的 include |
| Cue 资产必须放 `Content/GameplayCues/` | 放别处不报错但所有 Cue 静默不播 |
| `UGGYGOGameData::Get()` 可能返回 null | 资产未建时依赖它的功能失效 |
| `AGGYGOCharacterSlot` 的 Owner 必须是 PlayerController | 预测键失效，能力退化为纯服务器执行，输入慢一个 RTT，**不报错** |
| Pawn 的 `GetAbilitySystemComponent()` 在位置注入前为 null | 沿用"角色一定有 ASC"的旧假设会空指针 |
| 基础属性集不能同时配在 AbilitySet 与位置上 | 同一 ASC 上两份同类属性集，`GetSet` 返回的与 GE 改的可能不是同一份 |
