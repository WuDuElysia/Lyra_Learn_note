## 0. 已确认的架构决策

这四项已拍板，是后面所有设计的前提，不再作为开放选项讨论。

| # | 决策 | 内容 | 影响 |
|---|---|---|---|
| **D1** | **ASC 挂在队伍位置（Slot）上，不挂 Pawn** | 队伍由 N 个 Slot 组成，每个 Slot 是一个轻量 Actor，持有该位置的 ASC 与独立 AttributeSet；Pawn 只作为 Avatar 承载表现。PlayerState 额外持有一个队伍级 ASC（待有共享属性时再建，见 15.1） | GAS 代码按"Owner=Slot、Avatar=Pawn"写；角色数据与角色实体生命周期解耦，Pawn 可按需生成销毁而不影响属性、冷却、Buff |
| **D2** | **每个玩家各带一支队伍** | 联机时每名玩家拥有自己的完整队伍，队伍机制在联机下不关闭。队伍规模由配置决定，编译期上限固定 | 4 人房 × 3 角色 = 12 个角色 ASC 同时复制，网络与性能预算必须按这个量级设计 |
| **D3** | **移动权威是 CharacterMovementComponent** | 不在 CMC 外面驱动移动；速度、朝向、位移一律走 CMC 的扩展点 | 获得移动复制与客户端预测；代价是所有移动状态都要进 `FSavedMove` 才能正确回放 |
| **D4** | **同优先级 GA 由后来者打断先激活者** | 仲裁比较用 `>` 而不是 `>=` | 同级技能可互断；普攻连段不能靠"同级先到先得"实现，必须靠组规则 `SingleInstanceQueued` |

D1 的落点是**谁持有 ASC 决定了属性集何时就绪**。ASC 挂 Pawn 时，属性集只能在 Pawn
的初始化流程里授予，而 Pawn 上任何想读属性的组件（HealthComponent 是第一个）都在同一段
流程里初始化，两者的先后顺序变成必须靠约定维护的东西——一旦顺序错了，症状是"属性集找不到"
而根因在几百行之外的初始化链上。把 ASC 移到 Slot 之后，属性集在 Slot 构造时就位，
早于任何 Pawn 存在，这个顺序问题在结构上不可能发生。详见 9.2 与 9.3。

D3 的收益与代价都集中在网络上：在 CMC 外面驱动移动的写法在单机下能跑，
但那些写入发生在 `SavedMove` / `NetworkPrediction` 体系之外，服务器重演时拿不到，
位置校正会持续触发。回到 CMC 内部之后，加减速、摩擦、坡度、碰撞全部沿用引擎
已验证的实现，代价是任何影响移动结果的自定义状态都必须显式保存进 SavedMove。

## 1. 三条硬约束

所有设计都被这三条倒推：

| 约束 | 对架构的强制要求 |
|---|---|
| **动作游戏** | 帧级响应、输入缓冲、动作优先级与打断、命中判定窗口。GA 之间必须有可比较的优先级，不能只有二元的独占/非独占。 |
| **队伍多角色**（D1/D2） | 每个角色需要独立的属性、冷却、Buff；下场角色的 GE 必须继续运转；下场角色可由 AIController 接管参战。 |
| **多人联机**（D2） | 所有改变游戏状态的行为必须走 GAS 预测/复制链路，移动必须走 CMC。这是 D3 的直接原因。 |

三条里**多人联机是最强的**。它不是"以后再加"的特性——一旦有逻辑绕过复制链路，后期改造等于重写。

## 2. 分层总览

```
┌─ 输入层        Enhanced Input → InputTag                       [UE 输入框架 + Lyra 照抄]
├─ 意图层        InputTag/原始轴 → 语义意图 + 输入缓冲             [GGYGO 自建，Lyra 无]
├─ 仲裁层        意图 + 优先级 + 组规则 → 允许哪个动作             [GGYGO 扩展 Lyra 激活组]
├─ GAS 层        TryActivateAbility → GA/GE/Cue/Event            [Lyra 照抄 + GGYGO 扩展]
├─ 表现层        Montage / GameplayCue / AnimInstance 自拉        [GGYGO 接线]
└─ 移动层        UGGYGOCharacterMovementComponent (CMC 派生)      [GGYGO 自建]
```

各层的类清单见 [[模块参考]]；层与层之间的依赖方向见 [[GGYGO_模块依赖.canvas]]。

层间铁律：

1. **上层只产出请求，不直接改状态。** 意图层产出"想攻击"，不产出"已攻击"。
2. **状态变更的唯一入口是 GAS。** 除移动输入外，任何改变角色状态的行为都通过 `TryActivateAbility` 或 `ApplyGameplayEffect`。
3. **表现层只读。** AnimBP、Cue、UI 只消费状态，不反向写权威数据。
4. **移动层是唯一例外，权威是 CMC。** Locomotion 不走 GAS（和 Lyra 一致），但必须走 CMC 以获得复制与预测。动作位移走 RootMotion / RootMotionSource，同样由 CMC 应用。
5. **不存在第二个帧调度器。** CMC 自己 Tick、AnimInstance 自己 Update、GAS 自己驱动。不设"唯一角色 Tick 入口"那种需要手工维护顺序的调度器 —— 顺序一旦写在代码里，联机下就会因为各系统到达时机不同而失效。

## 4. 输入层与意图层

### 4.1 Lyra 的事实（已读源码确认）

Lyra 的输入分成**两条完全独立的路**：

```
路 A（动作 → GAS）：
  按键 → UInputAction → ULyraInputConfig 查表 → FGameplayTag(InputTag.*)
       → ULyraInputComponent::BindAbilityActions
       → ULyraHeroComponent::Input_AbilityInputTagPressed(InputTag)    [LyraHeroComponent.cpp:343]
       → ULyraAbilitySystemComponent::AbilityInputTagPressed(InputTag) [:351]
       → 按 Tag 扫描 Spec，缓存 Handle
       → ProcessAbilityInput（每帧）→ TryActivateAbility

路 B（移动/视角 → 不走 GAS）：
  按键 → BindNativeAction(InputTag_Move / Look_Mouse / Look_Stick / Crouch / AutoRun)
       → ULyraHeroComponent::Input_Move / Input_LookMouse ...           [:285-289]
       → 直接 AddMovementInput / AddControllerYawInput
```

**关键结论：Lyra 的移动完全不经过 GAS。** 只有跳跃、开火、交互这类"动作"走 Ability。GGYGO 与此一致（D3）。

两个值得抄的细节：
- `AddAdditionalInputConfig` / `RemoveAdditionalInputConfig`：运行时增删输入配置。**队伍换角色时正好用它换掉整套角色技能键位**。
- `NAME_BindInputsNow`：通过 `UGameFrameworkComponentManager` 广播的扩展事件，GameFeature 插件可以在这个时机注入输入绑定。

### 4.2 意图层：要有，但位置和职责必须收紧

**同意加意图层**，理由是 Lyra 的 `InputTag → Ability` 是一对一硬映射，动作游戏里同一个按键的语义依赖上下文：

- 轻攻击键在地面是普攻、空中是空袭、闪避后是反击
- 长按 0.3 秒变蓄力，连按变连段
- 方向键 + 闪避 = 定向闪避，无方向 = 后跳
- 攻击键在受击硬直窗口内按下，要进输入缓冲而不是丢弃

这些都是"一个物理输入 → 多种语义动作"，用 InputTag 直连表达不了，会退化成在每个 GA 的 `CanActivateAbility` 里塞上下文判断，逻辑分散且无法做输入缓冲。

**但意图层必须严格限制在"解释"，不能碰"执行"：**

| 意图层**可以**做 | 意图层**不可以**做 |
|---|---|
| 读原始输入与输入历史（长按时长、连按次数、方向） | 决定角色实际执行什么动作 |
| 读只读的上下文（CMC 的 MovementMode、ASC 的 Tag） | 修改 ASC 状态、应用 GE、改变属性 |
| 维护输入缓冲队列与有效窗口 | 直接改 Actor 位置或播放动画 |
| 产出结构化的候选动作请求 | 跳过 GAS 自己"执行"这个意图 |
| 把意图翻译成候选 Ability 的 InputTag | 决定最终哪个 Ability 胜出（那是仲裁层的事） |

**意图层的输出只有一件事：一个带优先级的候选动作请求，交给仲裁层，最终仍然通过 `TryActivateAbility` 进 GAS。**

这在联机下是硬要求。GAS 的客户端预测建立在"客户端调 `TryActivateAbility` → 生成 PredictionKey → 服务器验证"这条链上。如果意图层自己决定并执行了动作，就没有 PredictionKey，服务器无法验证，客户端也无法回滚。**意图层只跑在本地、只产出请求。**

### 4.3 落地结构

输入链路分三处，各自的理由不同：

```
Input/
  GGYGOInputConfig                 InputTag ↔ InputAction 映射（数据）
  GGYGOInputComponent              按 Tag 批量绑定，收集句柄以便整批解绑

Character/Components/
  GGYGOHeroComponent               注册 IMC、绑定输入、持有输入缓冲

Player/
  GGYGOPlayerController            在 PostProcessInput 驱动 ASC 消费输入缓存
```

**为什么消费必须由 Controller 做**：ASC 把输入分成 pressed / held / released 三个缓存，
需要有人每帧统一消费。时机必须在**所有** Enhanced Input 事件派发完之后 ——
若在派发中途消费，同帧内后到的按下会被推迟到下一帧，表现为偶发的一帧输入延迟。
`PostProcessInput` 是引擎保证的那个点，而它只存在于 PlayerController 上。

**输入缓冲放在 HeroComponent，没有独立成一层**。理由是：

- 缓冲需要的信息只有「哪个 InputTag 被拒了」和「什么时候拒的」，一个结构体两个字段
- 「该不该重试」的判断依赖组规则，而组规则只有 ASC 知道 ——
  所以由 ASC 广播 `OnAbilityInputRetryable`，缓冲方不反查配置表
- 重试就是重走一遍 `AbilityInputTagPressed`，不需要独立的执行路径

缓冲本身有三个必须做对的细节：用数组而非单槽位（可能先按普攻再按闪避，
两者属不同组、空出时机不同）；同一 Tag 重复缓冲只刷新时间戳（否则连按三次
会在一次组空出时连出三段）；重试不按 GroupTag 筛选（一个 InputTag 可能对应
多个能力分属不同组，缓冲方无从判断该等哪个组，全部重试交 ASC 仲裁）。

独立的意图层要到「一个物理键根据上下文产出不同语义动作」（蓄力、方向普攻、
空中变招）真正出现时才有价值。那时它的形态也应当由那些真实需求决定，
而不是现在先造一套结构等着被填。

**连段的实现**：普攻组配 `SingleInstanceQueued`，第二段在第一段播放中被拒并进缓冲，
第一段结束时 ASC 广播 `OnAbilityGroupFreed`，缓冲立即重试成功。
完整流转见 [[GGYGO_战斗链路.canvas]]。

### 4.4 移动输入

和 Lyra 一致：**移动/视角走 `BindNativeAction`，不进意图层，不进 GAS，直接 `AddMovementInput` / `AddControllerYawInput`。** 意图层只处理动作类输入（攻击、闪避、技能、大招、切人）。

## 5. GA 配置层：优先级 + 激活组 + 组规则

### 5.1 Lyra 的事实与局限

Lyra 有 `ELyraAbilityActivationGroup`，只有三个值：

```cpp
Independent            // 永不阻塞，也不被阻塞
Exclusive_Replaceable  // 可被其他 Exclusive 取消替换
Exclusive_Blocking     // 阻止所有其他 Exclusive 激活
```

判定实现（`LyraAbilitySystemComponent.cpp::IsActivationGroupBlocked`）是按枚举索引的固定数组 `ActivationGroupCounts[3]`，逻辑只有一句：**只要当前有任何 Blocking 能力，就拒绝所有新的 Exclusive**。

局限：

1. **只有一个"独占"概念，没有"组"。** 不能表达"技能之间互斥，但技能和普攻可以共存"。
2. **没有优先级数值。** `Exclusive_Replaceable` 之间是后到者无条件取消先到者——大招会被普攻打断。
3. **策略耦合在 GA 上。** 想改"技能组只能同时一个"这条规则，得改每个技能 GA 的配置。

### 5.2 方案：三个正交维度

| 维度 | 配在哪 | 类型 | 职责 |
|---|---|---|---|
| **组身份** `GroupTag` | GA 资产 | `FGameplayTag` | 这个 GA 属于哪个组。如 `AbilityGroup.Attack` / `.Skill` / `.Ultimate` / `.Dodge` / `.HitReact` |
| **组规则** `GroupRule` | 独立 DataAsset | 枚举 + 参数 | 该组内部的并发规则。**配在组上，不配在 GA 上**——改规则只改一处 |
| **自身策略** `SelfPolicy` + `Priority` | GA 资产 | 枚举 + int32 | 这个 GA 在组规则之上的个体行为，以及冲突时的强弱 |

**组规则**（`EGGYGOAbilityGroupRule`）：

| 值 | 语义 | 典型用途 |
|---|---|---|
| `Coexist` | 组内任意多个可同时激活 | Buff 类、被动 |
| `SingleInstance` | 组内同时只能一个，按优先级决定去留 | 技能组、大招组 |
| `SingleInstanceQueued` | 组内同时只能一个，新请求进缓冲队列而不是取消旧的 | **普攻连段**（等前一段结束再出下一段） |

**自身策略**（`EGGYGOAbilitySelfPolicy`）：

| 值 | 语义 |
|---|---|
| `Coexist` | 不主动排斥任何人，只受组规则约束 |
| `Exclusive` | 激活期间排斥**所有**组的低优先级 GA（不只是同组）。用于大招、死亡、被击倒 |

**优先级** `Priority`（int32，越大越强）。分段留空隙便于插值：

```
死亡 / 强制状态       1000
被击倒 / 强硬直        800
大招                  600
技能                  400
闪避                  300
重攻击                200
轻攻击                100
被动 / Buff             0
```

### 5.3 仲裁算法（含 D4）

把 Lyra 的固定数组换成按组 Tag 索引的实例表：

```cpp
// 取代 Lyra 的 ActivationGroupCounts[3]
TMap<FGameplayTag, TArray<TWeakObjectPtr<UGGYGOGameplayAbility>>> ActiveAbilitiesByGroup;
```

`CanActivateAbility` 阶段（只判断，不改状态）：

1. 取请求 GA 的 `GroupTag` / `Priority` / `SelfPolicy`
2. **全局排斥检查**：遍历所有已激活 GA，若存在 `SelfPolicy == Exclusive` 且 `Priority > 请求者Priority` 的实例 → 拒绝
3. **同组规则检查**：查 `GroupTag` 对应的 `GroupRule`
   - `Coexist` → 通过
   - `SingleInstance` → 若组内已有实例且其 `Priority > 请求者Priority` → 拒绝；否则通过（标记待取消列表）
   - `SingleInstanceQueued` → 若组内已有实例 → 拒绝激活，但把意图压回输入缓冲队列
4. **Tag 关系检查**：交给照抄来的 `GGYGOAbilityTagRelationshipMapping`，处理与组无关的 Tag 级 Block/Cancel

`NotifyAbilityActivated` 阶段（改状态）：

5. 把新实例登记进 `ActiveAbilitiesByGroup`
6. 执行第 3 步标记的取消列表（`CancelAbilityHandle`）
7. 若 `SelfPolicy == Exclusive`，取消所有 `Priority <` 自己的其他组实例

`OnAbilityEnded` 阶段：

8. 从 `ActiveAbilitiesByGroup` 摘除
9. 若该组规则是 `SingleInstanceQueued`，通知输入缓冲队列尝试出队

**D4 的落点在第 2、3 步：比较用 `>` 而不是 `>=`，即同优先级时后来者胜出并打断先激活者。**

这带来一个必须注意的后果：**普攻连段不能靠"同级先到先得"实现了**。第二段普攻如果和第一段同 Priority，会直接打断第一段，动画从头切。两个解法：

- 用 `SingleInstanceQueued` 组规则，让第二段进队列等第一段结束（推荐，语义清晰）
- 或给连段各段递增 Priority（100 / 101 / 102），靠优先级递增实现顺序推进

### 5.4 落地结构

```
AbilitySystem/
  GGYGOAbilitySystemComponent.h/.cpp     组表 + 仲裁实现
  Abilities/
    GGYGOGameplayAbility.h/.cpp          GroupTag / Priority / SelfPolicy 字段
  Groups/                                （新目录）
    GGYGOAbilityGroupConfig.h/.cpp       DataAsset：Map<GroupTag, FGGYGOAbilityGroupRule>
    GGYGOAbilityGroupTypes.h             枚举 + 规则结构体
```

## 6. GE 层

原本认为没有可抄的，实际上有三个值得抄：

1. **`LyraGameplayEffectContext`**：自定义 EffectContext，携带 `AbilitySource` 和命中的物理材质。"打到金属出火花、打到肉出血"就靠这个。
2. **`LyraDamageExecution`**：伤害结算用 `ExecutionCalculation` 而不是简单 Modifier。价值是能同时读源和目标的属性（攻击力 vs 防御力）、能读 EffectContext（命中部位）、能一次算完再写回。动作游戏的伤害公式必然需要。
3. **元属性模式**（`LyraHealthSet` 的 `Damage`/`Healing`）：GE 改的是 `Damage` 元属性，`PostGameplayEffectExecute` 里转换成 `Health` 扣减并清零。伤害可以被拦截、修正、触发事件，而不是直接扣血。GGYGO 的 `UGGYGOHealthSet` 用同样的模式，并多一个 `PoiseDamage` 元属性走韧性。

GGYGO 需要的 GE 分类（都是编辑器里的蓝图资产，代码侧只提供 Execution 与 Tag）：

| 分类 | 用途 | 归属 |
|---|---|---|
| 伤害 / 治疗 | 走 `GGYGODamageExecution`，用 `SetByCaller` 传数值 | `UGGYGOGameData`（15.4） |
| 硬直 / 受击 | 施加 `Restriction.*` Tag + 持续时间，动作游戏的核心 | 施加它的能力 |
| 削韧 / 破防 | 韧性属性的消耗与恢复 | 施加它的能力 |
| 冷却 | GAS 原生的 `CooldownGameplayEffectClass` | 能力自己 |
| 无敌帧 | 闪避的 i-frame，`Restriction.ImmuneDamage` | 闪避能力 |

**不做全局 GE 注册表**（一个集中保存所有 GE 软引用路径、启动时同步加载的命名空间）。
路径拼错只能在运行时发现、引用关系在编辑器的资产引用图里不可见、
全局可变变量无法按玩法模式差异化、启动时同步加载全部 GE 会拖慢启动。
共享的那几个 GE 走 `UGGYGOGameData` 资产（15.4），其余归属施加它们的能力。

## 7. GameplayEvent 层

直接照抄。GAS 原生的 `SendGameplayEventToActor` + `AbilityTask_WaitGameplayEvent` + `FGameplayEventData` 已经够用，Lyra 没有做额外封装。

动作游戏要额外接的两处：

1. **AnimNotify → GameplayEvent**：动画帧上的判定窗口、连段窗口、可取消点，用 AnimNotify 发 GameplayEvent，GA 内用 `WaitGameplayEvent` 接。这是动作游戏最常用的模式。动作类 Notify 一律走这条路，不要让 AnimInstance 直连调用逻辑层的具体类型——那样动画层就成了逻辑层的上游，且被调用方换实现时动画层要跟着改。
2. **命中 → GameplayEvent**：命中判定组件检测到命中后发事件，GA 决定要不要应用伤害 GE。

`GameplayMessageRuntime`（已在 `GGYGO.Build.cs` 声明）和 GameplayEvent 是两个不同东西：

| | GameplayEvent | GameplayMessage |
|---|---|---|
| 目标 | 特定 Actor 的 ASC | 全局广播，无目标 |
| 用途 | 驱动 Ability 逻辑 | 通知 UI / 音频 / 成就等旁观者 |
| 载荷 | `FGameplayEventData`（固定结构） | 任意 USTRUCT |

## 8. 表现层：GA 激活后怎么播动画和特效

### 8.1 事实澄清

**Lyra 确实没有专门的"GA 表现类"**，表现分散在三处：

1. GA 内部直接用 `AbilityTask_PlayMontageAndWait` 播 Montage
2. GE/GA 触发 `GameplayCue.*` Tag，由 `GameplayCueNotify` 处理特效音效
3. `LyraGameplayCueManager` 只负责 Cue 资源的异步/预加载优化，**不含任何 Cue 执行逻辑**，执行全在 GAS 原生

"GameplayCue"这个猜测是对的，它就是 GAS 的表现层机制。

### 8.2 三条表现通道

| 通道 | 机制 | 适用 | 联机行为 |
|---|---|---|---|
| **A. Montage** | GA 内 `PlayMontageAndWait` | 有独立完整动画的动作：攻击、闪避、技能 | Montage 由 GAS 复制（`NetExecutionPolicy` 决定），本地预测播放 |
| **B. GameplayCue** | Tag 触发 `GameplayCueNotify_Static`（一次性）/ `GameplayCueNotify_Actor`（持续） | 特效、音效、屏幕震动、命中反馈 | Cue 自带复制与本地预测 |
| **C. AnimInstance 自拉** | AnimInstance 在 `NativeUpdateAnimation` 里读 CMC + ASC，写自己的动画参数 | 需要和移动混合的表现：受击姿态、武器待机、上下半身分层 | 依赖 CMC / ASC 自身的复制 |

### 8.3 ZZZAnim 走通道 C

动画层采用"AnimInstance 自拉"模式：

```
UZZZAnimInstance::NativeUpdateAnimation
  └─ FZZZAnimSnapshotCapture::Capture
       └─ 读 UGGYGOCharacterMovementComponent：
            步态、移动意图、实际速度派生量、曲线运动量、转身相位、是否在地面
       → FZZZAnimSnapshot → ZZZ AnimBP 消费
```

`FZZZAnimSnapshotCapture` 是动画层与移动层之间的**唯一**读取点。
所有跨层取值收敛在一个文件里，于是"动画依赖了移动层的什么"只需看一处。

为什么要快照而不是让 AnimBP 直接读 CMC：AnimBP 的过渡条件可能在 worker 线程上
求值，而移动状态在游戏线程被改写，直接读有数据竞争。快照把读取时机收敛到
游戏线程的一个点，整帧内所有判定看到同一份值 —— 这也保证了同一帧里
多个过渡条件不会基于不同时刻的状态做出互相矛盾的决定。

单向只读的铁律：AnimInstance 不反向写 CMC 或 ASC 的权威数据。
唯一的反向通道是 AnimNotify（如 `CanYaw`），它只发事件、不写状态，
由移动层自己决定如何响应。

### 8.4 表现层的框架文件

```
AbilitySystem/
  Cues/
    GGYGOGameplayCueManager.h/.cpp              Cue 的加载策略
    GGYGOGameplayCueNotify_HitImpact.h/.cpp     命中反馈，按表面分流
  Tasks/
    GGYGOAbilityTask_PlayMontageAndWaitForEvent.h/.cpp
```

**`PlayMontageAndWaitForEvent` 合成一个 Task，而不是把 `PlayMontageAndWait` 与
`WaitGameplayEvent` 并联**：并联时 Montage 被打断后事件监听仍然活着，
会接到下一个动画发出的同名事件，于是"上一段攻击的判定窗口"在新动作里被打开。
合成一个之后，Montage 结束即取消监听。

**命中 Cue 按表面在一个 Cue 内部分流，而不是每种表面一个 Cue Tag**：
命中的表面来自 `FGGYGOGameplayEffectContext` 里的物理材质，
分流表配在资产上（更具体的表面排在前面，`DefaultEffect` 兜底）。
每种表面一个 Tag 的话，攻击能力就要自己判断打到了什么再选 Tag，
而它并不知道命中的物理材质——那是伤害 GE 的上下文。

**Cue 的加载策略**（`GGYGOGameplayCueManager`）：
同步加载恒关（宁可这一次不播特效也不卡帧）、Dedicated Server 完全跳过、
按 PawnData 的 `CuesToPreload` 预热。不预热的后果是第一次触发时资产还没就位。

## 9. 整体架构：Owner / Avatar 与队伍多角色（D1 / D2）

### 9.1 Lyra 的事实

Lyra 有两套布局：

**布局 1（玩家角色，默认）：ASC 挂 PlayerState**

```
ALyraPlayerState                     ← ASC 的 Owner
  ├─ ULyraAbilitySystemComponent     ← ASC 本体（LyraPlayerState.h:153）
  ├─ ULyraHealthSet / CombatSet
  └─ PawnData (Replicated)
        │ InitAbilityActorInfo(Owner=PlayerState, Avatar=Pawn)
        ▼
ALyraCharacter                       ← Avatar，GetAbilitySystemComponent() 转发到 PlayerState
  ├─ ULyraPawnExtensionComponent     ← InitState 状态机协调初始化顺序
  ├─ ULyraHeroComponent              ← 输入绑定、相机
  └─ ULyraHealthComponent            ← 把 HealthSet 包成组件 API
```

**布局 2（AI/NPC）：ASC 挂 Pawn 自身**

`ALyraCharacterWithAbilities` 自己持有 ASC + HealthSet + CombatSet，`PostInitializeComponents` 里自行 `InitAbilityActorInfo(this, this)`。

### 9.2 为什么布局 1 在 GGYGO 不成立

一个 ASC 只能挂**一套**同类型 AttributeSet。三个角色共用 PlayerState 上的一个 ASC，就是共享同一份 HP、同一份技能冷却——这不是绝区零，是换皮不换数据。

绝区零/原神的实际模型是：**每个角色有独立的 HP、能量、技能冷却、Buff，下场后继续走冷却和回能**。这要求每个角色一套独立的属性和 Ability 状态。

但"每个角色一套"不等于"ASC 必须挂 Pawn"。这两件事被混为一谈会带来 9.3 要解决的时序问题。

Lyra 两套布局的**属性集来路完全不同**，这是照抄时最容易漏掉的一点：

| Lyra 布局 | ASC 宿主 | AttributeSet 从哪来 | 为什么能这样 |
|---|---|---|---|
| 布局 1（`ALyraCharacter`，默认） | PlayerState | `ALyraPlayerState::SetPawnData` 里由 AbilitySet 授予 | PlayerState 先于 Pawn 存在。GameMode 在 Experience 就绪后设 PawnData 并授予，**之后**才生成 Pawn，所以 Pawn 上的 HealthComponent 初始化时属性集必然已在 |
| 布局 2（`ALyraCharacterWithAbilities`） | Pawn 自己 | **角色构造函数里的 `CreateDefaultSubobject`**，不走授予 | 默认子对象在 `InitializeComponent` 阶段被 ASC 自动发现，早于任何 InitState 阶段 |

布局 2 的源码注释把机制说得很直接：

```cpp
// These attribute sets will be detected by AbilitySystemComponent::InitializeComponent.
HealthSet = CreateDefaultSubobject<ULyraHealthSet>(TEXT("HealthSet"));
CombatSet = CreateDefaultSubobject<ULyraCombatSet>(TEXT("CombatSet"));
```

也就是说：**Lyra 在任何布局下都保证"属性集就绪早于读属性的组件初始化"**，只是两种布局靠不同机制达成。
如果采用布局 2 的 ASC 归属，却沿用布局 1 的授予方式，就得到一个两边优势都没有的组合——
属性集晚于 ASC 就绪，而又没有 PlayerState 那样的天然先后关系兜底。

### 9.3 D1 采纳的布局：Slot 持有 ASC 的三层结构

问题的实质不是"ASC 挂哪"，而是**ASC 的生命周期挂在谁身上**。挂 Pawn 意味着属性集的就绪时机
被 Pawn 的初始化流程牵制；而 Pawn 是三层里最"短命"也最复杂的一层（要生成 Mesh、CMC、AnimBP、
等 Controller）。把 ASC 上移一层，交给一个只承载数据的 Slot：

```
AGGYGOPlayerState                     ← 玩家级
  ├─ UGGYGOSquadComponent             ← 名单与出战索引
  ├─ UGGYGOAbilitySystemComponent     ← 队伍级 ASC（共享资源，待需求，见 15.1）
  └─ Slots[N]                         ← 持有各位置的 Slot 引用

AGGYGOCharacterSlot（AInfo 派生，无 Mesh、无碰撞、不 Tick）   ← 角色数据层
  ├─ UGGYGOAbilitySystemComponent     ← 该位置的 ASC（Owner=Slot，Avatar=Pawn）
  ├─ UGGYGOHealthSet / CombatSet      ← 构造函数子对象，随 Slot 一同就绪
  └─ PawnData 引用                     ← 这个位置装的是哪个角色

AGGYGOHeroCharacter（Pawn）                                  ← 角色表现层
  ├─ UGGYGOPawnExtensionComponent     ← 协调；ASC 从 Slot 注入而非自己创建
  ├─ UGGYGOCharacterMovementComponent / Mesh / AnimBP
  ├─ UGGYGOHealthComponent            ← 读 Slot 的 HealthSet
  └─ UGGYGOHeroComponent              ← 仅出战角色：输入绑定、相机
```

参考对象仍是 `ALyraCharacterWithAbilities` 的**属性集子对象化**做法，但宿主从 Pawn 换成 Slot。
Slot 用 `AInfo` 派生，可参考 Lyra `Teams/LyraTeamInfoBase` 的复制设置。

这个结构带来四个直接结果：

1. **时序问题在结构上消失。** 属性集是 Slot 的默认子对象，Slot 创建完成即就绪。
   Pawn 上的 HealthComponent 无论在哪个阶段初始化，都不可能"找不到 HealthSet"。
2. **Pawn 可以按需生成销毁。** 下场角色不必常驻带 Mesh 的 Pawn，而 GE 计时、冷却、回能
   继续在 Slot 的 ASC 上跑。这才是 9.4 里那条"轻量角色状态容器"的正解，
   而它同时也是性能优化。
3. **死亡与重生不牵动 GAS 状态。** Pawn 销毁只是失去 Avatar，Slot 的属性与 Buff 仍在。
4. **切人退化为换 Avatar。** 不需要在角色之间搬运 ASC，只需重设 Avatar 与附身关系。

代价是多了一层实体和一次 `InitAbilityActorInfo` 的重设时机，以及下面四条必须处理对的约束。

**约束 1：预测的 Owner 链必须能追到 PlayerController。**
GAS 的客户端预测依赖 `ASC->GetOwnerActor()->GetNetOwningPlayer()`。Slot 的 `SetOwner()`
必须指向 PlayerController（或已被 PlayerController 拥有的 PlayerState）。设错的症状是
PredictionKey 生成不出来、所有 `LocalPredicted` 能力静默退化为纯服务器执行，
表现为输入延迟一个 RTT，**且不产生任何错误日志**。这是本方案最容易翻车的一处。

**约束 2：Avatar 可能为空，能力要能识别这件事。**
Pawn 按需生成时 Slot 的 Avatar 为 null。纯数值 GE（冷却、回能、Buff 计时）不受影响，
但 Montage、位移、Cue、`MeleeTraceComponent` 全都依赖 Avatar。
统一在 `UGGYGOGameplayAbility::CanActivateAbility` 加一条"本能力需要 Avatar"的前置检查，
不要让每个能力各自判空——那等于把同一个前提复制 N 份。

**约束 3：切 Avatar 时必须重设 ActorInfo 并解绑旧 Pawn。**
`ASC->InitAbilityActorInfo(Slot, NewPawn)`，同时旧 Pawn 的 `PawnExtensionComponent`
要 `UninitializeAbilitySystem`，否则旧 Pawn 仍被当作 Avatar。

**约束 4：用复制模式区分收件人，不要用相关性。**
Slot 设 `bAlwaysRelevant`，ASC 用 `Mixed` 复制模式，和 Lyra 的 PlayerState 一致。

直觉上会想给 Slot 设 `bOnlyRelevantToOwner` —— "别人不需要我队伍的属性明细"。
**这是错的**：相关性是全有或全无的，Actor 一旦对某个客户端不相关，
它身上的 ASC 就整体收不到，于是别人也看不到你角色的 GameplayCue 与 GameplayTag，
命中特效、状态表现全部消失。

"属性只给自己、GE 与 Cue 给所有人"这件事正是 `Mixed` 模式的职责，
它在同一个相关的 Actor 上按内容类型分发。相关性控制的是"能不能看见这个 Actor"，
两者不能互相替代。Slot 是不复制 Transform 的轻量 Actor，
`bAlwaysRelevant` 的成本远低于丢失旁观者表现的代价。

跨级查询规则：角色 Ability 需要读队伍资源时，通过 Slot 的 Owner 链拿到 PlayerState 上的
队伍 ASC，不要把队伍属性复制进角色 AttributeSet。

**队伍规模可配置。** Slot 数量由队伍配置决定，当前内容规模是 3，不写死。
但保留一个编译期上限常量（`GGYGO_MAX_SQUAD_SIZE`）用于复制数组预分配与配置校验——
运行时长度可变，上限固定，避免配置错误把 12 个 ASC 变成几十个。

### 9.4 D2 的网络预算

每个玩家各带一支队伍，意味着：

| 项 | 4 人房 × 每队 3 角色 |
|---|---|
| Slot（含角色 ASC） | 12 |
| 队伍 ASC | 4 |
| 常驻角色 Pawn | 4（仅出战）～12（全常驻），由 Pawn 生成策略决定 |

Slot 是轻量 Actor，12 个 Slot 的开销与 12 个带 Mesh 的 Pawn 不在一个量级。
Pawn 的生成策略因此成为一个**可调项而非架构约束**：先按全常驻做（切人零延迟），
压力测试后若需要，改成仅出战角色持有 Pawn，Slot 侧不用改。

这个量级下必须做的事：

1. **下场角色降低复制频率。** 下场 Slot 用 `NetUpdateFrequency` 降频或 `NetDormancy` 休眠；但 GE 计时不能停（冷却、回能要继续），所以是"降低复制"而不是"停止模拟"。
2. **AttributeSet 复制模式。** GAS 的 `ReplicationMode` 三选：`Full`（单机/所有属性给所有人）、`Mixed`（属性只给所属客户端，GE 给所有人，玩家角色用这个）、`Minimal`（只给 GameplayTag 和 Cue，AI 用这个）。**队伍角色用 `Mixed`，敌人 AI 用 `Minimal`**。
3. **Slot 保持 `bAlwaysRelevant`，靠 `Mixed` 模式限制属性的收件人。** 不要用相关性来省流量，理由见 9.3 约束 4：Slot 一旦对旁观者不相关，他们连你的 Cue 与 Tag 都收不到。Slot 不复制 Transform，本身的常驻开销很小。

出现"给整支队伍或全场角色广播 Buff"的需求时，照抄 Lyra 的 `LyraGlobalAbilitySystem`
（一个 WorldSubsystem，登记所有 ASC 并统一施加/移除），不要手写遍历。

### 9.5 切换角色的流程

```
1. 输入触发切人 → UGGYGOSquadComponent::SetActiveSlot     ← 服务器权威
2. Controller UnPossess 旧 Pawn → Possess 新 Pawn
3. 旧 Pawn 隐藏并关碰撞；新 Pawn 显形（若采用按需生成，则此处生成新 Pawn）
4. 新 Slot 的 ASC 重设 Avatar：InitAbilityActorInfo(NewSlot, NewPawn)
5. HeroComponent 随新 Avatar 生效，输入配置换成新角色的键位
6. 相机目标切换（CameraComponent 跟随新 Avatar）
7. 待命 Slot 的 ASC 完全不动 —— 冷却继续走、Buff 继续计时、血量保留
```

第 7 步是队伍制成立的前提，而 Slot 结构让它变成默认行为而不是需要保护的特例：
待命角色的 GAS 状态在 Slot 上，与 Pawn 的显隐甚至存在与否都无关。

**顺序必须先 `UnPossess` 再 `Possess`**。反过来的话，`UnPossess` 旧角色时
会把刚建立的附身关系一起清掉。

**`Possess` 只能在服务器执行**，客户端只能预测表现层（相机、UI），不能预测控制权转移。
切人的输入响应延迟因此至少是一个 RTT，需要用表现（切人特效、镜头推进）盖住。

**全员常驻时生成在同一个出生点**：非出战成员立刻隐藏关碰撞，重叠无害；
分散生成反而有害——切人时角色会从别处瞬移过来。
`SpawnCollisionHandling` 必须用 `AdjustIfPossibleButAlwaysSpawn`，
否则第二、三个成员会因重叠而生成失败。改为按需生成后这条约束自然消失。

把切人做成一个走 GAS 的 GA（可被打断、有 CD、消耗切人能量）是后续的事，
前提是队伍级 ASC 存在（D1，见 15.1）。现在切人是组件上的直接调用，没有冷却与消耗。

### 9.6 从"ASC 挂 Pawn"迁移到 Slot 的改动清单

改动按依赖顺序排列，每一步都应能独立编译，便于出错时定位。

**第 1 步：新增 Slot 类型（纯新增，不影响现有代码）**

```
Teams/
  GGYGOCharacterSlot.h/.cpp      AInfo 派生。持有 ASC、HealthSet、CombatSet、PawnData 引用
  GGYGOSquadTypes.h              GGYGO_MAX_SQUAD_SIZE 常量
```

Slot 构造函数里做三件事，顺序不重要但都必须是 `CreateDefaultSubobject`：
ASC、`UGGYGOHealthSet`、`UGGYGOCombatSet`。ASC 的 `ReplicationMode` 设 `Mixed`。
类上设 `bReplicates = true`、`bOnlyRelevantToOwner = true`、关掉 Tick。
实现 `IAbilitySystemInterface::GetAbilitySystemComponent` 返回自己的 ASC。

Slot 需要一个 `InitializeForPawnData(const UGGYGOPawnData*)` 与
`SetAvatar(APawn*)`：后者内部调 `InitAbilityActorInfo(this, NewAvatar)`，
是约束 3 的唯一落点，不要让调用方各自去调 `InitAbilityActorInfo`。

**第 2 步：`AGGYGOCharacterBase` 交出 ASC 所有权**

| 位置 | 现在 | 改为 |
|---|---|---|
| 构造函数 | `AbilitySystemComponent = CreateDefaultSubobject<...>` | 删除。Pawn 不再创建 ASC |
| 成员 `AbilitySystemComponent` | `TObjectPtr<UGGYGOAbilitySystemComponent>` | 删除，避免出现两个真值来源 |
| `GetGGYGOAbilitySystemComponent()` | 返回自己的成员 | 转发到 `PawnExtComponent->GetGGYGOAbilitySystemComponent()` |
| `GetAbilitySystemComponent()` | 同上 | 同上 |

**这是一处行为变化，必须记住**：改造前 Pawn 一构造出来就有 ASC；改造后在 Slot 注入之前
返回 nullptr。所有 `GetAbilitySystemComponent()` 的调用点都要判空，
不能再假设它非空。`check(ASC)` 这类断言要改成早退。

**第 3 步：属性集不再经 AbilitySet 授予**

`UGGYGOPawnExtensionComponent::GrantAbilitySets` 保留，但 `UGGYGOAbilitySet` 的
`GrantedAttributes` 不再承载 `HealthSet` / `CombatSet` —— 它们现在是 Slot 的子对象。
字段本身保留：将来某个角色专属的 AttributeSet 仍可能走授予。

相应地 `AGGYGOCharacterBase::OnAbilitySystemInitialized` 里
`HealthComponent->InitializeWithAbilitySystem` 的那段注释要改——
它现在依赖的不再是"AbilitySet 在 DataInitialized 授予"，而是"Slot 构造即就绪"。

`UGGYGOHealthComponent::InitializeWithAbilitySystem` 里找不到 HealthSet 时
把 `AbilitySystemComponent` 置回 nullptr 的那行要删掉。那行的意图是"绑定失败就回滚"，
实际效果是把失败变成静默可重入状态，掩盖了失败本身（Lyra 的版本不这么做）。
属性集就绪问题从结构上解决后，这里应当是硬错误。

**第 4 步：`UGGYGOSquadComponent` 从持有角色改为持有 Slot**

| 现在 | 改为 |
|---|---|
| `TArray<TObjectPtr<AGGYGOCharacterBase>> Members` | `TArray<TObjectPtr<AGGYGOCharacterSlot>> Slots` |
| `RegisterMember(AGGYGOCharacterBase*)` | `RegisterSlot(AGGYGOCharacterSlot*)` |
| `ActiveMemberIndex` | `ActiveSlotIndex`（语义不变，仍复制序号而非指针） |
| `ActivateMember` / `DeactivateMember` | 操作 Slot 的 Avatar 与 Pawn 显隐 |
| `CanMemberBeActive` | 查 Slot 的死亡状态，而不是 Pawn |

`GetActiveCharacter()` 保留（UI 与相机要 Pawn），实现改为 `Slots[Index]->GetAvatarPawn()`。

**第 5 步：`AGGYGOGameMode::SpawnSquadForPlayer` 改为两阶段**

现在是"遍历 `Experience->SquadMembers` → 生成 Pawn → `SetPawnData` → `RegisterMember`"。
改为：

```
1. 遍历 SquadMembers，为每个 PawnData 生成一个 Slot
     SpawnActor<AGGYGOCharacterSlot>，Owner 设为 PlayerController   ← 约束 1
     Slot->InitializeForPawnData(PawnData)
     SquadComponent->RegisterSlot(Slot)
2. 按 Pawn 生成策略生成 Pawn（当前：全员生成）
     SpawnActor<AGGYGOCharacterBase>
     PawnExtComp->SetPawnData(PawnData)
     PawnExtComp->InitializeAbilitySystem(Slot 的 ASC, Slot)         ← Owner=Slot
     Slot->SetAvatar(Pawn)
3. 出战第一个 Slot，Controller 附身它的 Pawn
```

第 1 步与第 2 步之间是 Slot 结构的价值所在：属性集在阶段 1 结束时已全部就绪，
阶段 2 无论如何排序都不会踩到时序问题。

`InitializeAbilitySystem` 的第二个参数传 Slot 而不是 Pawn —— 这个参数一直存在，
`GGYGOPawnExtensionComponent.h` 的注释里也写明了"队伍级 ASC 将来仍走这条路"，
现在是它第一次被真正用上。

**第 6 步：受影响的资产**

| 资产 | 改动 |
|---|---|
| `DA_AbilitySet_Common` | 移除 `GrantedAttributes` 里的 `GGYGOHealthSet` 与 `GGYGOCombatSet`，只留 Ability |
| `DA_Pawn_Pyrios` | 不变。PawnData 的字段语义未变 |
| `BP_PC_Pyrios` | 不变，但它现在没有自带 ASC 组件了（父类改动带来的） |

**验证顺序**：编译通过只说明类型正确。运行时要按这个顺序确认——
Slot 生成且 Owner 是 PlayerController → Pawn 拿到非空 ASC →
HealthComponent 找到 HealthSet（不再报错）→ 输入能激活能力（预测键有效，
本地立即响应而非等一个 RTT）→ 切人后待命角色的 GE 计时继续。
第四项是约束 1 的唯一可观测信号，必须专门验。

## 10. 移动层重建（D3）

> 本章只讲 **locomotion**（走跑转身）这一层。攻击、闪避、突进这类**动作位移**的驱动方式
> 单独在[第 13 章](#13-动作位移驱动)展开，两者最终都落到 CMC，但决策点完全不同。

### 10.1 为什么移动逻辑必须写在 CMC 内部

在 CMC **外面**驱动移动（每帧覆写 `MaxWalkSpeed`、调 `RequestDirectMove`、
直接改 Actor 朝向）在单机下能跑，联机下必然出错：那些写入发生在
`SavedMove` / `NetworkPrediction` 体系之外，服务器重演客户端的 move 时拿不到它们。

三个后果：

1. **没有移动复制。** `ReplicateMoveToServer` / `ClientAdjustPosition` 被绕过，两端各算各的。
2. **没有客户端预测与纠正。** 高延迟下角色会橡皮筋。
3. **服务器无法验证。** 位置不经校验，作弊客户端可以任意改。

所以速度与状态一律走 CMC 的正规扩展点，见 10.2。

### 10.2 结构与扩展点

```
Character/
  Components/
    GGYGOCharacterMovementComponent.h/.cpp   UCharacterMovementComponent 派生
    GGYGOAnimCurveSampler.h/.cpp             纯 C++，RM_* 曲线采样与差分
  Data/
    GGYGOMovementSet.h/.cpp                  移动参数 DataAsset
    GGYGOMovementTypes.h                     EGGYGOGait / EGGYGOTurnBackPhase
```

CMC 只用三个扩展点，别的一律交给引擎：

| 扩展点 | 承担 | 为什么是这里 |
|---|---|---|
| `GetMaxSpeed()` | 速度上限 | CMC 自己在 `CalcVelocity` 里调它，加减速、摩擦、坡度、碰撞全部沿用引擎实现 |
| `UpdateCharacterStateBeforeMovement()` | 步态解算、转身推进 | 在本帧移动计算之前、且在 SavedMove 覆盖范围内 |
| `PhysicsRotation()` | 转身第一段由曲线驱动朝向 | 绕过 `Super` 就等于这一帧只有曲线在转角色，不必临时关掉自动朝向再恢复 |

移动被禁止时 `GetMaxSpeed()` 返回 0，而不是调 `StopMovementImmediately()`。
返回 0 走的还是 CMC 自己的制动减速度，会平滑压到零；瞬间定住在联机下会与服务器重演结果不一致。

预测数据：步态、走跑计时器、曲线运动量、转身相位都属于"影响移动结果但不在基类里"的状态，
必须进自定义 `FSavedMove_Character`（参与 `CanCombineWith` / `SetMoveFor` / `PrepMoveFor`），
否则回放结果与首次执行不同。这是这一层最容易出错的地方。

**步态只由本地控制端解算**，经 `CompressedFlags` 传给服务器。若服务器自算，
两端对"输入从哪一帧开始"的采样差异会让计时器错开，升档时机相差若干帧，
期间速度上限不同，位置校正持续触发。代价是客户端理论上可谎报步态，
收益上限仅走跑速差，位置本身仍受服务器校验。

### 10.3 ZZZ 曲线位移怎么接进 CMC

ZZZ 的位移信息存在动画的自定义曲线里（`RM_Speed` / `RM_PosX` / `RM_PosY` / `RM_Dist` /
`RM_Yaw` / `RM_VelocityDirX` / `RM_VelocityDirY`），不是 UE 原生 RootMotion。三种接法：

| 接法 | 机制 | 运行时可干预 | 复杂度 |
|---|---|---|---|
| **a. 离线烘成原生 RootMotion** | 曲线烘进 AnimSequence 的 RootMotion 轨道，CMC 通过 `RootMotionMode` 消费 | 只能整体缩放 | 低（但要处理每个资产） |
| **b. 运行时构造 RootMotionSource** | 采样曲线，输出 `FRootMotionSource_*` 交 `ApplyRootMotionSource()` | 高 | 高（要实现 `NetSerialize` / `Matches` / `PrepareRootMotion`） |
| **c. 采样成速度上限** | 采样曲线，值经 `GetMaxSpeed()` 交给 `CalcVelocity` | 高 | 低 |

**locomotion 选 c。** 理由是 locomotion 的曲线里真正消除脚滑的是 `RM_Speed`（该帧速度），
而不是位移轨迹本身——走跑的方向由玩家输入决定，只有速率必须跟动画一致。
把速率交给 `GetMaxSpeed()`，加减速、摩擦、坡度、碰撞挤压全部还是引擎在算；
换成 RootMotionSource 就等于自己重写这些，且要为每种情况定义与地形的交互。

采样值进 `FSavedMove` 就完成了预测一致性，不需要 b 的那套序列化。

**做法 a 留给动作位移**（起手、收招这类位移写死在资产里的动作），见[第 13 章](#13-动作位移驱动)。
`AAADocs/Scripts/` 下的 `run_turnback_yaw_bake.py`、`verify_turnback_program_rotation.py`
是这条烘焙链路的工具。

**做法 b 只在需要程序解算终点时用**，而那种情况下 GAS 已经提供了现成的 AbilityTask，
不需要自己接线（13.3）。

采样器独立成 `FGGYGOAnimCurveSampler` 而不是写在 CMC 里，是因为它持有跨帧基线
（上一帧的累计值），采样时机必须在 `TickComponent` 里、`Super` 之前——
放进 `UpdateCharacterStateBeforeMovement` 会在 sub-stepping 时一帧调多次，基线就错了。

段切换检测用 `RM_Dist` 回退判断，而不是位移差分：路程单调递增，位移会来回摆动；
换动画段时新段累计值从 0 重新开始，位移差分会得到一个指向反方向的大位移。

### 10.4 locomotion 状态的新归属

locomotion 不需要独立的状态机 —— 它的每一项状态都能从 CMC 或 ASC 直接推导：

| 状态 | 权威来源 |
|---|---|
| 是否在移动 | `CMC->IsMovingHorizontally()`（阈值 10 cm/s，过滤碰撞挤压的残余速度） |
| 是否有移动意图 | `CMC->HasMoveInput()`（读 `Acceleration`，因为它已被 SavedMove 保存） |
| 是否在地面 | `CMC->IsMovingOnGround()` |
| 当前速度 | `CMC->GetHorizontalSpeed()` |
| 步态 | `CMC->GetResolvedGait()` |
| 动作状态（攻击中、受击中） | ASC 的 `State.*` GameplayTag |
| 能否移动 | CMC 直接查 ASC 的 `Restriction.CantMove` |

**为什么不要 Idle/Moving 状态机**：那两个状态本身就是"有无移动输入"的投影 ——
Idle 见到方向就转 Moving，Moving 见到方向归零就转回。多一层间接只是多一处
可能与真实输入不同步的地方。

**不再需要单独的状态机对象。** locomotion 状态是 CMC 数据的派生视图，动作状态是 GAS Tag。

## 11. GameFeature 架构

### 11.1 Lyra 的模型

```
LyraExperienceDefinition (DataAsset)
  ├─ DefaultPawnData
  ├─ GameFeaturesToEnable[]
  └─ Actions[]
        ├─ AddComponents            ← 给指定 Actor 类加组件
        ├─ AddAbilities             ← 给 ASC 加 AbilitySet
        ├─ AddInputContextMapping   ← 加输入映射
        └─ AddWidgets               ← 加 UI

LyraExperienceManagerComponent（挂 GameState）
  └─ 加载 Experience → 激活 GameFeature → 执行 Actions → 广播就绪
```

**GameFeature 的价值是"按需装配"，代价是"初始化时序变复杂"。** Lyra 用 `UGameFrameworkComponentManager` 的 InitState 状态机（`ULyraPawnExtensionComponent`）协调"组件什么时候能用"，这是 Lyra 最难懂也最容易抄错的部分。

### 11.2 分两步走

**第一步（现在）：只抄 InitState 协调机制，不抄 GameFeature 插件化**

> InitState 机制与角色组件如何拆分，详见[第 14 章](#14-角色组件化与-initstate)。

- 抄 `LyraPawnExtensionComponent` 的 InitState 状态机，协调 ASC / PawnData / HeroComponent 的初始化顺序
- 抄 `LyraHeroComponent` 的 `NAME_BindInputsNow` 扩展点
- 不建 GameFeature 插件，Ability 和输入直接由 PawnData + AbilitySet 静态配置

InitState 机制本身就有独立价值，而且它是 GameFeature 的前置。它要解决的是这类竞态：
HeroComponent 想绑输入，但 ASC 还没建好；CMC 想读 `Restriction.CantMove`，但 PawnData 还没分发。
把这些顺序写成 `BeginPlay` 里一串手工排列的调用，在联机下会因为 PlayerController
到达时机不确定而失效——客户端上 Controller 可能比 Pawn 晚到几帧。

**第二步（角色数量上来之后）：把角色做成 GameFeature 插件**

- 每个角色一个 GameFeature 插件（角色 Ability、动画资产、输入配置、Cue）
- 队伍配置决定激活哪些插件
- D2 下这一步收益明显：4 人房 12 个角色，不做按需加载会把全部角色资产常驻内存

现在就上 GameFeature 收益是零（只有几个角色），成本是要同时调试 GameFeature 时序 + GAS 时序 + 新 CMC 时序三套东西。

### 11.3 第一步的落地结构

```
GameModes/
  GGYGOExperienceDefinition.h/.cpp      一局的玩法定义：GameFeature 列表 + 队伍成员
  GGYGOGameMode.h/.cpp                  按 Experience 装配，接管角色生成
Character/
  Components/GGYGOPawnExtensionComponent.h/.cpp   InitState 协调
  Data/GGYGOPawnData.h/.cpp                       角色定义 DataAsset
Teams/
  GGYGOSquadComponent.h/.cpp            队伍成员与出战切换（挂 PlayerState）
```

**GameFeature 的激活在 `InitGame`，但不等待完成**。完整的异步等待需要
`ExperienceManagerComponent` 那一套状态机；当前时序下激活在 `InitGame`、
角色生成在 `HandleStartingNewPlayer`，中间隔着关卡加载，通常足够。
第二步做插件化时这里必须补上等待，否则角色生成时它的 GameFeature 可能还没就位。

| 层 | Lyra 做法 | GGYGO 做法 | 性质 |

| 组件初始化 | InitState 状态机 | 照抄 | 照抄 |
| 数据装配 | Experience + GameFeature | 分两步，先静态 PawnData，后 GameFeature | 照抄但延后 |
| 队伍切换 | 无此概念 | PlayerState 上的 SquadComponent 换 Avatar，待命成员 ASC 不动 | **全新** |
| 联机形态 | 一玩家一角色 | 一玩家一支队伍（D2），4×3 量级 | **重大差异** |

## 13. 动作位移驱动

配套子图：[[GGYGO_模块_移动与位移.canvas]]

本章回答三个问题：攻击动作的位移**用什么机制驱动**、**终点解算写在哪里**、
**动画做成 in-place 还是带 RootMotion**。

### 13.1 先澄清一组容易混的概念

问题里"用 in-place 还是蒙太奇"其实把两个不相干的维度并列了，它们是正交的：

| 维度 | 选项 | 说明 |
|---|---|---|
| **播放方式** | Montage / 直接播 Sequence / AnimBP 状态机 | 动画**怎么播** |
| **位移来源** | 动画自带 RootMotion / 程序驱动位移 | 位移**谁算的** |

一个 Montage 可以带 RootMotion 也可以不带；一个 in-place 动画既能用 Montage 播也能用状态机播。

**播放方式对动作游戏没有选择余地：必须用 Montage。** 原因不是习惯，是功能：
- AnimNotify / NotifyState 打判定窗口、可取消点、连段窗口 —— 只有 Montage 有稳定的时间轴可挂
- Montage Slot 支持上下半身分层，让攻击动作能与 locomotion 混合
- `MontageBlendOut`、`Montage_Stop` 提供被打断时的可控退出
- GAS 的 `PlayMontageAndWait` 与预测/复制链路是配套的

所以真正要选的只有**位移来源**，下面展开。

### 13.2 位移来源的四种做法与取舍

| 做法 | 机制 | 位移可控性 | 脚滑风险 | 联机 | 适用 |
|---|---|---|---|---|---|
| **A. 纯 RootMotion** | 位移烘进动画，`bEnableRootMotion=true`，CMC 通过 `RootMotionMode` 消费 | 无（写死在资产里） | 无 | 自带复制 | 位移固定的动作：起手、收招、翻滚 |
| **B. RootMotion + 缩放** | A 基础上用 `SetRootMotionTranslationScale` 整体缩放 | 只能等比缩放 | 低 | 自带复制 | 需要按角色体型或 Buff 微调幅度 |
| **C. In-place + RootMotionSource** | 动画不带位移，位移由 `FRootMotionSource_*` 程序生成，交 CMC 应用 | **完全可控，可指定终点** | 中（需对齐节奏） | 自带复制与预测 | **需要程序解算终点的动作：突进、位移技、追击** |
| **D. 直接改 Actor 位置** | `SetActorLocation` / `AddActorWorldOffset` | 完全可控 | 高 | **不可用** | 无（联机下不成立，见下） |

**结论：你要的"位移终点程序解算"对应做法 C。** 做法 A 作为不需要解算的动作的默认选择，两者共存。

D 之所以不可用，是它绕过了 CMC 的 `ReplicateMoveToServer` / `ClientAdjustPosition`，
服务器和客户端各算各的必然漂移，且服务器无法验证位置（作弊客户端可任意传送）。

### 13.3 做法 C 的具体实现：GAS 自带的 RootMotion AbilityTask

不需要自己写 RootMotionSource 的接线。UE 5.8 的 GameplayAbilities 插件已经提供了五个 AbilityTask，
位于 `Plugins/Runtime/GameplayAbilities/.../Abilities/Tasks/`：

| AbilityTask | 底层 RootMotionSource | 用途 |
|---|---|---|
| `AbilityTask_ApplyRootMotionMoveToForce` | `FRootMotionSource_MoveToForce` | **移动到一个固定坐标**，指定时长 |
| `AbilityTask_ApplyRootMotionMoveToActorForce` | `FRootMotionSource_MoveToDynamicForce` | **移动到一个 Actor**，目标会动也能跟上 |
| `AbilityTask_ApplyRootMotionConstantForce` | `FRootMotionSource_ConstantForce` | 恒定方向推力，用于击退、滑行 |
| `AbilityTask_ApplyRootMotionRadialForce` | `FRootMotionSource_RadialForce` | 以某点为中心的吸引/排斥，用于吸附、爆炸击飞 |
| `AbilityTask_ApplyRootMotionJumpForce` | `FRootMotionSource_JumpForce` | 抛物线跳跃/跃击 |

这些 Task 全都是 `Replicated` 且带 `TickTask`，走 CMC 的 `FRootMotionSourceGroup`，
因此**网络复制与客户端预测是免费的**——这正是不自己造轮子的关键理由。

#### 三个参数决定手感，值得单独记住

`MoveToActorForce` 的完整签名里有几个参数是做手感的核心：

```cpp
static UAbilityTask_ApplyRootMotionMoveToActorForce* ApplyRootMotionMoveToActorForce(
    UGameplayAbility* OwningAbility,
    FName TaskInstanceName,
    AActor* TargetActor,
    FVector TargetLocationOffset,                    // 停在目标身前而不是身体里
    ERootMotionMoveToActorTargetOffsetType OffsetAlignment,
    float Duration,                                  // 位移总时长，要和 Montage 段落对齐
    UCurveFloat* TargetLerpSpeedHorizontal,
    UCurveFloat* TargetLerpSpeedVertical,
    bool bSetNewMovementMode, EMovementMode MovementMode,
    bool bRestrictSpeedToExpected,
    UCurveVector* PathOffsetCurve,                   // ★ 路径偏移：做弧线、侧滑、抛物
    UCurveFloat* TimeMappingCurve,                   // ★ 时间重映射：做"前段爆发、后段刹停"
    ERootMotionFinishVelocityMode VelocityOnFinishMode,
    FVector SetVelocityOnFinish,                     // 结束瞬间速度，决定收招是否带惯性
    float ClampVelocityOnFinish,
    bool bDisableDestinationReachedInterrupt,
    float ReachedDestinationDistance = 50.0f);       // 到达判定半径
```

- **`TimeMappingCurve` 是解决脚滑的主要手段。** 动画的视觉位移不是线性的（起手慢、突进快、收招停），
  如果程序位移匀速推进，脚步和位移就会错位。把这条曲线画成和动画视觉节奏一致的形状，
  脚滑问题基本消失。这是 in-place 方案能用的前提。
- **`PathOffsetCurve`** 让路径不必是直线，可以做侧向绕行、跃起再落下。
- **`SetVelocityOnFinish`** 决定动作结束时角色是立刻停住还是带一点惯性滑出，影响"重量感"。

另有 `ApplyRootMotionMoveToTargetDataActorForce`，直接从 `FGameplayAbilityTargetDataHandle`
取目标。命中判定已经产出 TargetData 时用它，省一次目标查找。

### 13.4 终点解算写 C++ 还是蓝图

> 本节是设计结论，解算器尚未实现（15.3）。它的形态取决于锁定系统与真实的攻击动作，
> 现在先造一套结构等着被填只会浪费一次返工。

**解算写 C++，参数配在数据资产，蓝图只做表现编排。** 三条理由：

1. **联机确定性。** 突进终点必须在客户端预测和服务器权威上算出**相同结果**，否则会出现
   客户端冲到位、服务器判定没到位，然后被 `ClientAdjustPosition` 拉回去的橡皮筋。
   蓝图容易引入非确定性来源（Tick 顺序依赖、随机、浮点累积路径不一致）；C++ 里可以把解算
   写成纯函数，输入相同必然输出相同。
2. **解算本身是几何与查询问题。** 目标筛选、扇形范围判定、障碍物检测、贴墙修正，
   这些是向量运算加 `SweepSingleByChannel`，在蓝图里连线又长又慢又难调。
3. **可测试。** 纯函数的解算器可以脱离运行时单测，蓝图不行。

但**不要把参数硬编码进 C++**。分工是：

```
C++（解算逻辑，确定性）
  └─ UGGYGOMotionWarpSolver::SolveDashTarget(
         const FGGYGOMotionWarpParams& Params,   ← 参数从资产来
         const FGGYGOMotionWarpContext& Context, ← 运行时上下文
         FGGYGOMotionWarpResult& OutResult)      ← 终点、时长、曲线选择

数据资产（可调参数，美术/策划改）
  └─ UGGYGOMotionWarpParams：最大突进距离、最小距离、停止余量、
                             时长、PathOffsetCurve、TimeMappingCurve

蓝图（表现编排，可选）
  └─ GA 的蓝图子类：串 Montage、Cue、镜头，但不参与终点计算
```

推荐的落地形态是**在 C++ GA 里做解算并启动 AbilityTask**，蓝图子类只覆盖表现部分。
纯蓝图 GA 只适合完全无位移解算的简单能力。

### 13.5 一次攻击的完整时序（做法 C）

```
1. HeroComponent 收到 InputTag.Attack.Light → ASC 缓存句柄   [本地]
2. Controller 的 PostProcessInput → ProcessAbilityInput
     → 组仲裁通过 → TryActivateAbility                      [生成 PredictionKey]
3. GA 的 ActivateAbility                                    [客户端预测 + 服务器]
     ├─ 解算终点/时长/曲线                                   [C++ 纯函数，两端一致]
     ├─ 启动 PlayMontageAndWaitForEvent（in-place 攻击 Montage）
     └─ 启动 ApplyRootMotionMoveToActorForce（或 MoveToForce）
4. CMC 逐帧消费 RootMotionSource 推进位移                    [自带复制与纠正]
5. Montage 上的 AnimNotify 发 GameplayEvent                 [判定窗口开/关]
6. Task 的 EventReceived → MeleeTraceComponent 开窗 → 命中 → 应用伤害 GE
7. GE 触发 GameplayCue → 特效音效震屏
8. Montage 结束或被打断 → EndAbility
     └─ RootMotionSource 随 Task 销毁自动移除
     └─ 相机接管随 EndAbility 自动撤销
```

关键点：**位移和动画是两条并行的轨道，由同一个 GA 启动、共享同一个时长**。
它们不互相驱动，而是各自独立地被对齐到同一个时间基准上。

### 13.6 什么时候用做法 A（纯 RootMotion）

不是所有动作都要程序解算。判断标准很简单：**位移终点是否依赖运行时上下文**。

| 动作 | 位移终点依赖运行时？ | 选择 |
|---|---|---|
| 原地轻攻击 | 否，固定小前冲 | A |
| 翻滚 / 后跳 | 否，固定距离 | A |
| 收招、起手 | 否 | A |
| 突进斩（冲到敌人身前） | **是，依赖目标位置** | C |
| 位移技（冲一段距离但要避开墙） | **是，依赖障碍** | C |
| 追击连段（目标在移动） | **是，依赖目标实时位置** | C（MoveToActorForce） |
| 被击退 | **是，依赖伤害方向与强度** | C（ConstantForce） |

做法 A 的资产要求：动画在 DCC 里保留根骨骼位移，导入时勾 `EnableRootMotion`，
`RootMotionRootLock` 按需设为 `RefPose` 或 `AnimFirstFrame`。

### 13.7 与 ZZZ 曲线位移的关系

第 10.3 节讨论的 ZZZ 曲线（`RM_PosX` / `RM_PosY` / `RM_Yaw`）属于 **locomotion** 层，
和本章的动作位移是两套东西，不要混：

| | locomotion（第 10 章） | 动作位移（本章） |
|---|---|---|
| 来源 | ZZZ 动画的自定义曲线 | 程序解算或动画 RootMotion |
| 驱动 | 烘成 UE RootMotion（路径 a）或运行时 RootMotionSource（路径 b） | GAS 的 ApplyRootMotion* Task |
| 发起者 | CMC / AnimInstance | GameplayAbility |
| 是否走 GAS | 否 | 是 |

两者最终都落到 CMC 的 `FRootMotionSourceGroup`，**CMC 会把同时存在的多个 RootMotionSource 累加**。
这带来一个必须注意的冲突点：攻击时如果 locomotion 仍在推进位移，两份位移会叠加成双倍速度。

处理方式：攻击类 GA 激活期间给 ASC 加 `Restriction.CantMove`，
`UGGYGOCharacterMovementComponent` 读到它就停止接受移动输入（但不影响 GA 自己的 RootMotionSource）。
"能不能移动"因此只有一个权威来源：ASC 上的 `Restriction.CantMove`，由 CMC 直接查询。
不要再给移动加第二个开关（组件上的 bool、每帧被清零的仲裁字段），
两个开关必然出现"一个说能动一个说不能"的帧。

### 13.8 是否需要 Motion Warping 插件

UE 自带 `MotionWarping` 插件，能按 Montage 上的 `MotionWarpingWindow` NotifyState
把动画自带的 RootMotion **重定向**到指定目标点。它和做法 C 的区别：

| | RootMotionSource（做法 C） | Motion Warping |
|---|---|---|
| 位移形状 | 程序生成 | 来自动画 RootMotion，只是被拉伸/旋转到目标 |
| 脚滑 | 靠 TimeMappingCurve 对齐 | 天然较好（形状还是动画的） |
| 精确终点 | 支持 | 支持 |
| 复杂度 | 中 | 需要给每个动画标 Warp 窗口 |

**Motion Warping 更适合"动画已经有很好的位移形状，只需要拉到目标点"的情况**，
这对做法 A 的资产是天然搭配。建议：先用做法 C 把突进跑通（不依赖额外插件），
等攻击动作数量上来、脚滑成为实际问题时再评估引入 Motion Warping。这一项列入待决策。

## 14. 角色组件化与 InitState

配套子图：[[GGYGO_模块_角色与组件.canvas]]

### 14.1 为什么角色要拆成组件

把 Actor 本体、GAS 宿主、输入处理、动画数据接口写在同一个角色类里，
问题不在"代码多"，而在**这些职责的生命周期与复用边界完全不同**：

- 输入绑定只对本地控制的玩家角色有意义，AI 角色不需要
- GAS 宿主对所有角色都需要
- 动画数据接口是给 AnimBP 的读接口，应当由 AnimInstance 自己去拉（第 8.3 节）

写在一个类里的后果是：加一个新角色类型（AI、载具、可操控道具）只能继承这个胖类，
继承来一堆不需要的东西；想给现有角色加一套能力（比如装备系统）只能改基类。

拆成组件后，"这个单位要不要响应输入"由**挂不挂那个组件**回答，
而不是在运行时判断。

### 14.2 Lyra 的拆法（读源码确认）

`ALyraCharacter` 本身只挂**三个**组件：

```
ALyraCharacter
├─ ULyraPawnExtensionComponent   ← 协调者，所有角色都有
├─ ULyraHealthComponent          ← 生命与死亡流程
└─ ULyraCameraComponent          ← 相机

玩家角色额外挂：
└─ ULyraHeroComponent            ← 输入绑定 + 相机模式选择（AI 不挂）
```

拆分依据是**"这个能力属于所有 Pawn，还是只属于被玩家控制的 Pawn"**。
`HeroComponent` 这个名字容易误解——它不是"英雄角色"，而是"被玩家操控的那个"。
下场角色交给 AI 时，把 HeroComponent 拿掉即可，这正好服务于队伍切换（决策 D1）。

#### `ULyraPawnExtensionComponent`：协调者而非功能组件

它自己几乎不实现玩法，职责是**让其他组件不必关心初始化顺序**：

- 持有 `PawnData`（`EditInstanceOnly` + `ReplicatedUsing = OnRep_PawnData`）与 ASC 缓存
- 暴露两个委托 `OnAbilitySystemInitialized` / `OnAbilitySystemUninitialized`
- 提供 `OnAbilitySystemInitialized_RegisterAndCall`：**注册时如果 ASC 已经就绪就立刻回调一次**。
  这个细节很重要，它消除了"我注册晚了，错过了通知"这类竞态
- 提供给 Pawn 调用的钩子：`InitializeAbilitySystem` / `UninitializeAbilitySystem` /
  `HandleControllerChanged` / `HandlePlayerStateReplicated` / `SetupPlayerInputComponent`
- `InitializeAbilitySystem` 会处理"目标 ASC 已经有别的 Avatar"的情况——**队伍换角色时正是这个路径**

#### `ULyraHealthComponent`：把 AttributeSet 包成可用的 API

注意它继承 `UGameFrameworkComponent` 而不是 `UPawnComponent`（不限定必须挂在 Pawn 上）。
它做三件事：

1. **委托类型转换**：`ULyraHealthSet` 上的委托是原生 C++ 六参委托（`FLyraAttributeEvent`），
   蓝图绑不上。HealthComponent 把它们转成 `BlueprintAssignable` 的动态委托
   （`OnHealthChanged` / `OnMaxHealthChanged` / `OnDeathStarted` / `OnDeathFinished`）
2. **持有死亡状态机**：`ELyraDeathState{NotDead, DeathStarted, DeathFinished}`，
   `ReplicatedUsing = OnRep_DeathState`。死亡是个**有中间态的过程**（演出中 vs 演出完），
   放在 AttributeSet 里不合适，AttributeSet 只该管数值
3. **只读转发**：`GetHealth` / `GetMaxHealth` / `GetHealthNormalized`，让 UI 不必直接摸 AttributeSet

这条分工值得照抄：**AttributeSet 管数值与钳制，Component 管流程与对外 API。**

### 14.3 InitState 四阶段状态机

这是 Lyra 最有价值也最容易抄错的部分。它解决的问题是：
组件 A 需要 ASC 就绪才能初始化，组件 B 需要 PawnData 就绪，PawnData 又要等 PlayerState 复制到，
而这些事件在不同网络角色上**到达顺序不确定**。手工排 `BeginPlay` 顺序在单机能跑，联机必然出竞态。

四个状态 Tag 构成一条链：

```
InitState.Spawned  →  InitState.DataAvailable  →  InitState.DataInitialized  →  InitState.GameplayReady
```

每个参与协调的组件实现 `IGameFrameworkInitStateInterface`，并注册一个 feature 名
（`NAME_ActorFeatureName`）。核心 API 与调用时机：

| API | 何时调用 | 作用 |
|---|---|---|
| `RegisterInitStateFeature()` | `OnRegister` | 把自己登记为一个 feature |
| `BindOnActorInitStateChanged(NAME_None, FGameplayTag(), false)` | `BeginPlay` | 监听**所有** feature 的状态变化 |
| `TryToChangeInitState(Tag)` | `BeginPlay` 推进到 Spawned | 请求进入某状态 |
| `CanChangeInitState(...)` | 由 Manager 回调 | **守卫**：声明进入下一状态的前置条件 |
| `HandleChangeInitState(...)` | 状态真正切换时 | 执行该状态对应的初始化动作 |
| `OnActorInitStateChanged(...)` | 任何 feature 状态变化时 | 别人前进了，再试着推进自己 |
| `CheckDefaultInitializationForImplementers()` | 推进前 | 先推进自己依赖的其他 feature |
| `ContinueInitStateChain(StateChain)` | `CheckDefaultInitialization` | 沿链尽可能往前走 |

`ULyraPawnExtensionComponent::CanChangeInitState` 的实际条件：

| 目标状态 | 前置条件 |
|---|---|
| `Spawned` | 有有效 Pawn |
| `DataAvailable` | 有 `PawnData`；且**在有权威或本地控制时**必须已被 Controller possess |
| `DataInitialized` | `Manager->HaveAllFeaturesReachedInitState(Pawn, DataAvailable)` ← **等所有 feature 就绪** |
| `GameplayReady` | 无条件 |

**`DataInitialized` 那一步是整个机制的核心**：它把"等别人"这件事从各组件的手工判断
变成了 Manager 的统一查询。任何一个组件没准备好，所有组件都停在 `DataAvailable`，
不会出现"一半初始化了一半没有"的中间态。

`HandleChangeInitState` 在 PawnExtension 里几乎是空的，注释写明
"This is currently all handled by other components listening to this state change"——
协调者只负责推进状态，具体初始化由监听者各自完成。

### 14.4 GGYGO 的落地设计

```
AGGYGOCharacterBase（参考 ALyraCharacterWithAbilities，自带 ASC —— 决策 D1）
├─ UGGYGOAbilitySystemComponent          ← 角色自己的 ASC
├─ UGGYGOHealthSet / UGGYGOCombatSet     ← 属性集子对象
├─ UGGYGOPawnExtensionComponent          ← 协调者
├─ UGGYGOHealthComponent                 ← 生命/韧性/死亡流程
└─ UGGYGOCharacterMovementComponent      ← CMC 派生（第 10 章）

AGGYGOHeroCharacter（继承上者，玩家操控的角色）
├─ UGGYGOHeroComponent                   ← 输入绑定
└─ UGGYGOCameraComponent                 ← 相机模式栈（第 8 章）
```

**玩家角色单独一个类，而不是给基类挂上再判断是否受控**：HeroComponent 是 InitState 的一个
feature，`PawnExtension` 的 `DataInitialized` 要等**所有** feature 到达 `DataAvailable`。
每个 AI 敌人都带一个永远等不到 PlayerController 的 feature，整条初始化链会卡住，连动画都起不来。

队伍成员管理挂 PlayerState（`UGGYGOSquadComponent`）而不是角色，因为它要跨越角色死亡与切换而存在。

与 Lyra 的差异有两处：

1. **ASC 挂在角色自己身上**（D1），所以 `PawnExtensionComponent` 的
   `InitializeAbilitySystem(InASC, InOwnerActor)` 里 Owner 和 Avatar 都是角色本身，
   不像 Lyra 那样 Owner 是 PlayerState。
2. **`HealthComponent` 要多管韧性**。`UGGYGOHealthSet` 把生命和韧性放在一起
   （同一次命中同时改两者，拆成两个属性集就得跨 Set 读写），所以组件也要把
   `OnPoiseChanged` / `OnPoiseBroken` 一并包装成动态委托，并持有破韧状态。

### 14.5 职责怎么划到组件上

划分标准是**生命周期与复用边界**，不是代码量。同一个类里塞进生命周期不同的职责，
就只能靠 `BeginPlay` 里的顺序把它们串起来，而那个顺序在联机下不成立。

| 职责 | 归属 | 理由 |
|---|---|---|
| ASC + AttributeSet 子对象 | 角色类本身 | D1，ASC 必须与 Avatar 同生命周期 |
| 授予默认能力与效果 | `UGGYGOAbilitySet` + PawnData | 数据驱动，换角色就换一份配置 |
| 输入绑定 | `UGGYGOHeroComponent` | 只对本地玩家有意义，AI 不需要 |
| 动画数据 | AnimInstance 自拉 | 见 8.3。让角色类转发只是多一层会失同步的镜像 |
| 移动状态与速度 | CMC | D3，只有 CMC 内部的写入会被 SavedMove 覆盖 |
| 生命/韧性/死亡流程 | `UGGYGOHealthComponent` | 死亡是可复制的状态机，需要独立的复制单元 |
| 角色定义（能力、动画、参数） | `UGGYGOPawnData` | 配在 Pawn 蓝图默认值上时，换一套能力就得复制整个蓝图 |

**初始化的验证标准**：不依赖任何手工排列的调用序列，
在 Listen Server、Dedicated Server 客户端、以及运行时动态生成的角色上，
都能稳定到达 `GameplayReady`。

## 15. 实施结果

前面各章的 C++ 部分均已落地并编译通过。本章记录**实际做出来的东西与设计的差异**，
以及还需要在编辑器里做什么才能真正跑起来。

### 15.1 与计划的偏离

| 领域 | 计划 | 实际 | 原因 |
|---|---|---|---|
| 移动 | CMC 直接承接曲线驱动 | 固定 `WalkSpeed` / `RunSpeed` 与曲线速度**并存**，曲线不可用时回落到固定值 | 曲线只在有 `RM_*` 曲线的动画播放时有值。没有回落档时，任何一个未烘焙曲线的动画会让角色完全不能动 |
| 角色类 | 只有 `AGGYGOCharacterBase` / `AGGYGOHeroCharacter` | 另有 `ABaseCharacter` / `APlayerCharacter` 两层**过渡壳**，只做 getter 转发 | 它们是 `BP_Player` / `BP_Miyabi` 的父类，而 `Content/` 不在版本控制内，改父类出错无法回退 |
| 攻击 | `GA_Attack_Light` 完整动作 | 伤害 Execution、近战判定、连段缓冲齐备；**没有具体的攻击 GA** | 攻击 GA 的主体是 Montage 编排与判定窗口通知，那些是资产而非代码 |
| 位移解算 | `MotionWarpSolver` 解算位移终点 | **未实现** | 它的输入是"目标在哪、想停在哪"，需要先有锁定系统与真实的攻击动作才能定形态 |
| 队伍 | 队伍级 ASC（挂 PlayerState） | **未建**，只有 `UGGYGOSquadComponent` | 目前没有任何队伍共享属性，建了就是一个谁都不读的 ASC |
| ASC 归属 | Slot 持有 ASC（D1 修订后） | **待改造**，当前 ASC 仍是 `AGGYGOCharacterBase` 的默认子对象 | D1 最初定的是"ASC 挂 Pawn"，落地后暴露出属性集就绪时机问题（见 15.3 第 1 条），已修订为 Slot 方案，改动清单见 9.6 |
| 联机 | Dedicated Server 实测预测与纠正 | 只补了转身状态的复制通道 | 联机验证需要能实际跑起来的场景，依赖 15.2 的资产配置 |
| Experience | 异步加载与等待 | GameFeature 在 `InitGame` 激活但**不等待完成** | 完整的异步等待需要 ExperienceManagerComponent 那一套；当前时序（激活在 `InitGame`、生成在 `HandleStartingNewPlayer`）通常够用 |

两项计划外的产出：

- **`.kiro/steering/code-comments.md`**：注释规范。核心是注释描述当下代码，
  不记录"从什么变成什么"—— 那属于 git log。历史型注释里被提及的类一旦删除，
  注释就变成读者查不到的死引用。
- **`InputTag` 根标签**：让"这个 Tag 是不是输入标签"能用一次层级匹配回答。

**Cue 资产的放置位置**

Cue 资产必须放在 `Content/GameplayCues/` 下 —— `DefaultGame.ini` 的
`GameplayCueNotifyPaths` 只扫这个目录。放在别处不会报错，但所有 Cue 都会
找不到而静默不播，这是个很难排查的失败模式。

Cue 走按需异步加载，所以要在 PawnData 的 `CuesToPreload` 里列出该角色会用到的
Cue Tag 做预热，否则第一次触发时资产还没就位（"第一刀没有火花"）。
排查特效不播时可以用 `UGGYGOGameplayCueManager::DumpPreloadedCues` 确认
是加载问题还是 Cue 本身的问题。

**蓝图改动**

- 玩家角色蓝图父类改为 `AGGYGOHeroCharacter`，并在其 `HeroComponent` 上配 IMC
- `BP_PlayerController` 的父类已是 `AGGYGOPlayerController`（类名未变，无需改动）

**动画资产**

- 移动动画需要烘焙 `RM_Speed` / `RM_PosX` / `RM_PosY` / `RM_Dist` / `RM_Yaw` 曲线；
  `RM_VelocityDirX` / `RM_VelocityDirY` 可用 `AnimSyncMarkerTools::BakeVelocityDirectionCurves` 生成
- 转身动画需要一个名为 `CanYaw` 的 AnimNotify，它决定何时把控制权交还输入
- 攻击 Montage 需要用 `AnimNotify_GameplayEvent`（或等价的自定义 Notify）发出这些事件，
  它们由 `PlayMontageAndWaitForEvent` 的 `EventReceived` 接收：

  | 事件 Tag | 攻击 GA 该做什么 |
  |---|---|
  | `Event.Montage.HitWindowBegin` | `MeleeTraceComponent->BeginTraceWindow()` |
  | `Event.Montage.HitWindowEnd` | `EndTraceWindow()` |
  | `Event.Montage.ComboWindow` | 此后按键可衔接下一段 |
  | `Event.Montage.CancelPoint` | 此后允许被其它动作打断 |

### 15.3 已知缺口

按影响程度排列。

**会让功能不完整**

1. **HealthComponent 拿不到 HealthSet（已在 PIE 复现，架构级）**。
   运行时生成的角色必然命中：`InitializeAbilitySystem` 在 `PostInitializeComponents`
   阶段广播 `OnAbilitySystemInitialized`，此时 PawnData 尚未设置、`GrantAbilitySets`
   还没执行，`HealthComponent` 取不到 `UGGYGOHealthSet` 便报错并把自己的 ASC 引用置空；
   之后 `DataInitialized` 才授予属性集，但不再广播，`HealthComponent` 没有第二次机会。
   结果是生命与韧性全部失效。关卡里手摆的角色反而可能正常（PawnData 在
   `PostInitializeComponents` 前就有值），所以表象是"偶发"。
   **根因是 ASC 归属，不是配置遗漏**，修法见 9.6 的 Slot 改造；
   在 Slot 方案落地前，任何依赖属性集的功能都无法验证。
2. **攻击 GA 未实现**。所有依赖都已就位 —— `PlayMontageAndWaitForEvent`（播动画并接收
   判定窗口通知）、`UGGYGOMeleeTraceComponent`（判定）、`GGYGODamageExecution`（伤害）、
   `GGYGOGameplayCueNotify_HitImpact`（反馈）、组仲裁与连段缓冲。
   缺的是把它们串起来的那个能力，它的主体是 Montage 编排。
   已建 `GA_Attack_Light` / `GA_Dodge` / `GA_HitReact` / `GA_Death` 四个空壳蓝图，
   只配了组身份与优先级，没有 Montage 编排。

**联机相关**

3. **转身第一段的位移方向在服务器不评估动画时会分歧**。曲线值是本地状态，
   彻底解决需要把曲线量放进 `FCharacterNetworkMoveData` 随 ServerMove 发送。
4. **联机未实测**。预测与纠正的正确性只做了静态推理，没有跑过 Dedicated Server。

**手感相关**

5. **松手防抖窗口未实现**。快速点按方向键会让动画在起步与停止之间抖动，
   抑制它需要输入层持有一个短的方向保持窗口。
6. **`IA_Sprint` / `IA_ForceWalk` 无效果**。步态只有走跑两档、靠持续时长升档，
   没有"按住冲刺"这一档，这两个键的语义待定。

**清理项**

7. **单体 `Attributes/GGYGOAttributeSet` 仍在**。已无 C++ 引用方，但蓝图 GE 引用它。
   清理它之后可以把 `GGYGOAttributeSetBase` 改回正名 `UGGYGOAttributeSet`。
8. **`BaseCharacter` / `PlayerCharacter` 过渡壳**。蓝图父类逐个改到 `AGGYGOHeroCharacter`
   之后即可删除，两个类都已标 `DeprecatedNode`。
9. **`Source/GGYGO/README.md` 与代码不同步**，暂不作为参考；模块速查用 [[模块参考]]。

**验证状态**：以上结论与全文的"已落地"均指**静态检查与编译通过**。
运行时行为一次都没有验证过 —— 项目还缺 15.2 的资产，起不到能操控角色的状态。

### 15.4 共享资产的归属

哪些 GameplayEffect 该放 `UGGYGOGameData`、哪些该配在别处，判断标准是
**谁施加它**。

| GE 类型 | 归属 | 理由 |
|---|---|---|
| 伤害、治疗 | `UGGYGOGameData` | 施加者可能是攻击能力、环境伤害、跌落伤害。放在能力上会让环境伤害拿不到 |
| 自毁 | `UGGYGOGameData` | 由 HealthComponent 直接应用，没有对应的能力 |
| 冷却 | **能力自己** | GAS 原生支持 `CooldownGameplayEffectClass`，每个能力的冷却时长本就不同 |
| 限制类（禁止移动、无敌帧） | **能力自己** | 它们属于施加它们的那个能力，随能力结束而移除 |
| 属性初始化 | `UGGYGOAbilitySet` | 每个角色的初始属性不同，属于角色定义 |

`UGGYGOAssetManager` 有两处刻意不用 `Fatal`（Lyra 原版用的是 Fatal）：

- **GameData 资产缺失**只警告。那份资产是在编辑器里创建的，若在启动时中止，
  引擎会在能创建资产之前就起不来 —— 一个死循环。
- **`AssetManagerClassName` 配错**用 Error 加兜底实例。这是个在编辑器里
  就能改好的配置问题，把工具链堵死代价太大。

因此 `UGGYGOGameData::Get()` 返回**可空指针**，调用方必须判空并给出
指向自身功能的错误信息。
